# OpenBao — activation in one sitting (SSC)

From "OpenBao is enabled in the values" to "OpenBao is unsealed, configured
and serving Frank!Gateway", in one flow: prepare once, deploy, run one
script. Written for SSC hosting; it works the same for any environment.

The script is [`scripts/openbao-activate.sh`](../../../scripts/openbao-activate.sh).
Background on every piece is in
[`frankgateway-openbao.md`](frankgateway-openbao.md); the step-by-step manual
alternative is the [deployment runbook](frankgateway-deploy-runbook.md).

## The flow

| # | What | Who / where | Key Vault writes |
|---|---|---|---|
| 1 | Prepare: database, Key Vault items, route, certificate | pipeline / Terraform, once per environment | creates 3 items, no secret typed by hand |
| 2 | Values | SSCHostingSync, once per environment | none |
| 3 | Keycloak role and group | chart (or Keycloak admin, once) | none |
| 4 | Deploy | normal deploy pipeline | none |
| 5 | Activate: `openbao-activate.sh` | pipeline step after the deploy | **one**: the recovery key, on the first run only |
| 6 | Give uploaders access | Keycloak admin | none |

After that, run the same script after every deploy (step 7). It changes
nothing when all is well.

## 1. Prepare once (pipeline)

Everything secret is generated by the pipeline, so nobody types or copies a
secret.

**Key Vault items** in the environment Key Vault:

| Item | Value at creation | Used by |
|---|---|---|
| `openbao-db-admin` (the environment's usual DB password naming) | random password, like every other app database | the deploy, as `openbao.database.password` |
| `openbao-seal-key` | **32 random alphanumeric characters**; never regenerate it (Terraform `ignore_changes`) | the deploy, as `openbao.seal.static.key` |
| `openbao-unseal-key` | the literal text `pending-init` | the activation script, which replaces it with the recovery key once |

- Enable **soft delete and purge protection** on the vault: losing
  `openbao-seal-key` loses everything stored in OpenBao.
- Nothing else goes into Key Vault. The root token is never stored (the
  script revokes it), and the two OpenBao tokens live in Kubernetes Secrets
  and can be re-minted from the recovery key.

**Permissions** for the pipeline identity:

| Step | Needs |
|---|---|
| Deploy | read `openbao-db-admin` and `openbao-seal-key` (Key Vault Secrets User) |
| Activate | read and write `openbao-unseal-key` (Key Vault Secrets Officer, or scope it to that item); create Secrets and Jobs and exec into pods in the PodiumD namespace; `helm get` on the release |

**Database:** an Azure PostgreSQL database `openbao` with role
`openbao-admin` and the password above. The chart creates the tables.

**Route and certificate:** a route from the OpenBao host
(`openbao.configuration.oidcUrl`) to service `<release>-openbao-active`, port
`8200`, plain HTTP behind the gateway. The gateway certificate's SAN must
cover that host. Details:
[§3.3 and §3.4](frankgateway-openbao.md#33-network-route-into-the-app-gatewayingress).

**Images:** `quay.io/openbao/openbao` and `docker.io/library/postgres` at the
tags pinned in `values.yaml`, or their mirrors.

## 2. Values

```yaml
openbao:
  enabled: true
  database:
    host: <server>.postgres.database.azure.com
    password: "REP_OPENBAO_DB_PASSWORD_REP"   # pipeline-substituted
  seal:
    static:
      key: "REP_OPENBAO_SEAL_KEY_REP"         # pipeline-substituted from openbao-seal-key
  configuration:
    oidcUrl: https://<env>-openbao-admin.<gemeente>.nl
    keycloak:
      url: https://<keycloak host>
      realm: podiumd
```

- Substitute `REP_OPENBAO_SEAL_KEY_REP` from `openbao-seal-key` the same way as
  the database passwords. The render fails on a key that is not 32 bytes,
  which also catches a placeholder that was not substituted.
- Leave `openbao.configuration.secrets.keycloak_client_secret` empty: the
  chart generates the client secret and keeps it stable.
- With Frank!Gateway, nothing extra: the script mints its token into the
  Secret named by `frankgateway.openbao.tokenSecret` (default
  `frankgateway-openbao-token`).

## 3. Keycloak

The chart adds the `openbao` client to the `podiumd` realm on every deploy.
The upload permission needs two more objects:

- client role `uploaders` on client `openbao`;
- group `vault-uploaders`, with that client role assigned.

The realm import creates them only when `keycloak.config.skipRoles` and
`keycloak.config.skipGroups` are `false`. When the environment keeps the
defaults (`true`), create them once in the Keycloak admin console: Clients →
`openbao` → Roles → Create role `uploaders`; Groups → Create group
`vault-uploaders` → Role mapping → Assign role → filter by clients →
`openbao uploaders`. Names come from `openbao.configuration.uploadersRole` and
`uploadersGroup`
([§3.7](frankgateway-openbao.md#37-keycloak--oidc-integration)).

## 4. Deploy

Deploy as usual. On this first deploy the vault is still uninitialised, so
the `openbao-config` Job logs that it skipped. That is expected; step 5
configures it.

## 5. Activate

One command, as a pipeline step right after the deploy, with the pipeline's
Azure login and kube-context:

```bash
KUBE_CONTEXT=<ctx> NAMESPACE=podiumd KEYVAULT=<kv> \
  charts/podiumd/scripts/openbao-activate.sh
```

Add `AZ_SUBSCRIPTION=<id>` when the Key Vault is not in the default
subscription. Run it from a checkout of the chart version that was deployed.

What it does, stopping at the first problem:

1. **Preflight** (read-only): cluster, release, OpenBao pods, seal type,
   `openbao-unseal-key`, and the Keycloak client secret. See
   [Preflight checks](#preflight-checks).
2. **Initialise** the vault, store the recovery key in `openbao-unseal-key`
   and read it back. Write access is checked before initialising, because the
   key is returned only once.
3. **Unseal**: with the static seal the pods unseal themselves; a standby that
   stays sealed is restarted.
4. **Tokens**: the scoped config token (Secret `openbao-bootstrap-token`) and,
   when Frank!Gateway is deployed, its read-only token. The gateways are
   restarted to pick it up.
5. **Configure**: re-runs the `openbao-config` Job from the deployed release.
   It sets up the Keycloak login, the `secret` kv mount, the uploader policy
   and the group binding. A skipped run fails the script.
6. **Revoke the root token.**
7. **Verify** every pod and both tokens, and print when the gateway token
   expires.

Exit code 0 means OpenBao is operational. Secrets are never printed and never
passed as command arguments.

## 6. Give uploaders access

Add the people who write secrets to the Keycloak group `vault-uploaders`.
They log in at the OpenBao host (or `bao login -method=oidc`) and write the
gateway's keys, as in
[runbook step 5](frankgateway-deploy-runbook.md#step-5--put-the-gateways-secrets-in-openbao).

## 7. After every deploy, and lifecycle

Run the same command after every deploy. On an operational vault it checks,
re-runs the `openbao-config` Job (which renews the config token) and exits.

| Event | What happens | Action |
|---|---|---|
| Pod restart, node drain, upgrade | pods unseal themselves (static seal) | none |
| Deploy | `openbao-config` runs while pods may be restarting and can skip | the script re-runs it |
| Config token (32-day period) | renewed by every `openbao-config` run | none while you deploy at least monthly; otherwise the script mints a new one |
| Gateway token (1 year) | not renewed automatically | `openbao-activate.sh --rotate-reader-token` before the date the script prints |
| Root token | never stored | the script creates a temporary one from `openbao-unseal-key` when it needs one, and revokes it |
| Seal key rotation | — | [§3.6.1](frankgateway-openbao.md#361-static-seal-unseal-without-an-operator-optional), rotating the key |

`--check` runs the preflight and shows the seal and token status without
changing anything. Use it before a deploy or as a periodic check.

## Preflight checks

What `openbao-activate.sh` checks before it changes anything:

| Check | Fails when | Fix |
|---|---|---|
| Cluster and namespace | context or namespace unreachable | pipeline kube-context and namespace |
| Release | no `openbao-config` Job in the release | `openbao.enabled` and `openbao.configuration.enabled`, then deploy |
| Pods | an OpenBao pod is not Running | `kubectl --context <ctx> -n <ns> describe pod <release>-openbao-<i>`; usually the database (`openbao-db-schema` Job) or image pull |
| Seal type | Shamir: `openbao.seal.static.key` not set | set it (step 2) and deploy; `--allow-shamir` only for a deliberate Shamir setup |
| Seal migration | a pod is migrating from Shamir to static | finish it by hand ([§3.6.1](frankgateway-openbao.md#361-static-seal-unseal-without-an-operator-optional)) |
| `openbao-unseal-key` | missing or unreadable | create it with `pending-init` (step 1) |
| `openbao-unseal-key` | vault uninitialised but the item holds a key | check the database is the right one; reset the item to `pending-init` only when its vault is gone |
| `openbao-unseal-key` | vault initialised but the item holds `pending-init` | the key was never stored; stop and escalate |
| Keycloak client secret | no `openbao-oidc-secret` in `keycloak-podiumd-realm-secrets` | deploy with the Keycloak realm import enabled |

The chart checks at render time too (`templates/validations.yaml`): a
static-seal key that is not 32 bytes, `previousKey` without `previousKeyId`,
an override that drops the seal configuration, an empty or `example.nl`
`oidcUrl`, and Frank!Gateway without OpenBao.
