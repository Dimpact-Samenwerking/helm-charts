# Upgrade doc set Is it "Operator Friendly" ?

## Checklist

**Can the operator find what to do without reading everything?**

- [ ] The runbook is ordered for maximum clarity for the operator.
- [ ] Explanations, history and background are in a Reference part at the
      end, reached by links from the steps. Nothing has to be read to find
      out whether it needs action.
- [ ] Changes that need no action are one list of one-liners.

**Can the operator run it as written?**

- [ ] Every step says when it runs **relative to** `helm upgrade`, whether it can
      be run twice, what state the environment is in if it fails, and which
      rights it needs.
- [ ] The migration scripts are one block: preview, migrate, check gate. A
      table says what each script changes and when it needs a person.

## The required layout, shown on 4.9.5 → 4.10.0

**The known-good form is the 4.9.5 → 4.10.0 set as reworked in**
**[PR #658](https://github.com/Dimpact-Samenwerking/helm-charts/pull/658).**
**Copy its shape; the links below point at each part.**

### The upgrade guide

[`4.9.5-to-4.10.0-upgrade.md`](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md)
has three parts, named in its first lines: the runbook, the record of what
moved, the reference.

| Part | What it is, and why it is there |
| --- | --- |
| Opening | Which version it starts from, the three-part outline, links to the companions. The operator knows in ten lines what to read and what to keep open. |
| [Checklist](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#checklist) | Six boxes, A to F, each a link and a half-line. "A and B are done once; C, D and E per environment." The whole hop on one screen. |
| [A. Once per cluster](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#a-once-per-cluster-crds) | CRDs: cluster-admin work outside the pipeline. Each item is an apply command with `--context`, a check command with the exact expected output, and what to do when it differs. |
| [B. Once per values repository](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#b-once-per-values-repository-migrate-the-values-files) | File changes, not cluster changes. B1: the scripts in one block (preview, migrate, check gate) and a table of what each changes and when it needs a person. B2: the hand edits as a table of edit, environments, link to the YAML in the deltas doc. B3: render before the deploy day, with a "render fails while / fix" table, one row per guard the chart has. |
| [C. Per environment, before the deploy day](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#c-per-environment-before-the-deploy-day) | Ordered by time: days before, the day before, directly before. Sets `CTX` and `NS` once. Preparations, images, Key Vault, backups, checks, who to tell outside the pipeline, and what the window costs (what restarts, what is lost, how long). |
| [D. The deploy run](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#d-the-deploy-run) | The pipeline, step by step. Each step: when relative to `helm upgrade`, the command, the expected output, whether it can run twice, what state a failure leaves. Ends with [If the run fails](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#if-the-run-fails): the log line verbatim, the step that fixes it. |
| [E. After the deploy](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#e-after-the-deploy) | Smoke tests tied to what changed, follow-ups that could not run earlier, cleanup with the check that something is a leftover. |
| [F. Rollback](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#f-rollback) | Per component with a one-way change: how to tell the failure apart first, the way back, what may stay. |
| [Changes that need no action](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#changes-that-need-no-action) | One line each. Anything that needs a command, an edit or a decision is not here but in A to F. |
| [Component versions](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#component-versions-4100-vs-495) and [Changes](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#changes) | The record of what moved. Generated by the release tooling; hand-written notes under a component link a step, they do not repeat it. |
| Reference, from [Objecten 4](_UPGRADE_PATHS/4.9.5-to-4.10.0-upgrade.md#reference-objecten-4-open-object) on | One section per topic a step links to. The detail for when a step fails or a choice has to be made. No test logs, dated counts or reasoning: those are in the commit message. |

### The values deltas document

[`4.9.5-to-4.10.0-values-deltas.md`](_UPGRADE_PATHS/4.9.5-to-4.10.0-values-deltas.md)
is config only. The operator keeps it open next to the values file.

| Part | What it is, and why it is there |
| --- | --- |
| Opening | "What changes in `podiumd.yml`, `services-gateway.yml` and `ssl-gateway.yml` for this hop, and nothing else", a link to the guide for everything else, and the census commits of the values repositories the keys were counted over. |
| Scripts block, still in the opening | The migration commands, one line each, before the first component heading. Not a `##` section of its own: `fix-doc-consistency` sorts those after the components. |
| One `## <component> old → new` section per component | The heading is generated by the tooling; link to it by file and section name, not by anchor. One lead sentence says which environments and names the script when a script makes the change. Then the YAML, annotated in place: `# new`, `# was …`, `# remove`, `# remove the whole block`. Only keys the environments actually set. No prose beyond that sentence. |
| [`ssl-gateway.yml`](_UPGRADE_PATHS/4.9.5-to-4.10.0-values-deltas.md#ssl-gatewayyml) | The gateway files get their own section in the same form. |

## Other docs

| File | Purpose |
| --- | --- |
| `<from>-to-<to>-upgrade.md` | The runbook (what to run, where, in which order, what to check), the record of what moved in the chart, and the reference behind each step. Owns all prose of the hop. |
| `<from>-to-<to>-values-deltas.md` | Config only: what changes in a gemeente `podiumd.yml`, `services-gateway.yml` and `ssl-gateway.yml`, as annotated YAML per component, limited to keys the environments actually set. Kept open next to the values file while editing. |
| `<from>-to-<to>-gemeente-specific.md` | Findings that hold for one gemeente or environment only. |
| `<from>-to-<to>-operators-crds.md` | Only when an operator or CRDs change: what changed, the impact on existing resources, the cluster-scoped commands that run before `helm upgrade`. |
| `images/images-<to>.yaml` | The image set SSC Hosting mirrors for the hop. Generated. |
| `apps/<app>/*.md` | A one-time or high-risk procedure too large for the guide, linked from the step that needs it. |

The folder layout and the steps for a new release are in
[`_README.MD`](_README.MD); which guide an operator reads is in
[`_UPGRADING.md`](_UPGRADING.md).
