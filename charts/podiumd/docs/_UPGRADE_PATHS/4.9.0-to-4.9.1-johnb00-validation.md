# PodiumD 4.9.1 — live validation on johnb00

First real-cluster deployment of the 4.9.1 line's opt-in components, run
against the `johnb00` test environment on `feature/IN-2658-frankgateway-4.9.1`
(chart-source-ref — confirmed a strict superset of `feature/podiumd-4.9.1` at
the time of this run: ahead by exactly the frankgateway commits, behind by
none). This document records what was validated, what broke on first contact,
and what was fixed — all fixes landed in the deploy repo
(`podiumd-infra`, `feature/johnb00-podiumd-4.9.0`), not in this chart, except
where noted.

## What was enabled

First-ever enablement of **openbao** and **Frank!Gateway** on any podiumd
environment (zaakbrug had precedent on jimme00/test00; openinwoner had
precedent on several jim0x environments but was newly turned on for johnb00
in this pass):

- **openbao** — initialized, unsealed (3/3 pods, Shamir), Keycloak OIDC wired
  (`uploader` policy + `vault-uploaders` group via the config Job), root
  token minted then revoked after the scoped config token was confirmed
  working.
- **Frank!Gateway** — `outway` instance only (2 replicas + 3-member etcd);
  johnb00 runs Traefik, not NGINX Gateway Fabric, so `inway` has nothing to
  front. No routes seeded (BAG/KVK need their API keys in OpenBao first,
  which needs OpenBao unsealed first — done, keys not yet seeded).
- **zaakbrug** — authenticating to OpenZaak via the existing `"zaak"`
  Applicatie rather than a newly-minted credential.
- **openinwoner** (Portaal) — config already existed on johnb00 (disabled);
  this pass turned it on and fixed everything that broke on first real
  deploy (below).

## Deploy-pipeline / values fixes (all in podiumd-infra)

None of these are chart bugs in the sense of "the chart renders something
wrong" — the chart's own values.yaml documents the correct shape in every
case below (comments, examples). They're gaps in an environment's values
file or the shared deploy script that only surface the first time a given
code path is actually exercised.

1. **`mini-helm-deploy.sh` never wired `OPENBAO_DB_PASSWORD` into a
   `--set-string`**, despite fetching it generically alongside every other
   app's DB password. The `openbao-db-schema` pre-upgrade hook Job ran with
   an empty `PGPASSWORD`, failing with `fe_sendauth: no password supplied`
   even though the Key Vault secret and Postgres role were correct
   (confirmed independently via a live `SELECT` from inside the cluster).
   Root-caused via the live pod's env, not guessed.
2. **Keycloak Operator CRD bootstrap only fetched the original two CRDs**
   (`keycloaks`, `keycloakrealmimports`). adfinis chart 1.13.0 (part of this
   release's operator bump) ships two more —
   `keycloakoidcclients.k8s.keycloak.org` and
   `keycloaksamlclients.k8s.keycloak.org` — whose controllers the operator
   starts unconditionally. Without them the operator pod crash-loops on
   `Not Found` for those API groups. This exact gap is already documented in
   [`4.9.0-to-4.9.1-operators-crds.md`](4.9.0-to-4.9.1-operators-crds.md);
   this run is the live confirmation that the documented risk is real
   (`treat as a hard prerequisite rather than a maybe` — it is one).
3. **Image-prepull DaemonSet crash-looped on the etcd image**
   (`quay.io/coreos/etcd`, added to the prepull list by enabling
   frankgateway) — it ships no shell, so the default `sh -c "exit 0"`
   prepull probe fails with `exec: sh: executable file not found`. Same
   class of issue the script already had a table for (opa,
   zookeeper-operator, redis-exporter, redis-operator); etcd just hadn't
   been hit yet.
4. **openinwoner's `eck-elasticsearch.nodeSets` override was incomplete.**
   The chart ships no default nodeSets for this block by design (each
   environment supplies its own — see the chart's own commented example),
   and a values override *replaces* the array rather than merging into it.
   johnb00's existing override only carried a `podTemplate` tweak and
   `volumeClaimTemplates`, so it silently had no `count` and no
   `node.roles` — ECK's admission webhook rejected it outright ("needs to
   have at least one master node") the first time this was actually
   deployed. This is a real trap in the current chart design (a partial
   override renders invalid, not "default plus your override") — worth a
   `helm-docs`-visible warning on that key, not just a comment.
5. **openinwoner's `oidc_db_config_admin_auth` predated the
   providers/items schema split.** It only had the flat single-level shape
   (`items` containing `endpoint_config`/`oidc_rp_client_id`/... directly,
   no `providers` list, no `oidc_provider_identifier`) that
   `mozilla_django_oidc_db`'s setup-configuration step no longer accepts —
   `oidc_provider_identifier` is now a pattern-validated field, defaulting
   to `""` and failing validation. Restructured to the providers/items
   split already working for objecten/objecttypen/openzaak on this same
   environment. Never caught because openinwoner was never actually
   deployed on johnb00 before this pass.
6. **Azure Files (SMB) PVs need `uid=`/`gid=`/`file_mode=`/`dir_mode=`
   mount options for `chmod()` to work at all.** Without them, Azure Files
   reports every file as root-owned with a fixed 0777 (the share has no
   real POSIX ACLs), and a non-root container's `chmod()` fails with
   `EPERM` regardless of the target mode, since the kernel's ownership
   check runs locally against that fabricated root ownership. This is
   invisible for apps that never call `chmod` on their media storage, which
   is every SMB-backed app on this environment *except* open-inwoner: its
   startup probe (`/_healthz/`, hardcoded in the vendored subchart's
   `deployment.yaml`, not overridable via values) runs
   `health_check.Storage`, which saves-then-chmods a test file and crash-
   loops forever without this fix. Confirmed the common uid/gid 1000
   convention across at least open-inwoner and objecten before generalizing
   the mount options in the shared SMB provisioning path.
7. **zaakbrug's `zakenApi.jwt.username` defaulted to `"zaakbrug"`**, which
   isn't a registered OpenZaak client on johnb00 — repointed at the
   existing `"zaak"` Applicatie instead of minting a new credential.
8. **`ita.apiConnections.object.apiKey` and objecten's own TokenAuth entry
   for `identifier: ita`** both still held the literal, never-substituted
   placeholder `REP_OBJECTEN_CREDENTIALS_ITA_TOKEN_REP` — filled in with a
   real, matching value. Surfaced while wiring up podiumd-testautomation's
   seeding (`seed-objecten-ita-keten.sh` registers this token against
   Objecten and needs it to already match what ITA is configured to send).
9. **The openinwoner Keycloak client's `redirectUris`/`webOrigins` pointed
   at `openinwoner.johnb00.pd.test-rig.nl`**, which isn't a real route — the
   actual host (ingress + `configuration.oidcUrl`) is
   `portaal.johnb00.pd.test-rig.nl`. Left as-is, a realm-import reconcile
   would have reverted podiumd-testautomation's own runtime fix for the
   same mismatch.

## Test coverage

**Source:** [`podiumd-testautomation`](https://github.com/ICATT-Menselijk-Digitaal/podiumd-testautomation),
`podiumd-4.9.0/` suite, `smoke` tier (`playwright.tiers.config.ts
--project=smoke`), `PODIUMD_ENV=johnb00`. First time this suite's seeding has
run against johnb00 at all.

Seeded via `seed-omgeving.sh` (all steps except the OAB ones, which the
orchestrator's own guard skips — openarchiefbeheer isn't deployed here):
TEST catalogus/zaaktype/IOT, OK partijen, Keycloak realm roles + test users,
DigiD-OIDC mock, eHerkenning-OIDC mock, Open Notificaties publishers +
kanalen, ITA medewerker-actor, Open Formulieren test form + OZ registration,
Objecten/Objecttypen ITA chain, and — once openinwoner was enabled — its ZGW
wiring, CMS pages, OpenKlant2 config, and contactflow.

Final stable result: **34 passed, 13 skipped, 3 failed** (repeated 4 times to
separate real failures from cluster noise):

- The 2 consistent failures are `tests/smoke/72-ita-health-kanalen.spec.ts`
  — ITA (`internetaakafhandeling`) is `enabled: false` on johnb00 and out of
  scope for this pass; not a regression.
- The 1 remaining failure moved between runs (Open Zaak, Portaal, Open
  Klant 2, and Open Formulieren admin pings each failed at least once, never
  the same one twice, all with 5–20s timeouts) — consistent with transient
  load/contention on a 3-node test cluster now running noticeably more
  workloads, not a real defect. `tests/README.md` in podiumd-infra
  documents this exact class of flake independently
  (`kubectl exec ... connection reset by peer` is called out as a known
  transient AKS API-server flake).

Everything else passes consistently across runs: OpenZaak ZGW JWT auth +
TEST-catalogus reachability, Keycloak SSO across components, KISS/KCC login
flow + BFF + SPA routes, DigiD and eHerkenning OIDC login through Portaal,
CMS/apphook pages, continuity pings, PABC/OMC health.

**Not covered by this or any other existing suite:** openbao, Frank!Gateway,
and zaakbrug have no dedicated specs anywhere (the suite predates all three).
Their verification for this pass was manual/functional: `bao` CLI checks for
seal state and OIDC/policy wiring, zaakbrug's live authentication against
OpenZaak, and Frank!Gateway's outway pods + etcd quorum (no routes seeded
yet, so no request-path check was possible).
