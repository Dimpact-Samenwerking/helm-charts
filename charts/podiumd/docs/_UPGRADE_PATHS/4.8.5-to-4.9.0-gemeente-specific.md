# Gemeente-specific notes — PodiumD 4.8.5 → 4.9.0

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## Open Inwoner — ClamAV virus scan (opt-in, any gemeente)

Open Inwoner Platform gained ClamAV virus scanning of file uploads in
[maykinmedia/open-inwoner#2415](https://github.com/maykinmedia/open-inwoner/pull/2415)
(first shipped in `v2.3.0`, 2026-06-11 — already included in the `2.4.3` app
version this chart currently pins). It's off by default
(`SiteConfiguration.enable_virus_scan = False`) and is a `SingletonModel` row
per environment, so it's a per-gemeente opt-in, not a chart default.

### Enabling it

The relevant fields are exposed through Open Inwoner's existing
`site_config_enable` / `site_config:` setup-configuration step (see the
commented example under `openinwoner.configuration.data` in
`charts/podiumd/values.yaml`):

```yaml
enable_virus_scan: true
clamav_host: clamav.podiumd.svc.cluster.local
clamav_port: 3310
clamav_timeout: 30.0
```

`clamav_host`/`clamav_port` point at the shared in-cluster ClamAV service
every environment already runs (`docs/apps/clamav/clamav-BASICS.md`) — the
fully-qualified name works from any namespace, so this doesn't need to vary
per gemeente. `clamav_port` (`3310`) and `clamav_timeout` (`30.0`) already
match the field defaults; they're listed explicitly here so the block is
self-documenting rather than relying on defaults a reader can't see.

### ⚠️ Must be merged into the gemeente's existing `site_config:` block

**Do not deploy the four lines above as a standalone `configuration.data`
block.** Per the upstream `SiteConfigurationStep` docstring:

> Every field this step manages is overwritten on every run, using its
> default when the YAML source doesn't set it: changes made to them in the
> admin do not survive a re-run. `name` has no sensible default and must
> always be provided.

The step manages roughly 70 `SiteConfiguration` fields — site name, primary/
secondary/accent colors, warning banner text, login/home page copy, help
texts, GTM/GA/Matomo codes, cookie banner text, and more (full list in
[`open_inwoner/configurations/bootstrap/siteconfig.py`](https://github.com/maykinmedia/open-inwoner/blob/main/src/open_inwoner/configurations/bootstrap/siteconfig.py)
upstream). If a gemeente enables `site_config_enable: true` with only the
ClamAV keys present, either the run fails validation (`name` is required
with no default) or — if that's worked around — every other field silently
resets to its schema default on the next deploy, wiping out that gemeente's
actual branding and copy.

**To enable ClamAV for a gemeente:** add the four keys above to that
gemeente's own, already-complete `site_config:` block in their `podiumd.yml`
(the one that already sets `name` and their branding). If a gemeente has no
existing `site_config:` block, populate the full set of fields they currently
rely on the admin UI for before enabling this — don't activate the step with
a partial block.

## Open Forms — ClamAV virus scan (opt-in, any gemeente)

Unlike Open Inwoner, Open Forms has **no** declarative setup-configuration
step for its ClamAV `GlobalConfiguration` fields — upstream only exposes them
through the admin UI (`docs/configuration/general/virus_scan.rst`: Configuratie
→ Algemene configuratie → Virus scan). So this hop adds a dedicated Job,
`openformulieren.clamavConfigJob` (see
`templates/openformulieren-configure-clamav.yaml`), that seeds the same four
fields via `manage.py shell`, verifying the ClamAV connection first exactly
like the admin form does (`GlobalConfiguration.clean()` upstream). Unlike the
Open Inwoner `site_config:` step, this one only ever touches those four
fields — no risk to unrelated settings, and it's safe to enable standalone.

**To enable it for a gemeente**, set in their `podiumd.yml`:

```yaml
openformulieren:
  clamavConfigJob:
    enabled: true
```

`clamavHost`/`clamavPort`/`clamavTimeout` default to the shared in-cluster
ClamAV service (`clamav.podiumd.svc.cluster.local:3310`, 30s timeout) and
don't need overriding per gemeente. The Job retries on its own
(`backoffLimit: 15`, `activeDeadlineSeconds: 1200`) if it races ClamAV's
cold-start or the openformulieren DB migration on a fresh deploy — no manual
intervention needed, just check `kubectl get jobs -n podiumd
openformulieren-configure-clamav` if it doesn't seem to have applied.
