# Gemeente-specific notes — PodiumD 4.8.5 → 4.9.0

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## Open Inwoner — ClamAV virus scan (opt-in, any gemeente)

Open Inwoner Platform gained ClamAV virus scanning of file uploads in
[maykinmedia/open-inwoner#2415](https://github.com/maykinmedia/open-inwoner/pull/2415)
(first shipped in `v2.3.0`, 2026-06-11 — already included in the `2.4.3` app
version this chart currently pins). It's off by default
(`SiteConfiguration.enable_virus_scan = False`) and is a `SingletonModel` row
per environment, so it's a per-gemeente opt-in, not a chart default.

The four fields (`enable_virus_scan`, `clamav_host`, `clamav_port`,
`clamav_timeout`) live on the same `SiteConfiguration` singleton as the
`site_config_enable` / `site_config:` setup-configuration step, but that
step does **not** manage them: upstream's `SiteConfigurationStep`
([`open_inwoner/configurations/bootstrap/siteconfig.py`](https://github.com/maykinmedia/open-inwoner/blob/main/src/open_inwoner/configurations/bootstrap/siteconfig.py))
only reads settings from a fixed `required_settings`/`optional_settings`
list, and the ClamAV fields are absent from both — so putting them under
`site_config:` in `configuration.data` is silently ignored, whether or not
they're merged into an existing block. (An earlier version of this guide
recommended exactly that; it doesn't work and has been corrected here.)

Same situation as Open Forms below, and the same fix: a dedicated Job,
`openinwoner.clamavConfigJob` (see
`templates/openinwoner-configure-clamav.yaml`), seeds the four fields via
`manage.py shell` instead. Unlike the `site_config:` step it only ever
touches those four fields — no risk to a gemeente's other `SiteConfiguration`
settings (branding, copy, banners, etc.) — and it pings clamd itself before
writing, since `SiteConfiguration.clean()` only checks that `clamav_host` is
non-empty and doesn't test connectivity the way Open Forms' does.

**To enable it for a gemeente**, set in their `podiumd.yml`:

```yaml
openinwoner:
  clamavConfigJob:
    enabled: true
```

`clamavHost`/`clamavPort`/`clamavTimeout` default to the shared in-cluster
ClamAV service (`clamav.podiumd.svc.cluster.local:3310`, 30s timeout) and
don't need overriding per gemeente. The Job retries on its own
(`backoffLimit: 15`, `activeDeadlineSeconds: 1200`) if it races ClamAV's
cold-start or the openinwoner DB migration on a fresh deploy — no manual
intervention needed, just check `kubectl get jobs -n podiumd
openinwoner-configure-clamav` if it doesn't seem to have applied.

## Open Forms — ClamAV virus scan (opt-in, any gemeente)

Open Forms has **no** declarative setup-configuration step for its ClamAV
`GlobalConfiguration` fields at all — upstream only exposes them through the
admin UI (`docs/configuration/general/virus_scan.rst`: Configuratie →
Algemene configuratie → Virus scan). So this hop adds a dedicated Job,
`openformulieren.clamavConfigJob` (see
`templates/openformulieren-configure-clamav.yaml`), that seeds the same four
fields via `manage.py shell`, verifying the ClamAV connection first exactly
like the admin form does (`GlobalConfiguration.clean()` upstream) — the same
approach as the Open Inwoner Job above. It only ever touches those four
fields — no risk to unrelated settings, and it's safe to enable standalone.

**To enable it for a gemeente**, set in their `podiumd.yml`:

```yaml
openformulieren:
  clamavConfigJob:
    enabled: true
```

`clamavHost`/`clamavPort`/`clamavTimeout` default to the shared in-cluster
ClamAV service (`clamav.podiumd.svc.cluster.local:3310`, 30s timeout) and
don't need overriding per gemeente. The Job retries on its own
(`backoffLimit: 15`, `activeDeadlineSeconds: 1200`) if it races ClamAV's
cold-start or the openformulieren DB migration on a fresh deploy — no manual
intervention needed, just check `kubectl get jobs -n podiumd
openformulieren-configure-clamav` if it doesn't seem to have applied.

## Image repository overrides — required per gemeente, not chart-level

This hop reverted `pabc.image.repository` / `pabc.migrations.image.repository`
/ `pabc.initContainers.waitFor.image.repository` to the public upstream
(`ghcr.io/platform-autorisatie-beheer-component/...`) — it was previously
hardcoded to `acrprodmgmt.azurecr.io/...` directly in the chart default,
which is the wrong layer: ACR mirroring is an environment concern, not
something the chart should assume for every deployment.

**Any gemeente behind AKS Gatekeeper (which only allows
`acrprodmgmt.azurecr.io/*`) must set these three PABC fields explicitly in
their own `podiumd.yml`.** PABC is not unique here — the chart has ~14
`image.repository` fields across other components (ZAC and everything it
bundles — office_converter/opa/solr-operator/solr/zookeeper*, KISS and its
sync-job/adapter images, ITA, openarchiefbeheer, omc) that are commented out
in `values.yaml` and rely entirely on the subchart's own upstream default
unless a gemeente overrides them too. Find the current list with:

```bash
grep -n "^\s*#\s*repository:" charts/podiumd/values.yaml
```

**Naming convention: the full namespace-preserving path**, i.e. the upstream
`<namespace>/<repo>` kept intact under the ACR host — e.g.
`acrprodmgmt.azurecr.io/openpolicyagent/opa`, not a flattened
`acrprodmgmt.azurecr.io/opa`. This matches the strip-registry convention
already documented in `docs/images/images-baseline.yaml`'s header comment
(`name = strip_registry(url)`).
