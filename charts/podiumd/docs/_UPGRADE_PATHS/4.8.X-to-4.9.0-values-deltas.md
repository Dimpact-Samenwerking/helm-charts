# Values deltas — PodiumD 4.8.X → 4.9.0 (DRAFT — exact source patch version not yet assigned)

> **Status: scaffold**, companion to
> [4.8.X-to-4.9.0-upgrade.md](4.8.X-to-4.9.0-upgrade.md). Drafted against
> the reviewable patch set under `patches/` at the repo root, which has since
> been applied to `charts/podiumd/`'s working tree (unstaged, not yet
> committed) — see `docs/apps/objecten/openobject-migration.md` for the full
> research and design-decision record this is based on. `4.8.X` here is a
> literal placeholder for whichever 4.8.x patch release the environment is
> running before this merge lands. This file lists every value override a
> gemeente `podiumd.yml` may need to add, change, or remove for the
> `objecten`/`objecttypen` merge; component/application-level detail lives
> in the upgrade guide.

## TL;DR

The **#** column refers to the numbered section below with full details.

| # | Component | Required action | Type |

| 1 | `objecten.image.repository` / `.tag` | If overridden, repoint to `maykinmedia/open-object` / `4.1.0`+digest | **Required** if overridden |
| 2 | `kiss.adapter.objecten.*` + `kiss.adapter.objecttypen.*` | Merge into one `kiss.adapter.objecten.*` block (union of fields) | **Required** if either is overridden |

| 6 | `openbeheer.configuration.data` → `zgw_consumers.services[].api_root` (objecttypen-service entry) + `api_configuration.objecttypen_service_identifier` | Repoint to the merged host; token must still match the new merged tokenauth item | **Required** if overridden |

## Required changes

### 1. `objecten` / `objecttypen` — chart-level merge

The `objecttypen` chart dependency is removed entirely; `objecten` now covers
both. Full key-mapping table: `docs/apps/objecten/openobject-migration.md` section C.

**Before (4.8.X, if a gemeente overrode any of this):**

```yaml
objecttypen:
  configuration:
    token: "<admin-token>"
    oidcUrl: https://<env>-objecttypen.dimpact.nl
  settings:
    allowedHosts: <env>-objecttypen.dimpact.nl
  image:
    repository: maykinmedia/objecttypes-api
    tag: "3.4.2@sha256:..."
```

**After (4.9.0):**

```yaml
# objecttypen: block removed entirely.
objecten:
  configuration:
    # Admin token moves to a tokenauth item with is_superuser: true (H.5) —
    # see docs/apps/objecten/openobject-migration.md section C / values.yaml comments.
    secrets:
      create_required_objecttypen_token: "<admin-token>"
  settings:
    # NEW, required — chart render fails without it (H.2: keep the existing
    # objecten hostname, not objecttypen's).
    siteDomain: <env>-objecten.dimpact.nl
  image:
    repository: maykinmedia/open-object
    tag: "4.1.0@sha256:7738cb8161d221d0a286d39d9d270c35024ff78123c296ceb46f3d9dda7208f9"
```

**Removed (no longer valid, upstream 4.0.0):**
- `objecttypen.configuration.token` (plain admin bearer token) — replaced by
  a `tokenauth` item, see above.
- `objecttypes.items[].service_identifier` in `objecten.configuration.data`
  — objecttypes are local now, no service reference possible.
- `tokenauth.items[].{fields,use_fields}` in `configuration.data`.
- `sites_config`/`sites_config_enable` in `configuration.data` — replaced by
  `settings.siteDomain`.

**Added:**
- `objecten.settings.siteDomain` (required).
- `objecten.settings.otel.*` (moved from a top-level, previously-inert
  `objecten.otel.*` key — fix this if a gemeente values file still sets the
  old top-level path expecting it to do something).

If a gemeente file does **not** override any `objecttypen.*` key and does
not override `objecten.image.*`, no action is needed — the chart defaults
already carry the merge.

### 2. KISS adapter — value-key collapse (H.7)

`kiss.adapter.objecten.*` and `kiss.adapter.objecttypen.*` collapse into one
`kiss.adapter.objecten.*` block. **Not** `kiss.adapter.openobject` — the
merge keeps the `objecten` name everywhere.

**Before:**

```yaml
kiss:
  adapter:
    objecten:
      baseUrl: "http://objecten.podiumd.svc.cluster.local"
      token: "<smoelenboek-token>"
    objecttypen:
      baseUrlIntern: "http://objecttypen.podiumd.svc.cluster.local"
      baseUrlExtern: "https://<env>-objecttypen.dimpact.nl"
      token: "<unused>"
      medewerkerUUID: "..."
      afdelingUUID: "..."
      groepUUID: "..."
      interneTaakUUID: "..."
      kennisartikelUUID: "..."
      vacUUID: "..."
```

**After:**

```yaml
kiss:
  adapter:
    objecten:
      baseUrl: "http://objecten.podiumd.svc.cluster.local"
      token: "<smoelenboek-token>"
      baseUrlIntern: "http://objecten.podiumd.svc.cluster.local"
      baseUrlExtern: "https://<env>-objecten.dimpact.nl"
      medewerkerUUID: "..."
      afdelingUUID: "..."
      groepUUID: "..."
      interneTaakUUID: "..."
      kennisartikelUUID: "..."
      vacUUID: "..."
```

`baseUrl`/`token` come from the old `objecten.*` fields (the ones the
adapter actually reads for `SMOELENBOEK_*`); everything else carries over
unchanged from the old `objecttypen.*` fields, just under the merged key.
`afdelingUUID`/`groepUUID`/`kennisartikelUUID`/`vacUUID` aren't read by any
template today (pre-existing, unrelated to this merge) — carry them over
anyway in case that changes.

### 3. ZAC — objectenApi / objecttypenApi

**Before:**

```yaml
zac:
  objectenApi:
    url: http://<env>-objecten.dimpact.nl
    token: "<objecten-token>"
  objecttypenApi:
    url: http://<env>-objecttypen.dimpact.nl
    token: "<objecttypen-token>"
```

**After:**

```yaml
zac:
  objectenApi:
    url: http://<env>-objecten.dimpact.nl
    token: "<merged-token>"
  objecttypenApi:
    url: http://<env>-objecten.dimpact.nl
    token: "<merged-token>"
```

ZAC's own chart schema still requires both keys — only the *values* collapse
to the same host/token, not the key structure.

### 4. ITA — objecttype URLs

All four `ita.*.type` fields use a `-objecttypen` hostname segment today;
repoint to the surviving `-objecten` hostname (UUIDs are unaffected — Open
Object 4.0 resolves objecttype URLs by UUID only, domain is ignored, so
existing data keeps resolving either way, but new/edited gemeente values
should use the current hostname going forward).

```yaml
ita:
  logboek:
    type: "https://<env>-objecten.dimpact.nl/api/v2/objecttypes/<uuid>"
  afdeling:
    type: "https://<env>-objecten.dimpact.nl/api/v2/objecttypes/<uuid>"
  groep:
    type: "https://<env>-objecten.dimpact.nl/api/v2/objecttypes/<uuid>"
  medewerker:
    type: "https://<env>-objecten.dimpact.nl/api/v2/objecttypes/<uuid>"
```

### 5. Open Formulieren — zgw_consumers service host

If a gemeente's `openformulieren.configuration.data` sets an explicit
`api_root` for the `objecttypen-api` service identifier, repoint it to the
merged host (the `objecten-api` identifier's `api_root` should already match
— both must now point at the same host). Open Formulieren's own schema still
expects two distinct service identifiers even though there's only one app
behind them now — don't collapse the identifiers, just their target host.

### 6. Open Beheer — zgw_consumers service host + token

Same pattern as Open Formulieren: repoint the `objecttypen-service`
identifier's `api_root` to the merged host. The `IN-2345` token-matching
constraint still applies — the `openbeheer_openbeheer_token`-style secret
must still equal the `Token <...>` value the merged `objecten` tokenauth
item for openbeheer expects; the identifier and secret name are unchanged,
only the target host moves.

### 7. MI exports — targets list

If a gemeente's `mi.targets[]` override still lists a `- component:
objecttypen` entry (customized from the chart default), remove it — the
existing `- component: objecten` entry now covers both exports. Leaving a
stale `objecttypen` entry renders no CronJob (since `objecttypen.enabled`
no longer resolves to anything), but clean it up to avoid confusion.

### 8. Observability overlay — objecttypen OTEL block

If any gemeente-specific observability overlay sets
`objecttypen.settings.otel.*`, remove it — the base
`values-enable-observability.yaml` no longer has a separate `objecttypen:`
block; `objecten.settings.otel.*` covers both.

## Optional / informational

### 9. Media path and Redis DB index

- `objecten.persistence.mediaMountSubpath` — the `openobject` chart's own
  default changed to `openobject/media` (was `objecten/media` under the old
  `objecten` chart). The base `values.yaml` already overrides this back to
  `objecten/media`, so **no gemeente action is needed** unless a gemeente
  values file overrides `objecten.persistence.*` wholesale (in which case,
  carry the subpath override forward explicitly).
- Redis DB index (H.3) — objecten keeps its existing DB 1 (cache) / DB 2
  (celery); objecttypen's old DB 0 is freed. No gemeente action — this was
  never a per-gemeente override in practice.

## Pre-deploy checklist

1. **Precondition per environment** (see the upgrade guide) —
   `import_objecttypes`/`check_for_external_objecttypes` must be clean
   *before* this release is deployed there. This is independent of the
   values changes above but gates whether the deploy will even start.
2. Audit the gemeente `podiumd.yml` for every key in the TL;DR table above —
   most gemeente files only touch `kiss.adapter.*`, `zac.objectenApi`/
   `.objecttypenApi`, and `ita.*.type` in practice (sections 2–4); the
   objecttypen chart-level block (section 1) and the openformulieren/
   openbeheer/mi/observability items (sections 5–8) are less commonly
   overridden but should still be checked.
3. ACR mirror: `maykinmedia/open-object` must be mirrored before deploy
   (new image, replaces both `objects-api` and `objecttypes-api`).
4. Confirm `objecten.settings.siteDomain` is set to the environment's actual
   public hostname — the chart fails to render without it.
5. After deploy: Celery smoke test (Open Object 4.0 fixes a bug where
   `CELERY_BROKER_URL` was actually wired to `CELERY_RESULT_BACKEND` — values
   look unchanged but runtime behavior changes).
