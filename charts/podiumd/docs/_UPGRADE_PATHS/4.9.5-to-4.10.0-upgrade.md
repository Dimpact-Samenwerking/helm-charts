# Upgrade guide: PodiumD 4.9.5 → 4.10.0

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

This is the upgrade guide for environments already on **4.9.5**.

Upstream defects that 4.10.0 still ships, with their status and workarounds:
[`misc/upstream-known-issues.md`](../misc/upstream-known-issues.md).

## Before you deploy (every environment)

- **SSC, blocker: check that Open Zaak's objecten token is unique in every
  environment's Key Vault.** The Objecten 4 migration adds an objecten
  `tokenauth` item `openzaak` with the secret behind
  `REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` (Key Vault secret
  `objecten-credentials-objecttypen-token`, Open Zaak's existing token). Open
  Object refuses two tokenauth items with the same token, so when that value
  equals another objecten token the objecten config job fails and the deploy
  does not complete. The migration script can't see secret values and cannot
  detect this; it only prints a reminder. On two of the eight ExternalsPodiumD
  environments the value equals the `esuite` token, so expect the same in SSC
  environments.

  Per environment, before the deploy, compare the hashes (values are never
  printed):

  ```bash
  KV=kv-<environment>-<gemeente>
  for s in objecten-credentials-objecttypen-token \
           objecten-credentials-formulier-token objecten-credentials-zaak-token \
           objecten-credentials-esuite-token objecten-credentials-contact-token \
           objecten-credentials-contact-esuite-token objecten-credentials-ita-token \
           objecten-credentials-omc-token objecten-credentials-integratieteam-token \
           objecten-credentials-openarchiefbeheer-token objecten-openbeheer-token; do
    h=$(az keyvault secret show --vault-name "$KV" --name "$s" --query value -o tsv 2>/dev/null \
        | tr -d '\n' | shasum -a 256 | cut -c1-12)
    echo "$h $s"
  done | sort
  ```

  - Two lines with the same hash, one of them
    `objecten-credentials-objecttypen-token`: change Open Zaak's side only,
    before the deploy. Never change the other token of the pair (often
    `objecten-credentials-esuite-token`): its clients keep using it, and they
    are usually outside our reach (the eSuite, for example). Both ends of
    Open Zaak's token are in the PodiumD values, so changing it needs no
    client outside to change. Either:
    - give `objecten-credentials-objecttypen-token` a new random value (for
      example `openssl rand -hex 20`; needs write access to the Key Vault).
      After the migration only Open Zaak sends it, and the deploy writes the
      new value to both Open Zaak and the `openzaak` item; or
    - give Open Zaak its own Key Vault item with a new random value, and use
      its placeholder in both places: the `header_value` of Open Zaak's
      `objecten-api` service and the token of objecten's tokenauth item
      `openzaak`.
  - `e3b0c44298fc` is the hash of an empty value: that secret doesn't exist
    in this Key Vault. Ignore it unless the values use the placeholder.
  - Tokens written in the values instead of Key Vault, and items created by
    hand in the objecten admin, count too.

  Details: [objecten below](#objecten-362--430-chart-2121--120).

- **SSC, blocker: the cluster's Solr CRDs must be from solr-operator 0.9.0 or
  newer.** The zac chart now sets `containerSecurityContext` on its
  SolrCloud, a field the `solrclouds.solr.apache.org` CRD only has from
  0.9.0. With an older CRD, Helm's server-side apply refuses the SolrCloud
  (`.spec.customSolrKubeOptions.podOptions.containerSecurityContext: field
  not declared in schema`) and the upgrade fails half-way: resources applied
  before it, such as Keycloak, are already changed, and a new ZAC pod waits
  for the Solr secret `zac-solr-solrcloud-security-bootstrap`. Helm installs
  CRDs only at the first install, so many clusters still have older Solr
  CRDs. Check once per cluster, before the `helm upgrade`:

  ```bash
  kubectl --context <kube-context> get crd solrclouds.solr.apache.org \
    -o jsonpath='{.metadata.annotations.operator\.solr\.apache\.org/version}'
  ```

  It must print `v0.9.0` or newer. Otherwise (an older version, or no
  annotation) apply the 0.9.1 CRDs with cluster-admin rights, through the
  cluster's change process:

  ```bash
  kubectl --context <kube-context> apply --server-side --force-conflicts \
    -f https://solr.apache.org/operator/downloads/crds/v0.9.1/all.yaml
  ```

  An upgrade that already failed on this: apply the CRDs, then run the
  deploy again. That run can stop on `Deployment/<namespace>/zac` with
  `Progress deadline exceeded`: the ZAC pod from the failed run waited for
  the Secret `zac-solr-solrcloud-security-bootstrap`, which only comes with
  the new SolrCloud spec, and passed its 10-minute deadline meanwhile. Wait
  until the SolrCloud has all pods ready
  (`kubectl -n <namespace> get solrcloud zac-solr`) and ZAC is available,
  then deploy once more.
  Details:
  [solr-operator](4.9.5-to-4.10.0-operators-crds.md#solr-operator).
- **`alpine/k8s`: set the ACR mirror on all three image paths.** Three
  workloads use `docker.io/alpine/k8s` `1.37.1`, pinned by digest:
  `zac.solr-operator.zookeeper-operator.hooks.image`,
  `redis-operator.redis-ha.labelMasterCronJob.image` and
  `redis-operator.redis-ha.preDeleteJob.image`. The hooks used
  `lachlanevenson/k8s-kubectl` `v1.25.4` before, a different image, not a new
  tag of the same one. The values share the YAML anchor
  `global.images.alpineK8s`; no template reads that key, so overriding it in
  an environment changes nothing, and `global.imageRegistry` does not apply
  to these paths. An environment that pulls from its ACR sets
  `repository: <acr>/alpine/k8s` on each path:
  - `hooks.image.repository`: change it from `k8s-kubectl`. Otherwise the hook
    Job pulls tag `1.37.1`, which does not exist there, and the `helm upgrade`
    fails. `scripts/migrate-zookeeper-hooks-image-4.10.0.py` makes that change
    in the gemeente values (same registry, `alpine/k8s`), and the render fails
    while an override still names `k8s-kubectl` with the new tag.
  - `labelMasterCronJob.image.repository`: most environments already have it.
  - `preDeleteJob.image.repository`: add it. No environment sets it, so the
    pre-delete Job (it runs on `helm uninstall`) pulls from Docker Hub; that
    was already so in 4.9.5.

  The ACR must hold `alpine/k8s:1.37.1` by digest. See
  [alpine/k8s image overrides](4.9.5-to-4.10.0-gemeente-specific.md#ssc-and-externalspodiumd-alpinek8s-image-overrides).
- **`helm upgrade` waits for four setup-configuration Jobs.** Open
  Archiefbeheer (chart 2.1.0), Open Notificaties (2.1.0), Open Formulieren
  (1.13.0) and Open Inwoner (2.6.0) run their configuration Job as a
  `post-install,post-upgrade` hook: Helm waits for each Job, and one that fails
  fails the whole release. podiumd keeps `configuration.job.backoffLimit: 6`
  and `restartPolicy: OnFailure` instead of the charts' new `0` and `Never`, so
  a Keycloak or realm import that is not ready yet is retried. A Job that keeps
  failing takes about 7 minutes before it gives up, longer than Helm's default
  `--timeout` of 5m, which applies to each hook Job: run `helm upgrade` with
  `--timeout 10m` or more. `helm uninstall` leaves the hook Jobs; the next
  install or upgrade replaces them (`before-hook-creation`).
- **`zac.auth.pkceEnabled` is replaced by `zac.auth.enablePkce`** (default
  `true`); the render fails while the old key is set. See
  [ZAC: PKCE on by default](#zac-pkce-on-by-default).
- **The render fails when a Django app sets `configuration.pkceEnabled: true`**
  (Open Zaak, Open Notificaties, Objecten, Open Archiefbeheer, Open Klant, Open
  Formulieren, Open Inwoner, Referentielijsten, Open Beheer, Open VTB). These
  apps cannot send PKCE yet (`oidc_use_pkce` in `configuration.data` is not
  read), so PKCE on their Keycloak client only broke the login. Set it to
  `false` or remove it; no SSC environment sets it. See
  [keycloak-security-updates.md](../apps/keycloak/keycloak-security-updates.md#pkce-enforcement).
- **KISS Elastic stack (kiss-eck): check your environment values.** PodiumD
  now renders the KISS `Elasticsearch`, `Kibana` and `EnterpriseSearch`
  resources itself, with a digest-pinned image block per resource.
  - Remove any `kiss-eck.eck-*.version`: the render fails while it is set.
    The version comes from `kiss-eck.eck-*.image.tag`.
  - Environments with an ACR: nothing to change when they set
    `eck-operator.config.containerRegistry` (all SSC environments do). As ECK
    did before, the chart then replaces the `docker.elastic.co` host of the
    KISS Elastic images with that registry, e.g.
    `acrprodmgmt.azurecr.io/elasticsearch/elasticsearch`. The ACR must hold the
    new 8.19.23 images by digest (see `images-4.10.0.yaml`). To use another repository, set
    `kiss-eck.eck-*.image.repository`; that always wins.
  - `kiss-eck.eck-*.image` as a string (e.g. ExternalsPodiumD icat ontw:
    `acrprodmgmt.azurecr.io/elasticsearch/elasticsearch:8.19.19`) fails the
    render: remove it, or move the repository part to `image.repository`.
  - `kiss-eck.eck-*.ingress` and `extraObjects` are no longer supported (the
    render fails); route Kibana through the platform Gateway.
  - `kiss-eck.eck-*.spec.*` and the root-level `kiss-eck.extraObjects` (both
    read by eck-stack) are no longer supported, and the render fails while they
    are set. Move `spec.*` settings one level up to `kiss-eck.eck-*.<key>`. No SSC
    environment sets either.
  See [kiss-eck below](#kiss-eck-81919--81923).
- **SSC: apply the Keycloak Operator 26.8.1 CRDs** before the `helm upgrade`,
  with `charts/podiumd/scripts/install-keycloak-operator-crds.sh --context
  <kube-context> --keycloak-version 26.8.1`. `helm upgrade` never updates CRDs.
  CRDs are cluster-wide: run it once per cluster, with cluster-admin rights,
  through the cluster's change process; every PodiumD namespace on that
  cluster then uses the new CRDs. The changes only add fields, so a namespace
  still on 4.9.x keeps working. See
  [`4.9.5-to-4.10.0-operators-crds.md`](4.9.5-to-4.10.0-operators-crds.md).
- **Allow admin role mapping on the admin identity provider (IN-3203).**
  Keycloak 26.8 refuses an identity provider mapper that grants an admin role
  unless the identity provider has `allowAdminRoleMapping` on. Environments
  whose `keycloak.config.adminIdentityProviderMappers` grant the master role
  `admin` (for example `admin-mapper` on `accp-dimp-oidc`) set it on that
  identity provider:

  ```yaml
  keycloak:
    config:
      adminIdentityProviders:
        identityProviders:
          - alias: "accp-dimp-oidc"
            config:
              allowAdminRoleMapping: "true"
  ```

  Without it the render fails. See [keycloak below](#keycloak-2673--2681).
- **Migrate Open Inwoner's admin OIDC values to the providers schema**, with
  `charts/podiumd/scripts/migrate-openinwoner-admin-oidc.py`. Open Inwoner
  rejects the old flat shape since 2.4.0; at SSCHostingSync `36f44d2`
  (2026-10-27) 4 of the 70 environments with Open Inwoner still have it. In
  4.10.0 its setup-configuration Job is a post-upgrade hook, so the old shape
  fails the whole `helm upgrade`, and the chart refuses to render it. See
  [Open Inwoner: admin OIDC login, the providers schema](#open-inwoner-admin-oidc-login-the-providers-schema)
  below; the migrated block is in the
  [values deltas](4.9.5-to-4.10.0-values-deltas.md#admin-oidc-login-the-providers-schema).
- **ZAC's Solr now requires a login: check scripts and monitoring that call
  it.** The SolrCloud runs with basic auth, and the solr-operator generates the
  `admin` password into the Secret `zac-solr-solrcloud-security-bootstrap`
  (key `admin`). With the operator-managed Solr (the default), ZAC uses it
  without any setting; an external Solr (`zac.solr.url`) needs
  `zac.solr.username` and `zac.solr.password`, or the render fails. Anything
  else that calls the Solr API, such as a deploy script that reloads the `zac` collection, a job
  that creates it, or a health check, gets `401 require authentication` until
  it sends `-u admin:<password>`. The SSC pipelines in ExternalsPodiumD and
  SSCHostingSync don't call the Solr API. See [zac below](#zac-545--591-chart-10297--10355).
- **The create-required Jobs now also run when `openzaak.enabled` or
  `objecten.enabled` is unset.** The chart has no default for either key.
  Before 4.10.0, `create-required-catalogi` and `create-required-objecttypen`
  rendered only when the key was set to `true`; 4.10.0 renders them whenever
  the subchart is deployed (only `false` turns them off, as for the
  dependency). On an environment that leaves the key unset, both Jobs start
  with this upgrade. Before you deploy, set
  `openzaak.create_required_catalogi_job.client_id` and `.secret` (an Open Zaak
  API client with rights on the catalogi) and
  `objecten.configuration.secrets.create_required_objecttypen_token` (the
  token of an objecten tokenauth item with `is_superuser: true`;
  `migrate-objecten-4.1.0.py` sets it), or turn the Jobs off with
  `openzaak.create_required_catalogi_job.enabled: false` and
  `objecten.create_required_objecttypen_job.enabled: false`. The render fails
  while a credential is empty or still a `<...>` default.
- **PostgreSQL must offer TLS.** 4.10.0 sets `sslmode: require` (security review
  NW-09) for Open Zaak, Open Notificaties, Objecten, Open Klant, Open Formulieren,
  Open Inwoner, Open Beheer, Open VTB and OpenBao; their charts defaulted to
  `prefer`. Against a PostgreSQL without TLS these components can no longer
  connect after the upgrade. Azure Database for PostgreSQL offers TLS. For a
  server without it, enable TLS, or set
  `<component>.settings.database.sslmode: prefer` (OpenBao:
  `openbao.database.sslmode`) before you deploy.
- **ZAC: drop `zac.objecttypenApi`.** ZAC reads only `zac.objectenApi` since the
  Objecten/Objecttypen merge, and 4.10.0 removes the unused `zac.objecttypenApi`
  from `values.yaml`. `migrate-objecten-4.1.0.py` removes it from an
  environment's values; a value that is left has no effect.
- **Two pre-existing values issues fail the 4.10.0 render.** Found while
  testing the Objecten migration against SSCHostingSync; these files fail
  with or without the migration, and they are unrelated to it:
  - `zac.brpApi.apiKey` must be a map `{header: <name>, value: <key>}`, not a
    plain string (dim1 accp and gene accp).
  - `kiss.settings.syncJobs.medewerkers`: the kiss chart's schema accepts
    either `useEmail: true` **or** a `baseUrl`/`objectTypeUrl` sync
    configuration. kiss chart 3.2.0 (in 4.10.0) defaults to `useEmail: false`,
    which does not match the `useEmail` branch, so an environment that
    configures the sync job renders without changes (checked on all 68 SSC
    environments that configure it). Only an environment that sets
    `useEmail: true` **and** a sync configuration fails; remove one of the two.

  Environment-specific findings:
  [`4.9.5-to-4.10.0-gemeente-specific.md`](4.9.5-to-4.10.0-gemeente-specific.md).
- **Back up the `openformulieren` database.** Open Forms 4.0 runs one-way
  data migrations; going back to 3.5.x after them is not documented as
  possible. Restore the backup to roll back.
- **Be on PodiumD 4.9.5 (Open Forms 3.5.10) and prepare Open Forms for 4.0
  there.** Open Forms 4.0 refuses to upgrade until every form uses the new
  logic evaluation and the legacy Catalogi URLs are migrated. Do this on
  3.5.10, not earlier: up to 3.5.9 the bulk conversion command has no dry
  run (it converts every form at once, and `--no-dry-run` is an unknown
  argument) and can give logic rules the wrong order. Open Forms 4.0 no
  longer has the command, so this cannot be repaired after the upgrade. See
  the 4.9.5 upgrade guide (`4.9.4-to-4.9.5-upgrade.md`) and
  [`openforms-migration-preparation.md`](../apps/openforms/openforms-migration-preparation.md).
  On 3.5.10:
  1. Forms converted earlier with the bulk command (on PodiumD 4.9.0–4.9.4):
     open each one in the admin and save it once, which restores the rule
     order. The dry run in step 2 cannot list them (it only looks at forms
     not converted yet); the 4.9.5 upgrade guide has a `manage.py shell`
     query that does.
  2. Convert the remaining forms:
     `python /app/src/manage.py enable_new_logic_evaluation_for_all_forms`
     (dry run on 3.5.10: lists the forms it would convert and the problems, changes nothing),
     then the same command with `--no-dry-run`. Forms with cyclic logic rules
     are listed and must be fixed by hand.
  3. Migrate the legacy Catalogi API URLs. `migrate_catalogi_api_urls` stops
     the whole run, and migrates nothing, on the first registration it can't
     validate, and prints only "The registration options are not valid." or
     "No service configured", without the form. So check and clean up first,
     with two scripts from this release: they are in `charts/podiumd/scripts`
     of the 4.10.0 chart, not in the 4.9.5 chart, but run against the
     environment while it is still on 4.9.5 (Open Forms 3.5.10). Run them
     from a helm-charts checkout of 4.10.0; they read from stdin, so
     `kubectl exec` needs `-i`. Do this some days before the 4.10.0 deploy:
     some problems need the form designers.
     1. Check, read-only. It prints one line per problem: `V1_KEYS` (with the
        keys to remove), `NO_SERVICE` (with the URL), `INVALID` (any other
        error), and a `SUMMARY` line:

        ```bash
        kubectl exec -i -n <ns> deploy/openformulieren -c openformulieren -- \
          python /app/src/manage.py shell < charts/podiumd/scripts/openforms-check-registration-options.py
        ```

     2. `V1_KEYS`: Objects API registrations at options version 2 that still
        hold v1-only keys (`content_json`, `productaanvraag_type`). Remove them
        with the cleanup script, or save the registration once in the form
        designer. The script only changes registrations whose every error is
        a v1-only key, all in one transaction, and prints their original
        options as `BACKUP_JSON`: keep that output. Without `APPLY=1` it is a
        dry run that rolls back:

        ```bash
        # Dry run: lists WOULD_FIX and OTHER, changes nothing
        kubectl exec -i -n <ns> deploy/openformulieren -c openformulieren -- \
          python /app/src/manage.py shell < charts/podiumd/scripts/openforms-fix-registration-options.py
        # Apply, keeping the output (BACKUP_JSON)
        kubectl exec -i -n <ns> deploy/openformulieren -c openformulieren -- \
          env APPLY=1 python /app/src/manage.py shell < charts/podiumd/scripts/openforms-fix-registration-options.py \
          | tee openforms-registration-options-<ns>.log
        ```

     3. `NO_SERVICE`: a registration or a file component points at a Catalogi
        without a configured service, for example another environment's URL.
        Correct or clear the reference in the form, or delete the form if it
        is in the trash. `INVALID`: fix the registration in the form designer.
     4. Run the check again until `SUMMARY` reports 0 problems. Then the
        migration itself, dry run first, until it reports no problems:

        ```bash
        kubectl exec -n <ns> deploy/openformulieren -c openformulieren -- \
          python /app/src/manage.py migrate_catalogi_api_urls
        kubectl exec -n <ns> deploy/openformulieren -c openformulieren -- \
          python /app/src/manage.py migrate_catalogi_api_urls --no-dry-run
        ```

     More detail: [`openforms-migration-preparation.md`](../apps/openforms/openforms-migration-preparation.md#4-catalogi-api-direct-url-references-removed-in-40---migration-script).
  4. Run `python /app/bin/report_logic_with_deprecated_clear_on_hide_behavior.py`
     and share the output with the form designers (see "Changes" below).
- **Check how long the Open Forms 4.0 data migration takes.** The file upload
  rework migrates every row of `submissions_submissionfileattachment`;
  upstream plans 0.9–1.2 seconds per 1000 rows. Open Forms runs `migrate` in
  the web container at startup (`bin/docker_start.sh`), and the chart's
  startup probe gives it about 315 seconds (15 s + 30 × 10 s). From about
  260,000 attachments the kubelet restarts the pod in the middle of the
  migration, and it loops. Count them first:

  ```sql
  select count(*) from submissions_submissionfileattachment;
  ```

  If the migration needs longer, raise
  `openformulieren.startupProbe.failureThreshold` for this deploy: allow
  `count / 1000 × 1.2` seconds plus a margin for the other migrations, in
  steps of 10 seconds (e.g. 500,000 rows: 600 s, so `failureThreshold: 75`).

  groups.** Open Forms 4.0 rejects `catalogue_domain`, `catalogue_rsin` and
  `document_type_*` in the `objects_api` and `zgw_api` groups of
  `openformulieren.configuration.data`, and the `openformulieren-config`

  see [Open Formulieren: the catalogue and document type fields of the API groups](#open-formulieren-the-catalogue-and-document-type-fields-of-the-api-groups)
  below.
- **Update custom themes for 4.0** (markup and design tokens changed).
- **Tell SDK embedders.** Embeds that load `/static/sdk/open-forms-sdk.js` or
  `/static/sdk/bundles/open-forms-sdk.js` stop working: they must load the
  `.mjs` file and start the SDK with an ESM `import`; `window.OpenForms` no
  longer exists.
- **Check the identity provider redirect URIs.** Open Forms 4.0 removes the
  `/digid-oidc/`, `/digid-machtigen-oidc/`, `/eherkenning-oidc/`,
  `/eherkenning-bewindvoering-oidc/` and `/org-oidc/` callbacks. Every OIDC
  provider must redirect to `https://<openforms-domain>/auth/oidc/callback/`.
  The podiumd Keycloak `openformulieren` client allows `<oidcUrl>/*`, so it
  needs no change; DigiD/eHerkenning brokers configured outside this chart
  do.
- **Replace every `changeme`/`dummy` credential.** The render now fails when
  any value is exactly `changeme` or `dummy` (any case), and lists every
  offending key. Sections with `enabled: false` are skipped at any depth, so
  a disabled component (`zac.enabled: false`) or part of one
  (`zac.office_converter.enabled: false`) may keep its placeholders. The
  chart defaults that trigger it are all under `zac`: `auth.secret`, `bagApi.apiKey`, `brpApi.apiKey.value`,
  `db.password`, `keycloak.adminClient.secret`, `kvkApi.apiKey`,
  `mail.smtp.username`, `mail.smtp.password`, `notificationsSecretKey`,
  `office_converter.username`, `office_converter.password`,
  `zacInternalEndpointsApiKey` and `zgwApis.secret`. Set each one that is
  not under a disabled section in the gemeente `podiumd.yml`.
  `zac.keycloak.adminClient.secret` matters most: it becomes the Keycloak
  secret of `zac-admin-client`, which can list every realm user.
  The same check rejects the other placeholders the chart ships:
  `openklanttoken` (`zac.klantinteractiesApi.token`), `objectentoken`
  (`zac.objectenApi.token`), `<kiss>`
  (`kiss.configuration.oidcSecret`, `kiss.adapter.esuite.clientId`,
  `kiss.settings.oidc.clientSecret`), `<token>`, and any value that still
  contains a `REP_..._REP` marker, also inside a URL (the `ita.*` defaults:
  `logboek.type`, `afdeling.type`, `groep.type`, `medewerker.type`,
  `apiConnections.*`, `database.host`, `database.password`,
  `web.oidc.authority`, `web.oidc.clientSecret`). The unused
  `ita.afdeling.uuid`, `ita.groep.uuid` and `ita.medewerker.uuid` keys are
  gone; the ITA chart only reads the `type` URLs.
- **Set the Keycloak client secrets that come from values.** The render now
  fails when one of these is empty while its client or component is
  enabled, because an empty value is imported as the client secret:
  `keycloak.config.clients.monitoring.secret`,
  `keycloak.config.clients.datamigratie.secret`,
  `keycloak.config.clients.zaakbrug.secret` (with `zaakbrug.enabled`),
  `kiss.settings.oidc.clientSecret`, `zac.auth.secret`,
  `ita.web.oidc.clientSecret`, `pabc.settings.oidc.clientSecret` and
  `pabc.settings.keycloakAdmin.clientSecret`.
- **Client secrets of disabled components are generated.** The realm import
  always creates the kiss, zac, zac-admin, ita and pabc clients, also when
  the component is disabled. Their secret no longer comes from an empty or
  placeholder value (such as `changeme`): the chart generates a random one,
  keeps it in `keycloak-podiumd-realm-secrets` across upgrades, and the
  realm import Job sets it in Keycloak. The same applies to the
  per-component secrets (`<component>.configuration.secrets.keycloak_client_secret`)
  and to a stored value that is a placeholder. The import Job now runs again
  whenever any client secret changes, so the first upgrade to 4.10.0 runs it
  once. No action needed.
- **Frank!Gateway: https upstreams must present a valid certificate.**
  `frankgateway.upstreamTls.verify` (default `true`) turns on nginx
  `proxy_ssl_verify` with the image's system CA bundle. An upstream with a
  private CA or a self-signed certificate now fails with a 502. Diginetwerk
  endpoints, such as a real BRP, typically use "Staat der Nederlanden Private
  Root CA – G1", which is not in that bundle: set `upstreamTls.verify: false`
  on the instance that calls them (usually `outway`). Before the upgrade,
  check each outway route's upstream host with
  `openssl s_client -connect <host>:443 -servername <host> </dev/null`, run
  from the cluster: `Verify return code: 0 (ok)` means it keeps working. On
  johnb00, KvK (api.kvk.nl) and BAG (api.bag.kadaster.nl) work with verify
  on. No SSC environment enables Frank!Gateway yet.
- **Frank!Gateway: `openbao-consumer-auth` needs NetworkPolicies.** An
  enabled inway route that uses it now fails the render while
  `frankgateway.networkPolicies.enabled` is false.
- **NetworkPolicies stay opt-in** (`networkPolicies.enabled`, default
  `false`). An environment that turns on `networkPolicies.namespaceIsolation`
  also gets peers in the Keycloak CR's `spec.networkPolicy`, so Keycloak's
  operator-made policy no longer opens 8080 and 9000 to the whole cluster.
  Something outside the namespace that calls Keycloak in-cluster rather than
  through the public URL needs an entry in
  `keycloak.networkPolicy.extraFrom` or `namespaceIsolation.extraNamespaces`.
  See [`network-policy-analysis.md`](../misc/network-policy-analysis.md).

- **Prepare the Objecten 4 migration** (objecten and objecttypen merge into
  Open Object): migrate the gemeente `podiumd.yml` with
  `scripts/migrate-objecten-4.1.0.py`, mirror `maykinmedia/open-object`, back
  up the objecten and objecttypen databases, then, directly before the
  `helm upgrade`, run `import_objecttypes` and `migrate-objecttypen-tokens.sh`.
  Switch clients outside the values that must use the objecten token. See
  [Objecten 4: migrating objecten and objecttypen to Open Object](#objecten-4-migrating-objecten-and-objecttypen-to-open-object)
  below, [manual steps per environment](#manual-steps-per-environment) in
  particular.
- **Check that Open Zaak's objecten token is unique.** The migration adds an
  objecten `tokenauth` item `openzaak` with the secret behind
  `REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` (Open Zaak's existing
  token). Open Object refuses two items with the same token, and the objecten
  config job then fails. Before the deploy, compare that secret's value with
  the other objecten tokens of the environment (`formulier`, `zaak`, `esuite`,
  `contact`, `ita`, `omc`, `integratieteam`, `openarchiefbeheer`,
  `openbeheer-token`). If it matches one, give it a new value: only Open Zaak
  sends it after the migration. On two ExternalsPodiumD environments it
  equals the `esuite` token. Hash check per Key Vault: see
  [Before you deploy](#before-you-deploy-every-environment).
- **Delete a leftover `create-required-objecttypen-job`.** 4.10.0 changes its
  pod template (Open Object image, a schemas volume), and Kubernetes refuses
  to change the pod template of an existing Job, so `helm upgrade` fails while
  the old Job exists. A finished Job removes itself after 10 minutes
  (`ttlSecondsAfterFinished: 600`), so it is usually gone already:

  ```bash
  kubectl --context "$CTX" -n "$NS" delete job create-required-objecttypen-job --ignore-not-found
  ```

- **Frank!Gateway runs hardened (environments with `frankgateway.enabled`).**
  Every Frank!Gateway pod now runs as a fixed non-root user with a read-only
  root filesystem, no capabilities, seccomp `RuntimeDefault` and no
  ServiceAccount token (`frankgateway.securityContext`). The etcd members
  switch from root to uid 1001: on their first start the kubelet re-owns the
  existing PVC to group 1001 (`fsGroup`, `fsGroupChangePolicy:
  OnRootMismatch`), so the stored routes are kept. A CSI driver without
  fsGroup support needs a one-off `chown -R 1001:1001` of the etcd volumes, or
  `frankgateway.securityContext.enabled: false`.
  The APISIX Admin API now only accepts private source addresses
  (`frankgateway.admin.allowFrom`) and, with `frankgateway.networkPolicies`,
  only the seed and sync jobs; the Control API (9092) listens on loopback
  only. With the dashboard on, the opt-in
  `frankgateway.dashboard.networkPolicy.enabled` (default `false`) adds
  NetworkPolicies that let only the oauth2-proxy reach the shim and only the
  shim reach the dashboard. Turn it on where the dashboard runs on a cluster
  that enforces NetworkPolicy; reach a dashboard without auth with
  `kubectl port-forward`.

- **The upgrade empties Redis; no maintenance window needed for employees.** redis-operator
  v0.27.0 renames the Redis append-only file from `Appendonly.aof` to
  `appendonly.aof` (upstream PR #1904). Every `redis-ha` pod restarts, finds no
  file under the new name and starts empty, and the replicas then copy the
  empty master:
  - caches refill by themselves;
  - the Django sessions of the components live in the Redis cache and are
    lost. Employees still have their Keycloak session, so the next request
    logs them in again through OIDC without a password prompt;
  - residents and businesses logged in to Open Formulieren or Open Inwoner
    with DigiD or eHerkenning at that moment lose that login and have to log
    in again; a form in progress may have to be resumed or started again. So
    deploy outside peak hours for those portals.

  Only Celery tasks still waiting in a queue at that moment are lost, for
  example notifications and Open Forms registrations not yet processed. So
  deploy when the Celery queues are empty. For each component's broker
  database (the list is in `values.yaml` above `redis-operator`), this must
  print `0`:

  ```bash
  kubectl --context "$CTX" -n "$NS" exec redis-ha-0 -c redis-ha -- \
    sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} -n <db> LLEN celery'
  ```

  The old `Appendonly.aof.*` files stay in `/data/appendonlydir` on each
  volume; remove them after the upgrade. On a test environment Redis went from about
  490,000 keys to about 890.

- **Fix inconsistent file-upload catalogues.** Run

  Forms 4.0 no longer sets them through setup-configuration: the API groups
  keep their values as a default, and a form can override them; see
  [Open Formulieren: the catalogue and document type fields of the API groups](#open-formulieren-the-catalogue-and-document-type-fields-of-the-api-groups).
- **Test DigiD and eHerkenning login** on a form, and any form embedded on
  another site (the Open Forms cookies are now `SameSite=Lax`, see
  [Open Formulieren: cookies are `SameSite=Lax`](#open-formulieren-cookies-are-samesitelax)).
  A login through OIDC keeps working; a direct SAML login with an HTTP-POST
  ACS does not.

- **Point the old objecttypen hostname at objecten** (the migrated
  `services-gateway.yml`, in the same pipeline run as the deploy), then run
  `check_for_external_objecttypes` in objecten: it must print `OK`.
- **Remove a leftover Enterprise Search.** KISS has not used Enterprise
  Search since 3.0.0 (PodiumD 4.9.0), and the chart renders none
  (`kiss-eck.eck-enterprise-search.enabled: false`). Environments that still
  ran it from the old `kisselastic` subchart can have kept the custom resource:
  Helm no longer manages it, so no upgrade removes it, and its pod keeps its
  memory request reserved. Check, and delete it unless the environment turned
  `eck-enterprise-search` on itself:

  ```bash
  kubectl -n <namespace> get enterprisesearch
  kubectl -n <namespace> get enterprisesearch kiss \
    -o jsonpath='{.metadata.labels.helm\.sh/chart}{"\n"}'   # kisselastic-…: a leftover
  kubectl -n <namespace> delete enterprisesearch kiss
  ```

  ECK then removes the `kiss-ent` Deployment, Service and Secrets with it;
  Elasticsearch, Kibana and the KISS indices are not touched. Found on one
  ExternalsPodiumD environment (2026-10-21); the others that could be checked had
  none.
- **ZAC's Solr probes now fail when Solr is unhealthy, and Solr runs as
  non-root.** The zac chart goes to 1.0.355 (the chart of ZAC 5.10); the ZAC
  image stays on 5.9.1. With basic
  auth the Solr Operator ran its probes as `solr api ... | grep -v`, which
  passed whenever anything was printed, so a Solr node that lost ZooKeeper at
  startup and shut down its cores stayed Ready. The chart's readiness and
  liveness probes are now `curl -f` against `/solr/admin/info/health`: such a
  node leaves the Service and is restarted after 2 minutes. The chart also adds
  memory limits (nginx and OPA 128Mi, init container 256Mi, office converter
  1Gi) to ZAC's pods; an environment that sets its own `resources` for them
  keeps them. Its new `runAsGroup: 10001` is cancelled in podiumd's
  `values.yaml` (`runAsGroup: null`), so the ZAC 5.9.1 containers keep their
  users and groups; Helm merges an environment's own `securityContext` keys
  with these, so only an environment that sets `runAsGroup` itself changes it.
  Solr and its init containers (`cp-solr-xml`, `setup-zk`) now run as uid
  8983, the solr image's own user that already owns the Solr data, with
  `fsGroupChangePolicy: OnRootMismatch`; the solr container also drops all
  capabilities. The Solr operator rolls the Solr pods to the new spec one at
  a time. During that roll the pods that still run the old spec can fail
  their health checks with 401 (the new spec turns on authenticated probes)
  and be restarted: that is expected, they come back with the new spec. ZAC
  waits for the Secret `zac-solr-solrcloud-security-bootstrap`, which the
  operator creates with the new spec. If ZAC still reaches its progress
  deadline (10 minutes, for example with a large index or slow nodes), wait
  until the SolrCloud has all pods ready and run the deploy again. SSC: no
  action.

## OpenBao and Frank!Gateway (only environments that enable them)

`openbao.enabled` and `frankgateway.enabled` are `false` by default. An
environment that keeps them off needs nothing from this section.

**Enabling OpenBao for the first time** (it holds the Frank!Gateway secrets)
is a one-time setup per environment, followed by one script after every
deploy. The full flow is in
[`frankgateway-openbao-activation.md`](../apps/frankgateway/frankgateway-openbao-activation.md);
in short:

1. **Key Vault, once.** The pipeline or Terraform creates three items in the
   environment Key Vault, so nobody types a secret:

   | Item | Value at creation |
   | --- | --- |
   | `openbao-db-admin` | random password, as for the other app databases |
   | `openbao-seal-key` | 32 random alphanumeric characters; never regenerate it |
   | `openbao-unseal-key` | the literal text `pending-init` |

   Turn on soft delete and purge protection on the vault: losing
   `openbao-seal-key` loses everything stored in OpenBao. With the static
   seal, `openbao-unseal-key` ends up holding OpenBao's *recovery* key; the
   activation script writes it there on its first run, and that is the only
   Key Vault write it does.
2. **Database.** Create the database `openbao` and the role
   `openbao-admin` (password `openbao-db-admin`) on the Azure PostgreSQL
   server, as for the other app databases, and give the role rights on the
   `public` schema. Owning the database is not enough on Azure PostgreSQL:
   without the grant the `openbao-db-schema` Job fails with `permission
   denied for schema public`. As the server admin, connected to `openbao`:

   ```sql
   GRANT ALL PRIVILEGES ON DATABASE "openbao" TO "openbao-admin";
   GRANT USAGE, CREATE ON SCHEMA public TO "openbao-admin";
   ```

3. **Permissions.** The deploy reads `openbao-db-admin` and
   `openbao-seal-key`. The activation step reads and writes
   `openbao-unseal-key`, creates Secrets and Jobs, execs into pods in the
   namespace and runs `helm get` on the release.
4. **Values.** Substitute `REP_OPENBAO_DB_PASSWORD_REP` and
   `REP_OPENBAO_SEAL_KEY_REP` (`openbao.seal.static.key`) like the other
   passwords. The render fails on a seal key that is not 32 bytes, which
   also catches a placeholder that was not substituted. Leave the OpenBao
   Keycloak client secret empty: the chart generates it.
5. **Pipeline steps.** Before every deploy: `scripts/openbao-keycloak-setup.py`
   (the `openbao` client, the `uploaders` role and the `vault-uploaders`
   group). After every deploy: `scripts/openbao-activate.sh`. On the first run
   it initialises and configures the vault; after that it only checks,
   re-runs the `openbao-config` Job and exits 0. The scripts are not in the
   packaged chart: run them from a checkout of the deployed chart version.
6. **Afterwards nothing by hand.** The pods unseal themselves after a
   restart, CronJob `openbao-token-renewal` renews both tokens weekly (alert
   on a failed run), and no root token is stored. Add the people who write
   the gateway's secrets to the Keycloak group `vault-uploaders`.

**An environment that already runs OpenBao with the Shamir seal** (no
`openbao.seal.static.key`) has to migrate once, by hand: deploy with the key
set, then run `bao operator unseal -migrate` with the current unseal key (see
[§3.6.1](../apps/frankgateway/frankgateway-openbao.md#361-static-seal-unseal-without-an-operator-optional)).
The pipeline does not migrate. Without the key, `openbao-activate.sh` stops
on the Shamir seal unless it is given `--allow-shamir`, and every pod restart
needs a manual unseal.

Security update: 26.7.5, 26.8.0 and 26.8.1 fix about 40 CVEs, among them
several in identity brokering (DigiD/eHerkenning log in through the OIDC
broker) and in Authorization Services. keycloak-config-cli stays on
`6.5.1-26.5.5`, the newest build.

Changes in Keycloak 26.8 that can affect an environment (see the upstream
[upgrading guide](https://www.keycloak.org/docs/latest/upgrading/)):

- **Identity provider mappers no longer grant admin roles by default**
  (CVE-2026-12388, IN-3203). A mapper that grants an admin role, or adds users
  to a group that carries admin roles, is refused when it is created or
  updated and at broker login, unless the identity provider's config has
  `allowAdminRoleMapping: "true"`. The default is off, also for existing
  identity providers. Without it, `keycloak-import-master-realm` fails on
  every run with `Create method returned status Forbidden (Code: 403)` at
  `IdentityProviderMapperRepository.create`, nothing after the mapper is
  imported, and users who log in through the identity provider don't get the
  admin role. Set it on the identity provider in
  `keycloak.config.adminIdentityProviders.identityProviders[].config`. The
  chart does not set it itself: granting admin roles through an external
  identity provider stays an explicit choice per environment. The render fails
  when an `oidc-hardcoded-role-idp-mapper` in
  `keycloak.config.adminIdentityProviderMappers` grants `admin`,
  `create-realm`, or a `realm-management` or `<realm>-realm` client role
  through an identity provider in these values without the setting. The check
  does not see composite roles or group mappers: an
  `oidc-hardcoded-group-idp-mapper` into a group with admin roles needs the
  setting too. The chart's podiumd realm group `/administrators` carries no
  admin roles, so a mapper into it keeps working.

- **SMTP StartTLS is enforced** (CVE-2026-107121). With
  `keycloak.config.smtp.starttls: "true"` (the default) Keycloak no longer
  falls back to plaintext: when the mail server does not offer STARTTLS,
  sending mail (password reset, verify email) fails. Check the realm's mail
  server, or set `starttls: "false"` for a mail server without TLS.
- **Backchannel logout tokens from an external OIDC identity provider must
  be signed**, also when `Validate Signatures` is off on the identity
  provider. An identity provider with backchannel logout and signature
  validation off needs its JWKS URL or public key configured.
- **An identity provider's client secret must be entered again** when its
  token URL changes (CVE-2026-15943).
- **Disabled clients are no longer in the token audience** (`aud`) and their
  roles are not in `resource_access`.
- **Brute-force login failures are stored in the database** by default, so a
  lock-out survives a Keycloak restart. Expect slightly more database load.
- **Refresh tokens expire with the user session idle timeout.**
  `refresh_expires_in` can be shorter than before; clients refresh earlier.
- **Client secret rotation and the SCIM API are enabled by default**
  (promoted from preview). PodiumD uses neither.
- **Database migration** adds a column and rebuilds indexes on
  `OFFLINE_USER_SESSION` at the first start. Above 300000 rows Keycloak
  builds the indexes in the background after startup (PostgreSQL
  `CREATE INDEX CONCURRENTLY`).
- **Deprecated:** the client switch *Full Scope Allowed*. It is on for
  PodiumD's clients (the Keycloak default; the realm config does not set it),
  so Keycloak logs a deprecation warning per client. No action yet: upstream

limit (`-XX:MaxRAMPercentage=75`) instead of `-Xmx1024m`. podiumd sets no

**Behandelaar roltype.** Since ZAC 5.6, ZAC only uses a roltype whose
omschrijving is exactly `Behandelaar` (and omschrijving generiek
`behandelaar`) to assign a zaak
([ZAC #6767](https://github.com/infonl/dimpact-zaakafhandelcomponent/pull/6767)).
A zaaktype without it still gets its zaak from a productaanvraag, but ZAC
cannot assign it or start its CMMN process (`RoltypeNotFoundException` in the
ZAC log), so no ontvangstbevestiging is sent. ZAC's health check lists such
zaaktypen. Check every zaaktype ZAC uses before the upgrade, and give it a new
version with that roltype where needed. The chart's e2e zaaktype
(`create_required_catalogi_job.e2eTestZaaktype.create`) is fixed by the job
itself: it publishes a new version with roltype `Behandelaar`, and ZAC moves
its zaakafhandelparameters to it. Before 4.10.0 this job ran only on
environments that set `openzaak.enabled` explicitly; see "Before you deploy".
A new zaaktype version has two consequences for other clients. Open Zaak autorisaties given per zaaktype URL only cover the
old version, so a client with such rights must get them on the new version too.
Tooling that looks up a zaaktype by identificatie now finds two versions and
must use the one without an end date (`eindeGeldigheid`).

**Documents up to 500 MB.** ZAC streams uploads and downloads, and podiumd
now follows the ZAC chart's defaults: `zac.maxFileSizeMB` 500 (was 150),
`zac.maxInMemoryFileSizeMB` 80 (preview, mail and WebDAV editing, which
cannot stream), `zac.nginx.client_max_body_size` 600M (was 150M) and
`zac.nginx.proxy_timeout` 1800s. ZAC uploads large documents to Open Zaak in
parts (bestandsdelen), so Open Zaak's nginx timeouts go from 300s to 1800s
too (`openzaak.nginx.config.proxyConnectTimeoutSeconds` and
`proxyReadTimeoutSeconds`); its body size limit is already 4G. Per
environment:

1. Remove `zac.maxFileSizeMB: 150` and `zac.nginx.client_max_body_size: 150M`
   from the gemeente values, or the 150 MB limit stays. 68 SSC environments
   set both (SSCHostingSync `fdddbdb`).
2. Allow 600 MB on the gateway routes in front of zac-nginx and
   openzaak-nginx. NGINX Gateway Fabric's default is nginx's `1m`, and the
   podiumd chart does not deploy the routes. Open Zaak's route is needed
   because ZAC reaches Open Zaak through its external URL (`zac.zgwApis.url`).
   Add to the environment's `ssl-gateway.yml`, one policy per route
   (`hr-zac-nginx`, and `hr-openzaak-nginx` with its own `metadata.name`,
   e.g. `openzaak-large-documents`):

   ```yaml
   apiVersion: gateway.nginx.org/v1alpha1
   kind: ClientSettingsPolicy
   metadata:
     name: zac-large-documents
     namespace: ingress-basic
   spec:
     targetRef:
       group: gateway.networking.k8s.io
       kind: HTTPRoute
       name: hr-zac-nginx
     body:
       maxSize: "600m"
   ```

   The unit must be lowercase (`600m`): the CRD only accepts `k`, `m` or `g`.

Applied and tested on info/ontw (ExternalsPodiumD `ddba916`, `cbd71e5`).
Without a ZAC image change the practical ceiling is about 768 MB
(`dev.resteasy.entity.file.threshold` in the image); the hard limit is
2047 MB (the Documenten API stores `bestandsomvang` as a 32-bit byte count).

## Objecten 4: migrating objecten and objecttypen to Open Object

PodiumD 4.10.0 replaces the separate `objecten` (objects-api) and
`objecttypen` (objecttypes-api) charts with one `openobject` chart, aliased
`objecten`. The Objecttypen API is now served by objecten itself. Background
and design decisions: [`openobject-migration.md`](../apps/objecten/openobject-migration.md).

Every gemeente `podiumd.yml` that configures objecten/objecttypen must be
migrated. Use the script; it applies every change below and keeps comments,
quoting and `REP_..._REP` placeholders as they are:

```bash
pip install ruamel.yaml
# Preview: unified diff, nothing written
python3 charts/podiumd/scripts/migrate-objecten-4.1.0.py --dry-run --gemeenten-dir <SSCHostingSync>/applications/gemeenten
# Migrate (podiumd.yml + the sibling services-gateway.yml)
python3 charts/podiumd/scripts/migrate-objecten-4.1.0.py --gemeenten-dir <SSCHostingSync>/applications/gemeenten
```

The script prints per file what it changed and what still needs a person.
Running it twice is safe: the second run changes nothing. The resulting values
are in the
[values deltas](4.9.5-to-4.10.0-values-deltas.md#objecten-362--430-chart-2121--120);
environment-specific findings (the 8 stubs, image names, token shapes, live
checks) in
[`4.9.5-to-4.10.0-gemeente-specific.md`](4.9.5-to-4.10.0-gemeente-specific.md).

### Read this first: one token per identifier after the merge

Before 4.10.0, objecten and objecttypen were two applications, each with its
own token table. Many environments have a token with the **same identifier in
both** (for example `zaak`, `omc`, `openbeheer-token`, `ibz`) but a
**different value**. A client sent the objecten value to the Objecten API and
the objecttypen value to the Objecttypen API.

From 4.10.0 on, one application (Open Object) serves both APIs, also on the
old `<env>-objecttypen` hostname, with one token table. An identifier can have
only one value, and **the objecten value wins**. So:

- Every client that called the Objecttypen API with the objecttypen token of
  an identifier that objecten also has, with another value, must send the
  **objecten** token of that identifier instead. If it keeps sending the old
  value, it gets `403` after the upgrade. Tokens that exist only in objecttypen
  are copied and keep working (see below).
- For clients configured in the gemeente values, the migration script does
  this rewrite (see the table below) and reports each identifier it changed.
- Clients outside the values are not rewritten: **external parties** that call
  the Objecttypen API with their own token, and services configured by hand in
  an admin (Open Formulieren, Open Inwoner, Open Beheer). Tell them before the
  upgrade which token to use from then on.
- Tokens that exist only in the objecttypen database are copied by
  `migrate-objecttypen-tokens.sh`, which also lists the identifiers where the
  objecten token wins (`objecten-wins`).

Which tokens are affected differs per environment. Find out before the
upgrade, per environment:

1. Run `migrate-objecttypen-tokens.sh --context <ctx>` (dry-run). Each
   `objecten-wins` line is an identifier whose clients must switch.
2. For each such identifier, find the clients: the migration script's report
   for the values, the admin of each component for hand-made services, and
   the contact person of the token for external parties.
3. Switch those clients at the moment of the upgrade.

Example: ontw-dim1 on 2026-10-07:

| objecttypen token | Used by | Same identifier in objecten | Action |
| --- | --- | --- | --- |
| `objecten` | objecten itself, Open Formulieren | no | values migration merges it; no client change needed |
| `openbeheer-token` | Open Beheer | yes, other value | Open Beheer uses the objecten value for both services |
| `ibz` | external party | yes, other value | the external party switches to the objecten value |
| `zaak`, `omc` | no client found | yes, other value | nothing; the objecten value stays |
| `integratieteam` | (both APIs) | yes, same value | nothing |

### Manual steps per environment

1. **Mirror the new image**: `maykinmedia/open-object` (4.3.0) must be in the
   registry the environment pulls from, as `<acr>/maykinmedia/open-object`,
   before deploying. It is listed in
   [`images-4.10.0.yaml`](../images/images-4.10.0.yaml) and
   [`images-baseline.yaml`](../images/images-baseline.yaml), so a mirror run
   from the 4.10.0 manifest picks it up.
2. **Import the objecttypes as the last step before deploying 4.10.0**: see
   [Importing the objecttypes (pre-deploy step)](#importing-the-objecttypes-pre-deploy-step).
   Open Object 4 refuses to start with remaining external objecttypes.
3. **Migrate the objecttypen tokens, directly after the import**: see
   [Migrating the objecttypen tokens (pre-deploy step)](#migrating-the-objecttypen-tokens-pre-deploy-step).
   Tokens that exist only in the objecttypen database stop working at the
   cutover otherwise.
4. **Switch clients outside the values** for every `objecten-wins` identifier
   (external parties, hand-made admin services): see
   [Read this first](#read-this-first-one-token-per-identifier-after-the-merge).
5. **Right after the deploy**: run `check_for_external_objecttypes` in
   objecten; it must print `OK`. The old objecttypen hostname keeps serving
   the Objecttypen API through the deploy: the chart replaces the
   `objecttypen` Service with one that selects the objecten web pods
   (`objecttypenCompatService`, on by default in 4.10.x), so a gateway
   ExternalName to `objecttypen.<namespace>.svc` reaches objecten without a
   change. This holds for the API only, and only when the old public
   hostname is in `objecten.settings.allowedHosts` (the migration adds it,
   see the table above). The admin login on the old hostname still fails:
   the `objecten` Keycloak client has no redirect URI for it, so admins use
   the objecten hostname. Repoint the gateway route to objecten
   (`services-gateway.yml` above) when convenient. After a repoint, check
   that the gateway picked it up: with NGINX Gateway Fabric controller 2.6.5
   the data plane kept the old upstream until the controller was restarted
   (`kubectl -n ingress-basic rollout restart deploy/nginx-gateway-fabric`).

   Two cases need attention:
   - **Something else already provides an `objecttypen` Service** in the
     namespace (another release, or a wrapper chart in the same release):
     set `objecttypenCompatService.enabled: false`. The chart fails the
     render when the existing Service belongs to another release; a wrapper
     chart in the same release would define the resource twice.
   - **In-cluster clients that call the short name** `http://objecttypen` or
     `http://objecttypen.<namespace>`: they now reach objecten with that Host
     header and get `400 DisallowedHost`, because objecten's `ALLOWED_HOSTS`
     covers `objecten`, `objecten.<namespace>` and `.svc.cluster.local` only.
     Use the full `objecttypen.<namespace>.svc.cluster.local` (what the SSC
     and ExternalsPodiumD values use), or add the short names to
     `objecten.settings.allowedHosts`.
6. **After the cutover**: clean up the Keycloak `objecttypen` client and the
   old objecttypen database once the environment runs fine.

### Rollback

Back up the objecten and objecttypen databases before step 2. If the upgrade
fails:

1. Check the objecten logs first (`kubectl logs deploy/objecten --previous`).
   A startup error that names objecttype UUIDs means objecttypes were not
   imported; anything else (image pull, database, memory) is a different
   problem.
2. `helm rollback podiumd <last 4.9.x revision>`. This brings back the
   separate objecttypen deployment. The `objecttypen` Service exists the whole
   time (`objecttypenCompatService`); the rollback patches it back to the
   objecttypen chart's selector. Restore the objecten database from the
   backup if the 4.10.0 migrations already ran.
3. Only if the gateway route for the objecttypen hostname was already
   repointed to objecten: point it back to objecttypen. A gateway that still
   uses the ExternalName to `objecttypen.<namespace>.svc` needs no change.
4. Tokens that the token step (manual step 3) copied into objecten can stay:
   in objecten 3.6 they have no rights. Clients that switched to the objecten
   token for the Objecttypen API must switch back.
5. For unimported objecttypes: run `import_objecttypes` again if the
   objecttype still exists in objecttypen. If it was deleted there, it cannot
   be imported; remove it from objecten (admin, or the Django shell), then
   check with the `is_imported` query from
   [Importing the objecttypes](#importing-the-objecttypes-pre-deploy-step)
   before trying again: objecten 3.6.x has no `check_for_external_objecttypes`.

### Importing the objecttypes (pre-deploy step)

Open Object 4 serves objecttypes from its own database. The running objecten
(3.6.x; PodiumD 4.9.x ships 3.6.2) copies them from objecttypen with
`import_objecttypes`. Run it in the deploy pipeline, directly before the
4.10.0 `helm upgrade`:

- It copies the latest state: objecttypes changed after the import are not
  copied, so keep the gap to the upgrade short.
- It upserts on objecttype `uuid`, so it is safe to run again.
- While it runs, nothing has switched yet: objecttypen and the old
  objecttypen hostname still serve as before. If it fails, stop the pipeline;
  the environment stays on 4.9.x untouched.
- A check then confirms that every objecttype is imported. It prints `OK`,
  or exits non-zero listing the UUIDs that are not. objecten 3.6.x has no
  `check_for_external_objecttypes` command (that ships with Open Object 4),
  so the check below queries the same `is_imported` flag directly.

`import_objecttypes` takes the slug of the `zgw_consumers` service that points
at objecttypen. The slug differs per environment: `objecttypen-api` in every
SSC environment, `objecttypes-api` in the chart example, `objecttypen` on some
test environments. Take it from the 4.9.x values
(`objecten.configuration.data` → `objecttypes.items[].service_identifier`;
the migration script removes it), or list the services in the running
objecten (`orc` is the Objecttypen API type; set `CTX` and `NS` as below):

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
  "from zgw_consumers.models import Service; [print(s.slug, s.api_type, s.api_root) for s in Service.objects.all()]"
```

The import fails with `Service '<slug>' does not exist` on a wrong slug, and
with a connection error when objecttypen is not reachable. Both exit non-zero
before anything is written.
Background: [`openobject-migration.md`](../apps/objecten/openobject-migration.md) §A.

Every `kubectl` call below passes `--context` explicitly, so a command never
runs against whatever cluster happens to be the current context. Set `CTX`
to the environment's context first.

**Option 1: `kubectl exec` in the running objecten pod.** Simplest, needs
`pods/exec` rights:

```bash
CTX=<kube-context-of-the-environment>   # never rely on the current context
NS=podiumd
SLUG=<objecttypen-service-slug>         # e.g. objecttypen-api (SSC)
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py import_objecttypes "$SLUG"
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c "from objects.core.models import ObjectType as T; bad=[str(u) for u in T.objects.exclude(is_imported=True).values_list('uuid', flat=True)]; print('OK' if not bad else 'NOT IMPORTED: ' + ', '.join(bad)); raise SystemExit(1 if bad else 0)"
```

**Option 2: one-time Job.** Needs no exec rights. The Job uses the same image
and the same `objecten` Secret and ConfigMap as the running objecten
Deployment:

```bash
CTX=<kube-context-of-the-environment>   # never rely on the current context
NS=podiumd
SLUG=<objecttypen-service-slug>         # e.g. objecttypen-api (SSC)
IMAGE=$(kubectl --context "$CTX" -n "$NS" get deploy objecten -o jsonpath='{.spec.template.spec.containers[?(@.name=="objecten")].image}')
kubectl --context "$CTX" -n "$NS" delete job objecten-import-objecttypes --ignore-not-found
kubectl --context "$CTX" -n "$NS" apply -f - <<EOF
apiVersion: batch/v1
kind: Job
metadata:
  name: objecten-import-objecttypes
spec:
  backoffLimit: 0
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsUser: 1000
        runAsGroup: 1000
        runAsNonRoot: true
      containers:
        - name: import-objecttypes
          image: ${IMAGE}
          command: ["/bin/sh", "-c"]
          args:
            - |
              python /app/src/manage.py import_objecttypes ${SLUG} &&
              python /app/src/manage.py shell -c "from objects.core.models import ObjectType as T; bad=[str(u) for u in T.objects.exclude(is_imported=True).values_list('uuid', flat=True)]; print('OK' if not bad else 'NOT IMPORTED: ' + ', '.join(bad)); raise SystemExit(1 if bad else 0)"
          envFrom:
            - secretRef:
                name: objecten
            - configMapRef:
                name: objecten
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              memory: 512Mi
EOF
kubectl --context "$CTX" -n "$NS" wait --for=condition=complete job/objecten-import-objecttypes --timeout=10m \
  || { kubectl --context "$CTX" -n "$NS" logs job/objecten-import-objecttypes; exit 1; }
kubectl --context "$CTX" -n "$NS" logs job/objecten-import-objecttypes
```

Add a `nodeSelector` if the environment pins workloads to a node pool (SSC:
`kubernetes.azure.com/mode: user`).

**Order in the 4.10.0 deploy run**:

1. `import_objecttypes` and the check (above). Stop on failure.
2. `migrate-objecttypen-tokens.sh`: dry-run, then `--apply` (see
   [Migrating the objecttypen tokens](#migrating-the-objecttypen-tokens-pre-deploy-step)).
   Stop on failure.
3. `helm upgrade` to 4.10.0 with the migrated `podiumd.yml`. objecten becomes
   Open Object 4.3.0, and objecttypen is removed.
4. The migrated `services-gateway.yml`: the old objecttypen hostname then
   routes to objecten directly. With `objecttypenCompatService` (on by
   default in 4.10.x) the old hostname keeps serving the Objecttypen API
   between steps 3 and 4, so this can be a later pipeline run. With it off,
   the old hostname has no backend between steps 3 and 4: run them in the
   same pipeline run.

5. After the upgrade: `check_for_external_objecttypes` exists in Open Object 4
   and must print `OK`:

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py check_for_external_objecttypes
   ```

Keep the old objecttypen hostname after the cutover. Objects, Open Formulieren
and ZAC/ITA/KISS/OMC configuration store objecttype URLs with that hostname.
Open Object 4 accepts those URLs, as `type` when creating an object and as a
`type` filter. In its responses it builds every URL from its own hostname:
an object's `type` comes back as `https://<objecten-host>/api/v2/objecttypes/<uuid>`.
That is why the migration script also rewrites the consumers' objecttype URLs
to the objecten hostname.

Tested end to end on a QA environment (johnb00, 2026-10-06):

- Setup: fresh objecten 3.6.2 and objecttypen 3.4.2, the old ingress, the
  4.9.4 create-required-objecttypen job, and objects created over the old
  hostname.
- Import: imported all objecttypes and versions. Run again after a change in
  objecttypen, it picked up the change without creating duplicates.
- Upgrade: Open Object 4.1.0 started on the migrated database, and
  `check_for_external_objecttypes` printed `OK`.
- After the cutover: objecttypes and objects were served on both hostnames.

### An objecttype that no longer exists in objecttypen

`import_objecttypes` copies only what objecttypen still has. An objecttype
row in objecten that points at objecttypen while the objecttype was deleted
there cannot be imported, and the `is_imported` check lists its UUID
(ontw-dim1, 2026-10-20: `Productaanvraag-eSuite`, 0 objects). Open Object 4
refuses to start with it, so deal with it before the `helm upgrade`:

1. Check that it is really gone upstream and unused:

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/objecttypen -c objecttypen -- python /app/src/manage.py shell -c \
     "from objecttypes.core.models import ObjectType as T; print(T.objects.filter(uuid='<uuid>').exists())"
   kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
     "from objects.core.models import ObjectType as T; t=T.objects.get(uuid='<uuid>'); print(t._name, t.object_set.count())"
   ```

   It must print `False`, and the objecten row must have 0 objects. With
   objects, stop: restore the objecttype in objecttypen (same UUID) and import
   again.
2. Delete the row in objecten. This also deletes the token permissions on it:

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
     "from objects.core.models import ObjectType as T; print(T.objects.get(uuid='<uuid>').delete())"
   ```

3. Run the `is_imported` check again; it must print `OK`.

If the environment's `objecten.configuration.data` still lists that UUID
under `objecttypes` (for example `esuite_productaanvraag_uuid`), the
4.10.0 config job creates it again as a local objecttype without versions,
and restores the token permissions from `tokenauth`. Objects created by the
config step get `is_imported=False` (the model default), so after the deploy
`check_for_external_objecttypes` fails on that UUID, and a later restart
could run into Open Object's upgrade check. Either remove the UUID from the
configuration (and its `permissions` entries) before the deploy, or mark the
re-created objecttype as imported after the deploy:

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
  "from objects.core.models import ObjectType as T; print(T.objects.filter(uuid='<uuid>', is_imported=False).update(is_imported=True))"
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py check_for_external_objecttypes
```

The second command must print `OK`.

### Migrating the objecttypen tokens (pre-deploy step)

After the cutover objecten (Open Object 4) serves the Objecttypen API, so
every token a consumer sends to the old objecttypen hostname must be a token
of objecten. Two kinds of objecttypen tokens exist:

- **Tokens in the values** (`objecttypen.configuration.data` → `tokenauth`).
  The migration script merges them into `objecten.configuration.data`, and
  the 4.10.0 setup-configuration job creates them in objecten.
- **Tokens only in the objecttypen database**, created by hand in the
  objecttypen admin. Neither `import_objecttypes` (it copies objecttypes only)
  nor the migration script (it only sees the values) migrates them. Without
  this step they stop working at the cutover. Example, from the objecttypen
  databases on 2026-10-07: `formulier`, `ibz`, `oip` and `openbeheer` on
  ontw-dimp; `token-2` and `token-3` on accp-dimp.

If the identifier already exists in objecten with another token, nothing is
copied: the objecten token wins, and the clients of the objecttypen token must
switch (see [Read this first](#read-this-first-one-token-per-identifier-after-the-merge)).
On ontw-dim1 that is `ibz`, `omc`, `openbeheer-token` and `zaak`.

`charts/podiumd/scripts/migrate-objecttypen-tokens.sh` copies the second kind
from the running objecttypen database into the running objecten database.
SSC runs it per gemeente environment, after `import_objecttypes` and before
the 4.10.0 `helm upgrade`, while objecttypen (3.4.x) and objecten (3.6.x)
both still run. It needs `pods/exec` rights, like option 1 of the import
step. It is a dry-run unless `--apply` is given:

```bash
CTX=<kube-context-of-the-environment>   # required; the current context is never used
charts/podiumd/scripts/migrate-objecttypen-tokens.sh --context "$CTX"           # dry-run: what --apply would do
charts/podiumd/scripts/migrate-objecttypen-tokens.sh --context "$CTX" --apply   # create the missing tokens
```

`--namespace` defaults to `podiumd`. The script reads the identifiers of
objecttypen's configured tokens from the ConfigMap the objecttypen config job
uses (`objecttypen-configuration`, key `configuration.yaml`; `--configmap` if
it is named differently). For every token in the objecttypen database it
prints one line, then a summary (ontw-dim1, 2026-10-07):

```text
Mode: dry-run (nothing written; --apply creates the tokens)
objecttypen identifier           sha256       action              objecten identifier
ibz                              d24861a81d2c objecten-wins       ibz (clients must switch to this objecten token)
integratieteam                   b5623e70fb01 exists-same-token   integratieteam
objecten                         104afcf76e6d skipped             - (in objecttypen configuration: merged by the values migration)
omc                              89a584eeda19 objecten-wins       omc (clients must switch to this objecten token)
openbeheer-token                 39d8c023a867 objecten-wins       openbeheer-token (clients must switch to this objecten token)
zaak                             9db4a7c06070 objecten-wins       zaak (clients must switch to this objecten token)
Summary: exists-same-token 1, objecten-wins 4, skipped 1
```

| Action | Meaning |
| --- | --- |
| `exists-same-token` | objecten already has this token (under the identifier shown). Nothing to do. |
| `objecten-wins` | objecten already has this identifier with another token. Nothing is created. Clients that send the objecttypen token must switch to the objecten token of this identifier. |
| `skipped` | The identifier is in objecttypen's configuration and not yet in the objecten database: the values migration merges it, and the 4.10.0 config job creates it in objecten. |
| `created` | Created in objecten with the same identifier. |
| `error` | The token cannot be created (an invalid field). Nothing is written; fix it by hand. |

What it copies, and what not:

- The token, identifier, `contact_person`, `email`, `organization`,
  `application` and `administration`, the fields both TokenAuth models have.
- No rights. A copied token is not a superuser and gets no object type
  permissions. In objecten 3.6 it can therefore do nothing until the upgrade.
  In Open Object 4 the objecttypes endpoints require only a valid token
  (`IsTokenAuthenticated`), as they did in objecttypen 3.4. The objects
  endpoints check object type permissions, which the copy does not have. So
  the token can do exactly what it could do before.
- Nothing in objecttypen is changed.
- Token values are never printed, logged or written to disk. They go from
  the objecttypen pod to the objecten pod through a pipe (`kubectl exec`
  stdout into `kubectl exec` stdin). The output shows identifiers and the
  first 12 characters of the token's sha256 only.
- Running it again creates nothing: the copied tokens then show as
  `exists-same-token`.

How it fits with the values migration: both follow the same rule, one token
per identifier and the objecten token wins. The setup-configuration job does
an `update_or_create` on the identifier, and Open Object 4 tokens are unique.
The script skips every identifier that is in objecttypen's configuration and
not yet in objecten, because the values migration merges it and the config job
creates it; copying it here as well could put the same token in twice. When
the config job later meets a token that already exists under the same
identifier, it only updates that row.

A copied token lives only in the objecten database, as it did in objecttypen.
To manage it in the values later, add it to `objecten.configuration.data`
`tokenauth` (and the token to Key Vault) **under the identifier the script
printed**. Under another identifier the config job fails on the duplicate
token.

### Open Beheer and other Objecttypen API consumers

Open Beheer reads objecttypes through the `zgw_consumers` service in
`openbeheer.configuration.data` that `api_configuration.objecttypen_service_identifier`
names (usually `objecttypen-service`). It sends `Authorization: Token <token>`.
The migration script repoints its `api_root` to the objecten hostname, like
every other consumer. Its token must then be an objecten token:

- If objecten has the same identifier with another token (for example
  `openbeheer-token`, with `REP_OBJECTTYPEN_OPENBEHEER_TOKEN_REP` in
  objecttypen and `REP_OBJECTEN_OPENBEHEER_TOKEN_REP` in objecten), the
  objecten token wins. The migration script sets Open Beheer's
  `objecttypen-service` token to the objecten token, also when the tokens come
  from `value_from` (ontw-dim1: `header_value: Token
  REP_OBJECTEN_OPENBEHEER_TOKEN_REP`). None of the SSC environments has an
  Open Beheer objecttypen token in its values.
- If the token is only in objecttypen's `tokenauth` items in the values, the
  migration script merges it into objecten.
- If it exists only in the objecttypen database (ontw-dimp: `openbeheer`),
  `migrate-objecttypen-tokens.sh` copies it.

Use the placeholder names as corrected in #469: `REP_OBJECTTYPEN_OPENBEHEER_TOKEN_REP`
for the objecttypen token, `REP_OBJECTEN_OPENBEHEER_TOKEN_REP` for Open
Beheer's `objecten-service`, plus `REP_OPENBEHEER_OIDC_SECRET_REP`,
`REP_OPENZAAK_OPENBEHEER_SECRET_REP` and `REP_OPENBEHEER_DATABASE_PASSWORD_REP`.
Neither script looks at placeholder names: the values migration compares
the token values as written, and the token script compares the tokens in the
databases. The same applies to every other consumer of the Objecttypen API,
such as Open Formulieren's `objecttypen-api` service.

### One zgw_consumers service per api_root (Open Formulieren, Open Beheer)

`zgw_consumers` allows each `api_root` only once. After the migration the
objecttypen service of a component points at the objecten `api_root`. A
component that also has an objecten service there then has two services
with the same `api_root`, and its config job fails during the deploy:

```text
Error while executing step `Configuration to connect with external services`
    duplicate key value violates unique constraint "zgw_consumers_service_api_root_key"
    DETAIL:  Key (api_root)=(https://<objecten-host>/api/v2/) already exists.
```

Open Formulieren (`objecttypen-api` + `objecten-api`) and Open Beheer
(`objecttypen-service` + `objecten-service`) have this pair. Dry run on
copies of the values, 2026-10-21: Open Formulieren in all 70 migrated
SSCHostingSync environments and in 7 ExternalsPodiumD environments
(ontw-dim1 is already fixed by hand); Open Beheer in 6 SSCHostingSync and 2
ExternalsPodiumD environments.

`migrate-objecten-4.1.0.py` merges each pair, also in values files it
migrated before:

1. It removes the objecttypen service from `zgw_consumers.services` and keeps
   the objecten service (`objecten-api`, `objecten-service`).
2. It points every reference to the removed service at the kept one: in Open
   Formulieren `objects_api.groups[].objecttypes_service_identifier`, in Open
   Beheer `api_configuration.objecttypen_service_identifier`.

`api_root`s are compared exactly, as the database does, and only at the
objecten host: a duplicate at another `api_root` isn't this migration's and
is left alone. Anything other than one objecttypen service plus one other
service at an objecten `api_root` is reported as an `ACTION` to fix by hand.
A `configuration.data` that doesn't parse is reported as `CHECK` and not
merged (ExternalsPodiumD ontw-dimp: Open Beheer's has a duplicate
`oidc_provider_identifier` key).

**Open Formulieren's old objecttypen token is switched to `formulier`.**
After the merge the kept service sends its own token for both APIs. In most
environments Open Formulieren's `objecten-api` sends
`Token REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP`, which is no objecten
token at all: on ontw-dim1 it answered 401 on the Objects and the
Objecttypes API. When objecten's `tokenauth` has an item `formulier` with
`read_and_write`, the script switches that header to the `formulier` token
(`Token REP_OBJECTEN_CREDENTIALS_FORMULIER_TOKEN_REP`) and prints
`SWITCHED openformulieren: ...`. A switched component needs no action. The
switch assumes the `formulier` token's Key Vault secret exists in the
environment; the objecten config of every environment already uses it, and
every ExternalsPodiumD Key Vault has it. Dry run on copies of the values,
2026-10-21: switched in 67 SSCHostingSync and 7 ExternalsPodiumD
environments.

**Open Zaak keeps its token; objecten gets an `openzaak` item for it.** Open
Zaak's `objecten-api` service (`api_type: orc`, used to validate zaakobject
URLs that point at objecten) sends the same
`Token REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP`, already before 4.10.0:
on ontw-dim1 it answers 401, because no objecten `tokenauth` item has that
token. Open Zaak keeps the header. The script adds a `tokenauth` item
`openzaak` to objecten with that token instead, and prints `ADDED objecten:
tokenauth item 'openzaak' ...`:

- not a superuser, `read_only` on the objecttypes of the `zaak` item. `zaak` is
  ZAC's own token (`zac.objectenApi.token`), so Open Zaak doesn't share it, and
  validating a zaakobject only needs read access;
- the token in the same form as the `zaak` item's: as the plain placeholder,
  or as `value_from` env `objecten_credentials_openzaak_token`, which the script
  adds to `objecten.configuration.secrets` with the same placeholder.

No new Key Vault secret is needed: the one behind
`REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` already exists (Open Zaak and
Open Formulieren send it today). Its name still says OBJECTTYPEN; that's only a
leftover of the old component. Its value must differ from every other objecten
token of the environment, because Open Object refuses a duplicate token and
the objecten config job then fails: check that before the deploy where the
script added the item. An existing `openzaak` item with another token, or no
`zaak` item with objecttype permissions, is an `ACTION`. Dry run on copies of
the values, 2026-10-21: added in 70 SSCHostingSync and 7 ExternalsPodiumD
environments. In all of them the `zaak` item has one objecttype (the ZAC
productaanvraag objecttype), so Open Zaak can validate zaakobjecten that point
at objects of that objecttype. For zaakobjecten of other objecttypes, add
those objecttypes to the `openzaak` item, `read_only`; don't widen `zaak`.

Values switched to the `zaak` token by an earlier version of this script:
the script reports `CHECK openzaak: ... sends ZAC's 'zaak' token`. Set Open
Zaak's `objecten-api` `header_value` back to
`Token REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` and run the script
again; it then adds the `openzaak` item. The same CHECK appears where Open Zaak
sent `zaak` before this migration (ExternalsPodiumD info); there it's a
choice, not a failure.

Any other component that still sends the old objecttypen token to the
objecten `api_root` is an `ACTION`: the script defines no switch for it. The
2026-10-21 dry run has none.

After a merge the script also checks that the removed service's identifier no
longer appears as a value anywhere in that component's `configuration.data`.
It only repoints `*_service_identifier` keys, so a reference under another key
refuses the file (`error`) and must be repointed by hand.

**Any other token difference stays a decision per environment.** When the
two services sent different tokens and the kept token isn't switched, the
script prints an `ACTION`. Its summary counts them as "need action", lists
them again after the summary, and exits with code 2. The 2026-10-21 dry run
leaves 5: Open Formulieren with the `esuite` token (2 SSCHostingSync
environments) or already with `formulier` (1 SSCHostingSync, 1
ExternalsPodiumD), and Open Beheer in 1 ExternalsPodiumD environment. Before the
deploy, check that the kept service has an objecten token that works for
both APIs and has the permissions the component needs:

- Open Formulieren: the objecten token with `read_and_write` on the
  objecttype it registers to (`formulier`,
  `REP_OBJECTEN_CREDENTIALS_FORMULIER_TOKEN_REP`).
- Open Beheer: its objecten token (a superuser token such as
  `openbeheer-token`).

Both switches also run on values files that were merged before (by an earlier
version of this script or by hand): a service at the objecten `api_root` that
still sends the old objecttypen token is switched the same way.

The token is the `header_value` of the kept service in
`<component>.configuration.data`, either as `Token REP_..._REP` (filled in by
the pipeline) or as `Token {value_from: {env: <key>}}`. In the second case
the value comes from `<component>.configuration.secrets.<key>`, which the
chart puts in the `<component>-configuration-secrets` Secret, so set that
key too. Check the token from inside the cluster against objecten:
`GET /api/v2/objecttypes` and `GET /api/v2/objects` must both return `200`.

The removed service's row stays in the component's database, unused; the
config job leaves rows it no longer manages alone. If a config job already
failed on this during a deploy, fix the values and deploy again. Or apply the
same change to the `<component>-configuration` ConfigMap (the service and its
references) and, for a `value_from` token, the key in the
`<component>-configuration-secrets` Secret, so the job's next retry passes;
then deploy the values afterwards.

## Open Formulieren: the catalogue and document type fields of the API groups

Open Forms 4.0 removed these fields from its setup-configuration models:

- Objects API groups: `catalogue_domain`, `catalogue_rsin`,
  `document_type_submission_report`, `document_type_submission_csv`,
  `document_type_attachment`
- ZGW API groups: `catalogue_domain`, `catalogue_rsin`

Remove them from every group in `openformulieren.configuration.data`, under
both `objects_api.groups` and `zgw_api.groups`. Open Forms 4.0 rejects any

`openformulieren-config` post-upgrade hook job fails, and the

objects_api.groups.0.catalogue_domain

CommandError: Failed to validate requirements for 2 steps
Error: UPGRADE FAILED: post-upgrade hooks failed: resource Job/podiumd/openformulieren-config not ready. status: Failed
```

The job retries 6 times before it fails, which takes about 7 minutes, and
its pod and logs are deleted afterwards.

Use the script. It removes exactly these keys and keeps comments, quoting and
`REP_..._REP` placeholders as they are:

```

It also takes single files: a `podiumd.yml`, or a setup-configuration data
file such as podiumd-infra's `openformulieren.configuration.data.yml` layers.
It prints the values it removed per group, so that a new environment can set
them in the admin. Running it twice is safe: the second run changes nothing.
It is independent of `migrate-objecten-4.1.0.py`; the order does not matter.
The keys it removes are in the
[values deltas](4.9.5-to-4.10.0-values-deltas.md#remove-the-catalogue-and-document-type-fields-from-the-api-groups).

The fields that Open Forms 4.0.2 still accepts:

| Group | Fields |
| --- | --- |
| `objects_api.groups` | `name`, `identifier`, `organisatie_rsin`, `objects_service_identifier`, `objecttypes_service_identifier`, `documenten_service_identifier`, `catalogi_service_identifier` |
| `zgw_api.groups` | `name`, `identifier`, `organisatie_rsin`, `auteur`, `zaak_vertrouwelijkheidaanduiding`, `doc_vertrouwelijkheidaanduiding`, `zaken_service_identifier`, `documenten_service_identifier`, `catalogi_service_identifier`, `objects_api_json_content_template` |

## Open Formulieren: cookies are `SameSite=Lax`

## Keycloak: rolling updates with update strategy Auto

`keycloak.update.strategy: Auto` (IN-3176). The Keycloak operator's default,
`RecreateOnImageChange`, stops every Keycloak pod when the image changes, even
for a patch release or the same version from another registry. Keycloak is
then down for one to two minutes, so every login fails. ZAC refreshes its
token every minute (realm `accessTokenLifespan: 60`), so its users can also
lose their session. With `Auto` the operator first runs an update Job that
checks whether the old and the new version can run side by side, and replaces
the pods one at a time when they can:

- **Rolled, no downtime:** the same version (for example another registry or
  digest) and a newer patch release in the same major.minor (26.8.1 → 26.8.2).
- **Still recreated, with downtime:** a minor or major upgrade
  (26.7.x → 26.8.x). Plan those in a maintenance window; ZAC users may have to
  log in again.

When the check cannot decide or its Job fails, the operator is expected to
recreate the pods as before.

No action needed. An environment that wants the old behaviour sets
`keycloak.update.strategy: RecreateOnImageChange`.

**Optional: a PodDisruptionBudget.** The Keycloak operator creates no
PodDisruptionBudget, and its Keycloak CR has no field for one. A node drain
(autoscaler, node image upgrade, AKS upgrade) therefore only takes Keycloak
down when both pods run on the drained node; the pod anti-affinity is
`preferred`, so that is rare but possible. An environment that wants to rule
it out sets `keycloak.podDisruptionBudget.enabled: true`: the chart then
renders a budget `keycloak` with `maxUnavailable: 1`, so a drain evicts one
Keycloak pod at a time.

Optional, and nothing changes until it is set. Open Inwoner's KvK settings had

## Namespace portability (Redis, allowedHosts, ClamAV, Kibana)

Cluster-internal references that previously hard-coded the `podiumd` namespace no
longer do, so the chart can be deployed into any namespace:

- Redis connection strings use the bare service name `redis-ha-master` (was
  `redis-ha-master.podiumd.svc.cluster.local`). A bare name resolves in the pod's
  own namespace.
- Django `allowedHosts` use the leading-dot wildcard `.svc.cluster.local` (was

  in-cluster only.
- `clamavHost` uses the bare `clamav`; KISS Kibana uses the bare `kiss-kb-http:5601`.

and the wildcard resolve identically there.

## Security headers at the edge (IN-3162)

Several apps send no `Strict-Transport-Security` (HSTS) and/or no
`X-Content-Type-Options: nosniff`: PABC, ITA, OMC, Open Archiefbeheer and Open
Beheer (see [security-headers.md](../misc/security-headers.md)). HSTS belongs at
the edge, where TLS terminates; nosniff is the apps' job, and the vendors are
asked to add it, but the edge sets it too until they do. Not tied to the chart
version: it can be applied before or after the upgrade.

The routes are not in the podiumd chart but in each environment's
`ssl-gateway.yml` (NGINX Gateway Fabric). The script gives every rule of every
HTTPRoute a `ResponseHeaderModifier` that sets `Strict-Transport-Security:
max-age=31536000` and `X-Content-Type-Options: nosniff`:

```bash
pip install ruamel.yaml
python3 charts/podiumd/scripts/migrate-gateway-security-headers.py --dry-run --gemeenten-dir <repo>/applications/gemeenten
python3 charts/podiumd/scripts/migrate-gateway-security-headers.py --gemeenten-dir <repo>/applications/gemeenten
```

- `set` replaces a value an app sends itself, so no header is sent twice. A
  route that already has a `ResponseHeaderModifier` only gets the headers it
  lacks; a header the environment already sets, adds or removes there keeps
  the environment's choice.
- Rules that redirect (`RequestRedirect`) or have no `backendRefs` are skipped.
- No `X-Frame-Options` or CSP: Open Formulieren is embedded in Open Inwoner,
  and only an app can decide whether it may be framed.
- The routes attach to both the http and the https listener, so HSTS is also
  sent over plain HTTP; browsers ignore it there.
- The pipeline applies `ssl-gateway.yml` with `kubectl apply`; no restart is
  needed.

On ExternalsPodiumD `42af10f` it changes all 8 environments (141 routes, 145
rules) and on SSCHostingSync `fdddbdb` all 78 (1246 routes, 1291 rules); a
second run changes nothing, and the result validates against the Gateway API
schema. SSC applies it in its own hosting repo: SSCHostingSync is a read-only
copy.

Tested on QA (NGINX Gateway Fabric 2.6.7, 19 October 2026): the script ran on
the environment's 68 live HTTPRoutes, gave 67 of them the filter (it skipped
the HTTP-to-HTTPS redirect route and two login-redirect rules), the API server
accepted the result, and PABC, Open Beheer, ITA, Open Zaak, Objecten and Open
Formulieren then answered with both headers. A second run changed nothing.

## Redis HA: failover safeguards (IN-2961)

Three new values under `redis-operator.redis-ha`, all on by default:

- `topologySpreadConstraints`: the `redis-ha` pods go to different nodes where
  possible (`maxSkew: 1` on `kubernetes.io/hostname`, `ScheduleAnyway`, so a
  cluster with fewer nodes still starts them). Before, two of the three pods
  could share a node; on QA they did.
- `pdb`: the redis-operator creates a PodDisruptionBudget with
  `maxUnavailable: 1`, so a node drain evicts one Redis pod at a time.
- `masterReadinessCheck.enabled`: a pod labelled `redis-role=master` that
  reports `role:slave` itself is NotReady and drops out of the
  `redis-ha-master` Service. During a failover the operator briefly labels two
  pods master; apps that connected in that window wrote to a read-only replica
  (IN-2869). Correctly labelled replicas stay Ready, so rolling updates are not
  blocked.

The `redis-ha` pods restart once, one at a time, to pick these up. Each master
change makes every Celery worker restart once (`UNBLOCKED force unblock …
(master -> replica?)`); that is expected. Connections an app already holds to a
replica are not closed by this change (IN-2962).

Also fixed by redis-operator v0.27.0 in this release (upstream PR #1843): in
v0.26.0 one unreachable Redis pod could stop the operator from finding the
master, so it re-ran `REPLICAOF` about every 16 seconds and all Celery workers
kept restarting until the pods were recreated. See
[`redis-ha.md`](../apps/redis/redis-ha.md).

SSC: an environment that wants other placement sets its own
`topologySpreadConstraints`, or `[]` to schedule freely.

**Existing environments keep their placement.** The Redis volumes are zonal
disks (`managed-csi-premiumv2`), so a pod can only restart in the zone of its
disk. Where two `redis-ha` volumes share a zone with one node, the two pods stay
on that node. To move one, recreate a **replica** (never the master) with a new
volume; the replica copies the data from the master again:

```bash
kubectl --context "$CTX" -n "$NS" get pods -l app=redis-ha -L redis-role
# pick a pod with redis-role=slave that shares a node with another redis-ha pod
kubectl --context "$CTX" -n "$NS" exec <replica> -c redis-ha -- \
  sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} info replication' # role:slave, master_link_status:up
kubectl --context "$CTX" -n "$NS" delete pvc redis-ha-<replica> --wait=false
kubectl --context "$CTX" -n "$NS" delete pod <replica>
```

The new pod starts on another node with a new disk, briefly reports
`role:master` while it is empty, and within about a minute the operator makes it
a replica again; it is never labelled master, so `redis-ha-master` is not
affected. Tested on QA: the replica moved to the third zone and was back in sync
with the master's 212,809 keys within a minute.

## ZAC: PKCE on by default

ZAC supports PKCE since 5.4.5 (`enable-pkce` in its `oidc.json`, read from
`AUTH_ENABLE_PKCE`). `zac.auth.enablePkce` (default `true`) now drives both
sides: the ZAC sub-chart sets `AUTH_ENABLE_PKCE`, and the realm import sets
`pkce.code.challenge.method: S256` on the `zac` client, so Keycloak requires
PKCE for ZAC's login.

- The old key `zac.auth.pkceEnabled` only set the Keycloak side; turned on
  alone it broke ZAC's login. `zac.auth.pkceEnabled: true` now fails the
  render; a left-over `false` is ignored.
- To opt out, set `zac.auth.enablePkce: false`. The realm import then sets
  `pkce.code.challenge.method` on the `zac` client to an empty value, which
  turns PKCE off there too; no manual step in the Keycloak admin console.
- After the upgrade, check the ZAC login, logout and a session refresh.

## ClamAV configuration Jobs on by default

`openformulieren.clamavConfigJob.enabled` and
`openinwoner.clamavConfigJob.enabled` now default to `true`: uploads in Open Formulieren and Open Inwoner are
scanned by ClamAV. A Job runs while ClamAV itself is deployed
(`clamav.enabled`), or when its `clamavHost` points at a clamd outside this
chart (anything other than the default `clamav`), so an environment with an
external ClamAV keeps its Job.

- All 69 SSCHostingSync environments with ClamAV already set both to `true`:
  nothing changes there.
- The ExternalsPodiumD environments do not set them, so the Jobs run there for
  the first time and switch the virus scan on in both apps.
- To opt out, set `<app>.clamavConfigJob.enabled: false`.

## Security contexts of the chart's own Jobs

- The configure Jobs of Open Formulieren and Open Inwoner
  (`templates/openformulieren-configure-*.yaml`,
  `templates/openinwoner-configure-*.yaml`) copy
  `<app>.securityContext`. Helm merges the sub-chart defaults into it, so they
  already ran with `runAsNonRoot`, `runAsUser: 1000` and
  `capabilities.drop: [ALL]`. `values.yaml` now adds `seccompProfile:
  RuntimeDefault`, for those Jobs and per container in the app pods.
- The `generate-sql` and `ensure-podiumd-admin-user` containers of
  `keycloak-ensure-podiumd-admin-user` run with `readOnlyRootFilesystem: true`;
  they only write to their `/work` and `/tmp` emptyDirs.
- The `ensure-podiumd-admin-user` container now mounts the `skip-flag` volume
  that its `check-operator-sa` init container writes. Before, it never saw
  `/skip/done` and ran `setup.sql` on every install and upgrade, recreating the
  `podiumd-admin` credential each time. Now it skips that once the
  keycloak-operator ServiceAccount is ready, as it was meant to.

## Non-root containers: runAsNonRoot where podiumd can set it

The chart now enforces `runAsNonRoot: true`, with an explicit numeric user, on
workloads whose subchart or custom resource lets podiumd set it:

| Workload | Values key | User |
| --- | --- | --- |
| Keycloak operator | `keycloak-operator.operator.securityContext` | 1000 |
| Redis operator | `redis-operator.securityContext` | 65532 |
| Redis HA pods (redis, redis-exporter, both init containers) | `redis-operator.redis-ha.podSecurityContext` | 1000 |
| Kibana | `kiss-eck.eck-kibana.podTemplate.spec.securityContext` | 1000 |
| PABC (main and `pabc-wait-for-migrations` init) | `pabc.podSecurityContext` | 1000 |
| zookeeper-operator hook Jobs (post-install/upgrade, pre-delete) | `zac.solr-operator.zookeeper-operator.hooks.securityContext` | 65534 |

Six of these containers ran as root before, because their image's default
user is root: the Redis HA `redis-exporter` and busybox init, the operator's
`init-config`, PABC's `k8s-wait-for` init, and the two zookeeper-operator hooks
(`alpine/k8s`). They only write the `/etc/redis` emptyDir and `/data`, or run
`kubectl`, so they work as a non-root user; kubectl works without a writable
`$HOME`, it then skips its discovery cache. The pods restart once with the new
settings.

Not yet covered, because the chart offers no setting: ITA (web and the
notification CronJob), the PABC migration Job, the zookeeper-operator and the
BRP mock. These need changes in the vendor charts.

An environment that sets its own values for these keys keeps them; Helm
merges maps, so one that sets only some fields gets the rest from the chart.
SSC: no action.
