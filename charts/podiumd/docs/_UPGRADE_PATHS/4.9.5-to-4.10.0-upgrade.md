# Upgrade guide: PodiumD 4.9.5 → 4.10.0

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

For environments already on **4.9.5**. The guide has three parts:

1. **The runbook** (sections A to F): what to run, in which order, and what
   to check. Written for the deploy pipeline.
2. **Component versions and changes**: the record of what moved in the chart.
3. **Reference**: the detail per topic, for when a step fails or a choice has
   to be made.

Companion documents:

- [`4.9.5-to-4.10.0-values-deltas.md`](4.9.5-to-4.10.0-values-deltas.md):
  the exact changes in a gemeente `podiumd.yml`, `services-gateway.yml` and
  `ssl-gateway.yml`.
- [`4.9.5-to-4.10.0-gemeente-specific.md`](4.9.5-to-4.10.0-gemeente-specific.md):
  findings per environment.
- [`4.9.5-to-4.10.0-operators-crds.md`](4.9.5-to-4.10.0-operators-crds.md):
  the CRD changes.
- [`misc/upstream-known-issues.md`](../misc/upstream-known-issues.md):
  upstream defects 4.10.0 still ships, with workarounds.

## Checklist

A and B are done once; C, D and E per environment.

- [ ] **[A. Once per cluster](#a-once-per-cluster-crds)**: apply the Keycloak
      Operator 26.8.1 CRDs; make sure the Solr CRDs are 0.9.0 or newer.
- [ ] **[B. Once per values repository](#b-once-per-values-repository-migrate-the-values-files)**:
      run the six migration scripts, make the hand edits, render, commit.
- [ ] **[C. Per environment, before the deploy day](#c-per-environment-before-the-deploy-day)**:
      prepare Open Forms on 3.5.10, mirror the images, check the Key Vault,
      back up, tell the people outside the pipeline, plan the window.
- [ ] **[D. The deploy run](#d-the-deploy-run)**: import the objecttypes,
      migrate the tokens, `helm upgrade --timeout 10m`, apply the gateway
      files, check.
- [ ] **[E. After the deploy](#e-after-the-deploy)**: smoke tests, the Open
      Forms reports, cleanup.
- [ ] **[F. Rollback](#f-rollback)**: only when needed.

## A. Once per cluster: CRDs

Cluster-wide, with cluster-admin rights, through the cluster's change process.
`helm upgrade` never updates CRDs. Other PodiumD namespaces on the cluster
that stay on 4.9.x keep working. Details:
[`4.9.5-to-4.10.0-operators-crds.md`](4.9.5-to-4.10.0-operators-crds.md).

1. **Keycloak Operator 26.8.1 CRDs** (additive fields):

   ```bash
   charts/podiumd/scripts/install-keycloak-operator-crds.sh --context <kube-context> --keycloak-version 26.8.1
   ```

2. **Solr CRDs from solr-operator 0.9.0 or newer.** The zac chart sets
   `containerSecurityContext` on its SolrCloud, a field older CRDs refuse
   (`field not declared in schema`); the upgrade then fails half-way. Check:

   ```bash
   kubectl --context <kube-context> get crd solrclouds.solr.apache.org \
     -o jsonpath='{.metadata.annotations.operator\.solr\.apache\.org/version}'
   ```

   It must print `v0.9.0` or newer. Otherwise (older, or no annotation)
   apply the 0.9.1 CRDs:

   ```bash
   kubectl --context <kube-context> apply --server-side --force-conflicts \
     -f https://solr.apache.org/operator/downloads/crds/v0.9.1/all.yaml
   ```

3. **redis-operator 0.27.0 CRDs**: optional, the change is description text
   only. See [redis-operator](4.9.5-to-4.10.0-operators-crds.md#redis-operator).

## B. Once per values repository: migrate the values files

Everything in this section changes files under
`applications/gemeenten/<gemeente>/<env>/`, not the cluster. Do it once,
review the diff against the
[values deltas](4.9.5-to-4.10.0-values-deltas.md), commit.

### B1. Run the six scripts

Every script keeps comments, quoting and `REP_..._REP` placeholders, shows a
unified diff with `--dry-run`, and changes nothing on a second run. Run them
from a checkout of the 4.10.0 chart; the scripts are not in the packaged chart.

```bash
pip install ruamel.yaml
S=charts/podiumd/scripts
G=<values repository>/applications/gemeenten

# 1. Preview: a unified diff per file, nothing written
for s in migrate-objecten-4.1.0.py migrate-openforms-4.0-api-groups.py migrate-openinwoner-admin-oidc.py \
         migrate-zookeeper-hooks-image-4.10.0.py migrate-eck-resources-4.10.0.py migrate-gateway-security-headers.py; do
  python3 "$S/$s" --dry-run --gemeenten-dir "$G"
done

# 2. Migrate
python3 "$S/migrate-objecten-4.1.0.py" --gemeenten-dir "$G"                # objecten + objecttypen merge: podiumd.yml and services-gateway.yml
python3 "$S/migrate-openforms-4.0-api-groups.py" --gemeenten-dir "$G"      # Open Forms 4.0: API group fields
python3 "$S/migrate-openinwoner-admin-oidc.py" --gemeenten-dir "$G"        # Open Inwoner: admin OIDC providers schema
python3 "$S/migrate-zookeeper-hooks-image-4.10.0.py" --gemeenten-dir "$G"  # ZAC: ZooKeeper hooks image alpine/k8s
python3 "$S/migrate-eck-resources-4.10.0.py" --gemeenten-dir "$G"          # KISS Elasticsearch: CPU and memory
python3 "$S/migrate-gateway-security-headers.py" --gemeenten-dir "$G"      # ssl-gateway.yml: HSTS and nosniff

# 3. Pipeline gate: exit 1 while a file still needs migrating
for s in migrate-openforms-4.0-api-groups.py migrate-openinwoner-admin-oidc.py migrate-zookeeper-hooks-image-4.10.0.py \
         migrate-eck-resources-4.10.0.py migrate-gateway-security-headers.py; do
  python3 "$S/$s" --check --gemeenten-dir "$G"
done
```

| Script | Changes | Needs a person when |
| --- | --- | --- |
| `migrate-objecten-4.1.0.py` | Removes `objecttypen:`, migrates `objecten.*` to Open Object, rewrites every consumer (`ita`, `zac`, `kiss`, `omc`, `mi`, Open Formulieren, Open Beheer) and repoints `services-gateway.yml`. | It prints `ACTION` or `CHECK` lines and exits 2. See [what the objecten script leaves to a person](#what-the-objecten-script-leaves-to-a-person). |
| `migrate-openforms-4.0-api-groups.py` | Removes the catalogue and document type fields from the Open Forms API groups. | Never. It prints the removed values; a new environment sets them in the admin. |
| `migrate-openinwoner-admin-oidc.py` | Rewrites a flat `oidc_db_config_admin_auth` item to the providers schema. | Never. |
| `migrate-zookeeper-hooks-image-4.10.0.py` | `zac.solr-operator.zookeeper-operator.hooks.image.repository`: `<registry>/.../k8s-kubectl` → `<registry>/alpine/k8s`. | A `hooks.image.tag` override with a `v` prefix: remove the tag, the chart pins 1.37.1. |
| `migrate-eck-resources-4.10.0.py` | Adds CPU and memory to a `kiss-eck.eck-elasticsearch.nodeSets` override (and to Kibana and Open Inwoner's Elasticsearch where they lack them). | Never. |
| `migrate-gateway-security-headers.py` | Adds a `ResponseHeaderModifier` (HSTS, nosniff) to every HTTPRoute rule with `backendRefs` in `ssl-gateway.yml`. SSC runs it in its own hosting repo. | Never. A weaker header the environment sets itself is kept, with a warning. |

Every script also takes single files instead of `--gemeenten-dir`. The
objecten script has `--no-gateway` to leave `services-gateway.yml` alone, and
`--objecten-image-repository <repo>` to set `objecten.image.repository`
explicitly where it leaves an override alone.

### B3. Render before the deploy day

Render the migrated values (`helm template` with the 4.10.0 chart) for every
environment. The chart refuses to render while one of these is set, and names
the key:

| The render fails while | Fix |
| --- | --- |
| any value is exactly `changeme` or `dummy` (any case), outside a section with `enabled: false` | set it. The chart defaults that trigger it are all under `zac`: `auth.secret`, `bagApi.apiKey`, `brpApi.apiKey.value`, `db.password`, `keycloak.adminClient.secret`, `kvkApi.apiKey`, `mail.smtp.username`, `mail.smtp.password`, `notificationsSecretKey`, `office_converter.username`, `office_converter.password`, `zacInternalEndpointsApiKey`, `zgwApis.secret`. |
| a value is still `openklanttoken`, `objectentoken`, `<kiss>`, `<token>`, or contains `REP_..._REP` (also inside a URL) | substitute it. The `ita.*.uuid` keys are gone; only the `type` URLs are read. |
| `objecten.settings.siteDomain` contains `example.nl` | the objecten script sets it; set it by hand on a new environment. |
| a Keycloak client secret from the values is empty while its client or component is enabled: `keycloak.config.clients.monitoring.secret`, `.datamigratie.secret`, `.zaakbrug.secret`, `kiss.settings.oidc.clientSecret`, `zac.auth.secret`, `ita.web.oidc.clientSecret`, `pabc.settings.oidc.clientSecret`, `pabc.settings.keycloakAdmin.clientSecret` | set it. |
| `zac.auth.pkceEnabled: true` | remove it; `zac.auth.enablePkce` (default `true`) replaces it. |
| `<django app>.configuration.pkceEnabled: true` | remove it, or `false`: these apps cannot send PKCE yet. |
| an `oidc-hardcoded-role-idp-mapper` grants `admin`, `create-realm` or a `realm-management`/`<realm>-realm` role without `allowAdminRoleMapping` on its identity provider | B2. A group mapper into a group with admin roles needs the setting too; the check does not see it. |
| `kiss-eck.eck-*.version`, `kiss-eck.eck-*.image` as a string, `kiss-eck.eck-*.ingress`, `kiss-eck.eck-*.extraObjects`, `kiss-eck.eck-*.spec.*` or `kiss-eck.extraObjects` | remove it. The version comes from `image.tag`; a string image moves to `image.repository`; `spec.*` keys move one level up; Kibana is routed through the platform Gateway. |
| `kiss.settings.syncJobs.medewerkers` has `useEmail: true` **and** a `baseUrl`/`objectTypeUrl` sync configuration | remove one of the two. |
| `openinwoner.nginx.config.basicAuth.enabled: true` without `users` | set htpasswd lines (`htpasswd -nB <user>`); no example user ships any more. |
| an Open Inwoner `oidc_db_config_admin_auth` item in the old flat shape | B1. |
| a create-required Job credential is empty or a `<...>` default: `openzaak.create_required_catalogi_job.client_id`/`.secret`, `objecten.configuration.secrets.create_required_objecttypen_token` | set it, or `<job>.enabled: false`. The Jobs now also run when `openzaak.enabled`/`objecten.enabled` is unset. |
| `zac.resources.limits.memory` unset (an override that drops it) and no `-Xmx` in `zac.javaOptions` | set the limit, or an `-Xmx`; without an override the chart's 2Gi limit and 75% heap apply. |
| `zac.solr.url` (an external Solr) without `zac.solr.username`/`.password` | set them. |
| `omc.enabled: true` without `omc.settings.omc.actor.id` | B2. |
| `openvtb.enabled: true` with an empty or `example.nl` `openvtb.configuration.oidcUrl` | set it. |
| `openbao.seal.static.key` is not 32 bytes | fix the placeholder substitution. |
| a Frank!Gateway inway route with `openbao-consumer-auth` while `frankgateway.networkPolicies.enabled` is false | enable the NetworkPolicies. |
| `zgw-office-addin.common.frontendUrl` without `https://` | set an https URL. |

Found while rendering SSCHostingSync: `zac.brpApi.apiKey` as a plain string

## C. Per environment, before the deploy day

In the order they need to happen. Set the target once; every command below
names it:

```bash
CTX=<kube-context-of-the-environment>   # never the current context
NS=podiumd
```

### C1. Some days before: prepare Open Forms on 3.5.10

Open Forms 4.0 refuses to upgrade until every form uses the new logic
evaluation and the legacy Catalogi URLs are migrated. This must be done on
3.5.10 (PodiumD 4.9.5) and some findings need the form designers. The two
check scripts are in `charts/podiumd/scripts` of the 4.10.0 chart and run
against the environment while it is still on 4.9.5 (they read from stdin:
`kubectl exec -i`). Detail:
[`openforms-migration-preparation.md`](../apps/openforms/openforms-migration-preparation.md)
and the 4.9.5 upgrade guide (`4.9.4-to-4.9.5-upgrade.md`).

1. Forms converted with the bulk command on PodiumD 4.9.0 to 4.9.4: open each
   one in the admin and save it once, which restores the logic rule order.
   The 4.9.5 guide has a shell query that lists them.
2. Convert the remaining forms: dry run (lists the forms and the problems,
   changes nothing), then for real. Forms with cyclic logic rules are listed
   and must be fixed by hand.

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/openformulieren -c openformulieren -- \
     python /app/src/manage.py enable_new_logic_evaluation_for_all_forms
   kubectl --context "$CTX" -n "$NS" exec deploy/openformulieren -c openformulieren -- \
     python /app/src/manage.py enable_new_logic_evaluation_for_all_forms --no-dry-run
   ```

3. Check the registration options, read-only. One line per problem
   (`V1_KEYS` with the keys to remove, `NO_SERVICE` with the URL, `INVALID`)
   and a `SUMMARY` line:

   ```bash
   kubectl --context "$CTX" -n "$NS" exec -i deploy/openformulieren -c openformulieren -- \
     python /app/src/manage.py shell < charts/podiumd/scripts/openforms-check-registration-options.py
   ```

   - `V1_KEYS`: remove them with the fix script. Without `APPLY=1` it is a
     dry run; with it, keep the output (`BACKUP_JSON` holds the original
     options):

     ```bash
     kubectl --context "$CTX" -n "$NS" exec -i deploy/openformulieren -c openformulieren -- \
       python /app/src/manage.py shell < charts/podiumd/scripts/openforms-fix-registration-options.py
     kubectl --context "$CTX" -n "$NS" exec -i deploy/openformulieren -c openformulieren -- \
       env APPLY=1 python /app/src/manage.py shell < charts/podiumd/scripts/openforms-fix-registration-options.py \
       | tee "openforms-registration-options-$NS.log"
     ```

   - `NO_SERVICE`: a registration or file component points at a Catalogi
     without a configured service (another environment's URL, for example):
     correct or clear it in the form, or delete the form if it is in the
     trash. `INVALID`: fix the registration in the form designer.
4. Repeat step 3 until `SUMMARY` reports 0 problems. Then migrate the
   Catalogi URLs: dry run until it reports no problems, then for real.

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/openformulieren -c openformulieren -- \
     python /app/src/manage.py migrate_catalogi_api_urls
   kubectl --context "$CTX" -n "$NS" exec deploy/openformulieren -c openformulieren -- \
     python /app/src/manage.py migrate_catalogi_api_urls --no-dry-run
   ```

5. Give the form designers the output of
   `python /app/bin/report_logic_with_deprecated_clear_on_hide_behavior.py`
   (logic evaluates differently in 4.0, see
   [other Open Forms 4.0 changes](#other-open-forms-40-changes)).
6. Size the data migration. Open Forms runs `migrate` at startup, and the
   startup probe allows about 315 seconds; from about 260,000 attachment rows
   the kubelet restarts the pod mid-migration and it loops. Count them:

   ```sql
   select count(*) from submissions_submissionfileattachment;
   ```

   Above that, raise `openformulieren.startupProbe.failureThreshold` for this
   deploy: allow `count / 1000 × 1.2` seconds plus a margin, in steps of
   10 seconds (500,000 rows: 600 s, so `failureThreshold: 75`).

### C2. Mirror the images

The registry the environment pulls from must hold everything in
[`images-4.10.0.yaml`](../images/images-4.10.0.yaml), by digest. New or
renamed this release, so a mirror run by old names misses them:

- `maykinmedia/open-object` 4.3.0 (replaces `maykinmedia/objects-api` and
  `objecttypes-api`);
- `alpine/k8s` 1.37.1 (replaces `lachlanevenson/k8s-kubectl` for the
  ZooKeeper hooks; the redis-ha Jobs used it already);
- `elasticsearch` and `kibana` 8.19.23;
- only when enabled: `maykinmedia/open-vtb` 0.2.0, `worthnl/notifynl-omc`
  2.3.1 (tag-pinned; the manifest records its digest).

### C3. Key Vault: Open Zaak's objecten token must be unique

**SSC blocker.** The objecten script adds a tokenauth item `openzaak` with the
secret behind `REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` (Key Vault
`objecten-credentials-objecttypen-token`, Open Zaak's existing token). Open
Object refuses two tokenauth items with the same token: the objecten config
Job then fails and the deploy does not complete. The script cannot see secret
values. On two of the eight ExternalsPodiumD environments the value equals the
`esuite` token; expect the same in SSC environments. Compare the hashes
(values are never printed):

```bash
KV=kv-<environment>-<gemeente>
for s in objecten-credentials-objecttypen-token \
         objecten-credentials-formulier-token objecten-credentials-zaak-token \
         objecten-credentials-esuite-token objecten-credentials-contact-token \
         objecten-credentials-contact-esuite-token objecten-credentials-ita-token \
         objecten-credentials-omc-token objecten-credentials-integratieteam-token \
         objecten-credentials-openarchiefbeheer-token objecten-openbeheer-token; do
  h=$(az keyvault secret show --vault-name "$KV" --name "$s" --query value -o tsv 2>/dev/null \
      | tr -d '\n' | shasum -a 256 | cut -c1-12)
  echo "$h $s"
done | sort
```

- Two lines with the same hash, one of them
  `objecten-credentials-objecttypen-token`: give **that** secret a new random
  value (`openssl rand -hex 20`). After the migration only Open Zaak sends it,
  and the deploy writes it to both ends. Never change the other token of the
  pair: its clients (often the eSuite) are outside our reach.
- `e3b0c44298fc` is the hash of an empty value: the secret does not exist in
  this Key Vault. Ignore it unless the values use the placeholder.
- Tokens written in the values instead of Key Vault, and items created by
  hand in the objecten admin, count too.

### C4. Objecttypen tokens whose clients must switch

After the merge an identifier has one token, and the objecten token wins.
Clients outside the values that send the objecttypen token of such an
identifier get `403` after the upgrade: external parties, and services made by
hand in an admin (Open Formulieren, Open Inwoner, Open Beheer). Find the
identifiers with the dry run; every `objecten-wins` line is one:

```bash
charts/podiumd/scripts/migrate-objecttypen-tokens.sh --context "$CTX" --namespace "$NS"
```

Find their clients (the objecten script's report for the values, the admin
of each component, the contact person of an external token) and tell them
which token to use from the moment of the upgrade. Detail:
[one token per identifier](#one-token-per-identifier).

### C5. Back up

The `objecten`, `objecttypen` and `openformulieren` databases. Open Forms 4.0
runs one-way data migrations; the backup is the only way back.

### C6. Checks

- **ZAC zaaktypen need a roltype `Behandelaar`** (omschrijving exactly
  `Behandelaar`, omschrijving generiek `behandelaar`). Since ZAC 5.6 a
  zaaktype without it still gets its zaak from a productaanvraag, but ZAC
  cannot assign it or start its CMMN process, so no ontvangstbevestiging is
  sent. ZAC's health check lists such zaaktypen; give them a new version. See
  [Behandelaar roltype](#behandelaar-roltype).
- **ZAC memory.** The ZAC pod now requests and limits 2Gi (was a 1Gi request,
  no limit): nodes need 2Gi free. An `-Xmx` in `zac.javaOptions` still pins
  the heap; remove it to use the 75% default.
- **PABC names are case-sensitive** from 2.1.0: functional role names must
  match the Keycloak realm roles ZAC sends exactly, entity type ids the
  zaaktype omschrijvingen. On an environment curated in the PABC UI, compare
  first: a difference in case only silently stops granting the application
  roles. **The seed job reruns** on this upgrade and replaces all PABC
  content: keep `pabc.seedJob.enabled` off where PABC was edited by hand. See
  [PABC 2.1.0](#reference-pabc-210).
- **PostgreSQL must offer TLS**: the Django apps and OpenBao now connect with
  `sslmode: require`. Azure Database for PostgreSQL does. For a server
  without TLS set `<component>.settings.database.sslmode: prefer` (OpenBao:
  `openbao.database.sslmode`).
- **Anything that calls ZAC's Solr API** (a script that reloads the `zac`
  collection, a health check) gets `401` from now on unless it sends
  `-u admin:<password>`, the password from the Secret
  `zac-solr-solrcloud-security-bootstrap` (key `admin`). The SSC pipelines do
  not call it.
- **Keycloak mail**: 26.8 no longer falls back to plaintext when the mail
  server offers no STARTTLS (`keycloak.config.smtp.starttls`, default
  `"true"`); password reset and verify mail then fail. Check the realm's
  mail server, or set `"false"` for a server without TLS.

### C7. Tell the people outside the pipeline

- **Form designers**: Open Forms 4.0 evaluates logic differently (a component
  hidden with "clear on hide" loses its value, values of future steps are not
  available, DMN actions wait for all inputs, "trigger from step" is gone);
  the form builder is new; file-upload registration options moved to the
  Variables tab; ZGW registration uses public references by default; custom
  themes need updating (markup and design tokens); exports from before 4.0
  may not import cleanly.
- **SDK embedders**: `/static/sdk/open-forms-sdk.js` and
  `/static/sdk/bundles/open-forms-sdk.js` stop working; load the `.mjs` file
  with an ESM `import`; `window.OpenForms` is gone.
- **DigiD/eHerkenning brokers configured outside this chart**: the callbacks
  `/digid-oidc/`, `/digid-machtigen-oidc/`, `/eherkenning-oidc/`,
  `/eherkenning-bewindvoering-oidc/` and `/org-oidc/` are removed; every OIDC
  provider must redirect to `https://<openforms-domain>/auth/oidc/callback/`.
  The chart's Keycloak client `openformulieren` allows `<oidcUrl>/*` already.
- **External parties on the Objecttypen API**: the token to use from the
  upgrade on (C4).
- **Objecten admins**: log in on the objecten hostname. The old objecttypen
  hostname serves the API only; an admin login there fails with
  `Invalid parameter: redirect_uri`.

### C8. Plan the window

- **The upgrade empties Redis.** redis-operator v0.27.0 renames the
  append-only file, every `redis-ha` pod starts empty and the replicas copy
  the empty master. Caches refill; employees are logged in again through
  Keycloak without a prompt; residents logged in to Open Formulieren or Open
  Inwoner with DigiD/eHerkenning lose that login and a form in progress may
  have to be restarted. **Celery tasks still waiting in a queue are lost**
  (notifications, Open Forms registrations not yet processed): deploy outside
  peak hours, when the queues are empty. For each component's broker database
  (the list is in `values.yaml` above `redis-operator`) this must print `0`:

  ```bash
  kubectl --context "$CTX" -n "$NS" exec redis-ha-0 -c redis-ha -- \
    sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} -n <db> LLEN celery'
  ```

- **Keycloak 26.7 → 26.8 recreates the Keycloak pods**: one to two minutes
  without logins; ZAC users may have to log in again.
- **Pods that restart once**: Solr (rolled one at a time), `redis-ha`, KISS
  Elasticsearch (one at a time) and Kibana, the Keycloak and Redis operators,
  PABC, ZAC and every pod whose security context changed.
- **`helm upgrade` takes longer**: four configuration Jobs are now
  post-upgrade hooks that Helm waits for (D4).

## D. The deploy run

Per environment, in this order. `CTX` and `NS` as set in C.

### D1. Import the objecttypes into objecten

Directly before the `helm upgrade`: objecttypes changed after the import are
not copied. The import upserts on `uuid`, so it is safe to run again. Nothing
has switched yet; on failure stop the run, the environment is untouched.
`SLUG` is the slug of objecten's `zgw_consumers` service for objecttypen:
`objecttypen-api` in every SSC environment; the 4.9.x values have it under
`objecten.configuration.data` → `objecttypes.items[].service_identifier`.

```bash
SLUG=objecttypen-api
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py import_objecttypes "$SLUG"
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c "from objects.core.models import ObjectType as T; bad=[str(u) for u in T.objects.exclude(is_imported=True).values_list('uuid', flat=True)]; print('OK' if not bad else 'NOT IMPORTED: ' + ', '.join(bad)); raise SystemExit(1 if bad else 0)"
```

The second command must print `OK`. A wrong slug fails with
`Service '<slug>' does not exist`, an unreachable objecttypen with a
connection error; both before anything is written. Without `pods/exec`
rights: [the one-time Job variant](#importing-the-objecttypes-without-exec-rights).
`NOT IMPORTED` with a UUID:
[an objecttype that no longer exists in objecttypen](#an-objecttype-that-no-longer-exists-in-objecttypen).

### D2. Migrate the objecttypen tokens

Directly after D1, while objecttypen and objecten both still run. The script
copies tokens that exist only in the objecttypen database into objecten
(values are piped between the pods, never printed). It needs `pods/exec`
rights. Stop the run on an `error` line.

```bash
charts/podiumd/scripts/migrate-objecttypen-tokens.sh --context "$CTX" --namespace "$NS"           # dry-run
charts/podiumd/scripts/migrate-objecttypen-tokens.sh --context "$CTX" --namespace "$NS" --apply   # create the missing tokens
```

The output legend is under [the token script](#the-token-script).

### D3. Remove a leftover Job

4.10.0 changes the pod template of `create-required-objecttypen-job`, which
Kubernetes refuses on an existing Job. A finished Job removes itself after
10 minutes, so it is usually gone already:

```bash
kubectl --context "$CTX" -n "$NS" delete job create-required-objecttypen-job --ignore-not-found
```

### D4. `helm upgrade`

Run the deploy with the migrated `podiumd.yml` and `--timeout 10m` or more on
the `helm upgrade`. Open Archiefbeheer, Open Notificaties, Open Formulieren and
Open Inwoner now run their configuration Job as a `post-install,post-upgrade`
hook: Helm waits for each Job, and one that fails fails the release. podiumd
keeps `backoffLimit: 6` and `restartPolicy: OnFailure`, so a Keycloak or
realm import that is not ready yet is retried, and a Job that keeps failing
takes about 7 minutes before it gives up, longer than Helm's default timeout
of 5m, which applies per hook. `helm uninstall` leaves the hook Jobs; the
next install or upgrade replaces them.

### D5. Apply the gateway files

`services-gateway.yml` (the objecten script points `objecttypen-nginx` at
`objecten.<ns>.svc.cluster.local`) and `ssl-gateway.yml` (B1, B2), with
`kubectl apply` as usual; no restart is needed. The old objecttypen hostname
keeps serving the Objecttypen API between D4 and D5 (`objecttypenCompatService`,
on by default), so this can also be a later run. After the repoint, check that
the gateway picked it up: with NGINX Gateway Fabric 2.6.5 the data plane kept
the old upstream until the controller was restarted:

```bash
kubectl --context "$CTX" -n ingress-basic rollout restart deploy/nginx-gateway-fabric
```

### D6. Check the import

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py check_for_external_objecttypes
```

It must print `OK`.

### D7. OpenBao environments only

Before every deploy `charts/podiumd/scripts/openbao-keycloak-setup.py`, after
every deploy `charts/podiumd/scripts/openbao-activate.sh`, from a checkout of
the deployed chart version. See
[OpenBao and Frank!Gateway](#openbao-and-frankgateway).

## F. Rollback

- **Open Forms**: restore the `openformulieren` database backup. Going back
  to 3.5.x after the 4.0 migrations is not documented as possible.
- **Objecten**: read the objecten log first
  (`kubectl --context "$CTX" -n "$NS" logs deploy/objecten --previous`). A
  startup error that names objecttype UUIDs means objecttypes were not
  imported; anything else (image pull, database, memory) is a different
  problem. Then:
  1. `helm rollback podiumd <last 4.9.x revision>`: brings back the separate
     objecttypen deployment; the `objecttypen` Service exists the whole time
     and is patched back to the objecttypen chart's selector. Restore the
     objecten database from the backup if the 4.10.0 migrations already ran.
  2. A gateway route already repointed to objecten: point it back. One still
     on the ExternalName to `objecttypen.<ns>.svc` needs no change.
  3. Tokens copied by D2 can stay: in objecten 3.6 they have no rights.
     Clients that switched to the objecten token switch back.
  4. An unimported objecttype: run `import_objecttypes` again if it still
     exists in objecttypen. If it was deleted there, remove it from objecten
     (see [an objecttype that no longer exists in objecttypen](#an-objecttype-that-no-longer-exists-in-objecttypen))
     and check with the `is_imported` query from D1; objecten 3.6.x has no

## Changes that need no action

One line each. The chart handles them; an environment that sets the key
itself keeps its own value.

- **Keycloak client secrets of disabled components are generated** (the kiss,
  zac, zac-admin, ita and pabc clients, and an empty or placeholder
  `<component>.configuration.secrets.keycloak_client_secret`), kept in
  `keycloak-podiumd-realm-secrets`. The realm import runs once more on the
  first 4.10.0 deploy.
- **The realm import no longer manages client scopes**; the new
  `keycloak-repair-client-scopes` Job runs on every deploy, gives a client
  without default scopes the realm's defaults and removes `offline_access`.
  See [keycloak-default-client-scopes.md](../apps/keycloak/keycloak-default-client-scopes.md).
- **Keycloak update strategy `Auto`** (IN-3176): patch releases and registry
  changes roll without downtime; a minor or major upgrade, such as this one,
  still recreates the pods. Opt-in `keycloak.podDisruptionBudget.enabled: true`
  renders a budget with `maxUnavailable: 1`.
- **The Keycloak operator's ServiceMonitor Role is rendered by default**. A
  cluster without the `servicemonitors.monitoring.coreos.com` CRD can set
  `keycloak-operator.enableServiceMonitor: false`; with the CRD present the
  Role is needed, or the Keycloak CR stays `InProgress`.
- **Celery result backend** is now set for Open Zaak (Redis db 5) and Open
  Inwoner (db 12); the Open Archiefbeheer and Open Formulieren charts read
  `resultBackend` instead of `resultBackendl`. Only an environment that sets
  `settings.celery.resultBackendl` for one of these four itself must rename
  it (none in SSCHostingSync does); the openklant chart keeps `resultBackendl`.
- **NetworkPolicies stay opt-in** (`networkPolicies.enabled`, default
  `false`). With `networkPolicies.namespaceIsolation` on, Keycloak's
  operator-made policy no longer opens 8080 and 9000 to the whole cluster;
  an in-cluster caller from another namespace goes in
  `keycloak.networkPolicy.extraFrom` or `namespaceIsolation.extraNamespaces`.
- **Namespace portability**: Redis, `allowedHosts`, ClamAV and Kibana
  references use bare service names and the `.svc.cluster.local` wildcard.
  Nothing changes in the `podiumd` namespace; another namespace:
  [namespace portability](#namespace-portability).
- **Resource requests and limits**: Referentielijsten (`100m`/`320Mi`) and
  Open Beheer (`100m`/`256Mi`) get requests; KISS Elasticsearch
  (`250m`/`2000m`), Kibana (`100m`/`1000m`) and the Redis exporter
  (`10m`/`100m`, `32Mi`/`64Mi`) get CPU; ZAC's nginx, OPA (128Mi), init
  container (256Mi) and office converter (1Gi) get memory limits. An
  override of `kiss-eck.eck-elasticsearch.nodeSets` replaces the list, which
  is what B1's `migrate-eck-resources-4.10.0.py` is for.
- **Redis HA failover safeguards** (IN-2961): topology spread, a
  PodDisruptionBudget and a master readiness check, all on by default. The
  `redis-ha` pods restart once; each master change restarts every Celery
  worker once. See [Redis](#reference-redis).
- **ZAC**: Solr's readiness and liveness probes are now `curl -f` against
  `/solr/admin/info/health`, so an unhealthy node leaves the Service; Solr
  and its init containers run as uid 8983; the zac chart's `runAsGroup` is
  cancelled so the 5.9.1 containers keep their users.
- **PKCE on by default for ZAC**: `zac.auth.enablePkce` (default `true`) sets
  `AUTH_ENABLE_PKCE` in ZAC and `S256` on the `zac` client. `false` turns both
  off; no step in the Keycloak console.
- **ClamAV configuration Jobs on by default** for Open Formulieren and Open
  Inwoner, while ClamAV is deployed or `clamavHost` points elsewhere. All
  SSCHostingSync environments with ClamAV already set them; the
  ExternalsPodiumD environments get the scan switched on. Opt out with
  `<app>.clamavConfigJob.enabled: false`.
- **Security contexts**: seccomp `RuntimeDefault` on the Open Formulieren and
  Open Inwoner configure Jobs and app containers; `runAsNonRoot` with a
  numeric user on the Keycloak and Redis operators, the `redis-ha` pods,
  Kibana, PABC and the ZooKeeper hook Jobs; `readOnlyRootFilesystem` on the
  `keycloak-ensure-podiumd-admin-user` containers, which now also skip
  `setup.sql` once the operator ServiceAccount is ready. The pods restart once.
- **Open Archiefbeheer**: a `sitecustomize.py` from the ConfigMap
  `openarchiefbeheer-patches` works around
  [open-archiefbeheer#1103](https://github.com/maykinmedia/open-archiefbeheer/issues/1103)
  (a review response processed before its transaction commits). Only an
  environment that sets `openarchiefbeheer.extraEnvVars`, `extraVolumes` or
  `extraVolumeMounts` itself must keep the chart's entries (Helm replaces
  lists); none in SSCHostingSync does.
- **Open Forms environment variables no longer read**:
  `USE_LEGACY_OIDC_ENDPOINTS`, `USE_LEGACY_DIGID_EH_OIDC_ENDPOINTS`,
  `USE_LEGACY_ORG_OIDC_ENDPOINTS`, `ELASTIC_APM_SERVER_URL`,
  `ELASTIC_APM_SECRET_TOKEN` and
  `PERSIST_USER_DEFINED_VARIABLES_UPON_STEP_COMPLETION`.
- **zgw-office-addin 0.12.0** refuses to start on a `frontendUrl` without
  `https://`, a `TO_REPLACE_*` placeholder or the dummy MSAL client id; every
  SSC environment is fine unless a `REP_..._REP` placeholder is not
  substituted. The manifest version gets a `1.` prefix.
- **KISS 3.2.0** adds an optional PABC integration
  (`kiss.settings.pabc.baseUrl` and `.apiKey`), off while empty.
- **OpenBao 2.7.1**: the PebbleDB change concerns the standalone backend
  only (PodiumD runs HA on PostgreSQL); the removed auth engines are not used;
  the break-glass endpoints still work; a new liveness probe restarts a
  standby that sealed itself after a takeover.
- **Open Inwoner KvK API settings** can now come from the values
  (`openinwoner.kvk.*`); nothing changes until `apiRoot` is set. See
  [KvK API configuration](#open-inwoner-kvk-api-configuration).
- **Observability overlay**: `values-enable-observability.yaml` also turns
  on OpenBao's metrics, which restarts the OpenBao pods; with the Shamir seal
  they come back sealed (run `bao operator unseal` on each), with the static
  seal they unseal themselves.

## Reference: Objecten 4 (Open Object)

Background and design decisions:
[`openobject-migration.md`](../apps/objecten/openobject-migration.md).

### One token per identifier

Before 4.10.0, objecten and objecttypen each had their own token table, and
many environments have a token with the same identifier in both (`zaak`,
`omc`, `openbeheer-token`, `ibz`) but a different value. From 4.10.0 one
application serves both APIs with one token table: an identifier has one
value, and **the objecten value wins**.

- A client that called the Objecttypen API with the objecttypen token of such
  an identifier must send the objecten token instead, or it gets `403`.
- Clients in the gemeente values are rewritten by the objecten script, which
  reports each identifier it changed.
- Clients outside the values are not: external parties, and services made by
  hand in an admin. C4 finds the identifiers; the clients switch at the
  moment of the upgrade.
- Tokens that exist only in objecttypen keep working: the script merges the
  ones in the values, D2 copies the ones only in the database.

Example, ontw-dim1:

| objecttypen token | Used by | Same identifier in objecten | Action |
| --- | --- | --- | --- |
| `objecten` | objecten itself, Open Formulieren | no | merged by the values migration; no client change |
| `openbeheer-token` | Open Beheer | yes, other value | Open Beheer uses the objecten value for both services |
| `ibz` | external party | yes, other value | the external party switches to the objecten value |
| `zaak`, `omc` | no client found | yes, other value | nothing; the objecten value stays |
| `integratieteam` | both APIs | yes, same value | nothing |

### What the objecten script changes

| Area | Change |
| --- | --- |
| `objecttypen:` | Block removed. |
| `objecten.settings.siteDomain` | New, required: the objecten domain (was `sites_config` in `configuration.data`). |
| `objecten.settings.allowedHosts` | The old public objecttypen hostname is added. |
| `objecten.configuration.secrets` | objecttypen's secrets are moved over; `create_required_objecttypen_token` is set to the token of objecten's existing superuser tokenauth item. |
| `objecten.create_required_objecttypen_job` | Moved from `objecttypen`. |
| `objecten.image.repository` | `<registry>/maykinmedia/objects-api`, or the old mirror `<registry>/objecten`, → `<registry>/maykinmedia/open-object`. Other overrides are left alone and reported. |
| `objecten.configuration.data` | Removed: `objecttypes.items[].service_identifier`, the `objecttypen-api` service, `sites_config`, `tokenauth.items[].fields`/`use_fields`. objecttypen's tokenauth items are merged in (one token per identifier, above). A tokenauth item `openzaak` is added with Open Zaak's existing token (`read_only` on the `zaak` item's objecttype). |
| Consumer tokens | A consumer value that carries the objecttypen token of an identifier that keeps the objecten token becomes the objecten token; a `value_from: {env: ...}` token is resolved through the component's `configuration.secrets`. A token it cannot resolve is reported. |
| Consumer URLs | The objecttypen public hostname and `objecttypen.<ns>.svc.cluster.local` become objecten's: `ita.*.type`, `zac.objecttypenApi` (removed), kiss `objectTypeUrl`s, `omc.settings.zgw.endpoint.objectTypen`, Open Formulieren's and Open Beheer's objecttypen service. |

| `mi.targets` | Entries for component `objecttypen` removed. |
| Open Formulieren, Open Beheer | The objecttypen and objecten services then share one `api_root`, which `zgw_consumers` refuses: the objecttypen service is removed and every `*_service_identifier` reference is repointed to the objecten service. | `services-gateway.yml` | The `objecttypen-nginx` ExternalName Service points at `objecten.<ns>.svc.cluster.local`. Only when `podiumd.yml` has an objecten block: a stub environment (deployed from another repo) keeps its gateway. `--no-gateway` skips it. |

### What the objecten script leaves to a person

The summary counts the files that "need action", lists them again after the
summary, and the script exits with code 2. Fix the values, run it again.

| Line | Meaning | What to do |
| --- | --- | --- |
| `ACTION <component>: ... token ...` | After the service merge the kept service's token differs from the removed one and the script knows no switch for it. The 2026-10-21 dry run leaves 5 (Open Formulieren with the `esuite` token, or already on `formulier`; one Open Beheer). | Make sure the kept service sends an objecten token that works for both APIs with the rights the component needs: Open Formulieren `read_and_write` on the objecttype it registers to (`formulier`); Open Beheer a superuser token (`openbeheer-token`). | `ACTION`: an existing `openzaak` item with another token, or no `zaak` item with objecttype permissions | The `openzaak` item cannot be added. | Add it by hand, `read_only` on the objecttypes Open Zaak must validate. |
| `CHECK openzaak: ... sends ZAC's 'zaak' token` | Open Zaak's `objecten-api` service sends the `zaak` token (an earlier version of this script did that; on ExternalsPodiumD info it was a choice). | Set the `header_value` back to `Token REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP` and run the script again; it then adds the `openzaak` item. | `CHECK`: a `configuration.data` that does not parse | Not merged. ExternalsPodiumD ontw-dimp: Open Beheer's has a duplicate `oidc_provider_identifier` key. | Fix the YAML, run the script again. |

| an image repository it does not recognise | Reported, not changed. | `--objecten-image-repository`, or edit it. |

The token is the `header_value` of the kept service, either as
`Token REP_..._REP` or as `Token {value_from: {env: <key>}}`; in the second

row stays in the component's database, unused. If a configuration Job already
failed on this during a deploy: fix the values and deploy again, or apply the

next retry passes, then deploy the values afterwards.

Open Beheer: its objecttypen service (`objecttypen-service`, named by

other consumer; none of the SSC environments has an Open Beheer objecttypen

`REP_OBJECTTYPEN_OPENBEHEER_TOKEN_REP` for the objecttypen token,

### Importing the objecttypes without exec rights

A one-time Job instead of D1's `kubectl exec`. It uses the same image and the
same `objecten` Secret and ConfigMap as the running Deployment:

```bash
SLUG=objecttypen-api
IMAGE=$(kubectl --context "$CTX" -n "$NS" get deploy objecten -o jsonpath='{.spec.template.spec.containers[?(@.name=="objecten")].image}')
kubectl --context "$CTX" -n "$NS" delete job objecten-import-objecttypes --ignore-not-found
kubectl --context "$CTX" -n "$NS" apply -f - <<EOF
apiVersion: batch/v1
kind: Job
metadata:
  name: objecten-import-objecttypes
spec:
  backoffLimit: 0
  ttlSecondsAfterFinished: 86400
  template:
    spec:
      restartPolicy: Never
      securityContext:
        runAsUser: 1000
        runAsGroup: 1000
        runAsNonRoot: true
      containers:
        - name: import-objecttypes
          image: ${IMAGE}
          command: ["/bin/sh", "-c"]
          args:
            - |
              python /app/src/manage.py import_objecttypes ${SLUG} &&
              python /app/src/manage.py shell -c "from objects.core.models import ObjectType as T; bad=[str(u) for u in T.objects.exclude(is_imported=True).values_list('uuid', flat=True)]; print('OK' if not bad else 'NOT IMPORTED: ' + ', '.join(bad)); raise SystemExit(1 if bad else 0)"
          envFrom:
            - secretRef:
                name: objecten
            - configMapRef:
                name: objecten
          resources:
            requests:
              cpu: 100m
              memory: 256Mi
            limits:
              memory: 512Mi
EOF
kubectl --context "$CTX" -n "$NS" wait --for=condition=complete job/objecten-import-objecttypes --timeout=10m \
  || { kubectl --context "$CTX" -n "$NS" logs job/objecten-import-objecttypes; exit 1; }
kubectl --context "$CTX" -n "$NS" logs job/objecten-import-objecttypes
```

Add a `nodeSelector` if the environment pins workloads to a node pool (SSC:
`kubernetes.azure.com/mode: user`). To find the slug on an environment whose
values do not show it (`orc` is the Objecttypen API type):

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
  "from zgw_consumers.models import Service; [print(s.slug, s.api_type, s.api_root) for s in Service.objects.all()]"
```

### An objecttype that no longer exists in objecttypen

`import_objecttypes` copies only what objecttypen still has. An objecttype row
in objecten that points at objecttypen while the objecttype was deleted there
cannot be imported, and D1's check lists its UUID (ontw-dim1:
`Productaanvraag-eSuite`, 0 objects). Open Object 4 refuses to start with it.

1. Check that it is gone upstream and unused:

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/objecttypen -c objecttypen -- python /app/src/manage.py shell -c \
     "from objecttypes.core.models import ObjectType as T; print(T.objects.filter(uuid='<uuid>').exists())"
   kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
     "from objects.core.models import ObjectType as T; t=T.objects.get(uuid='<uuid>'); print(t._name, t.object_set.count())"
   ```

   It must print `False`, and the objecten row must have 0 objects. With
   objects, stop: restore the objecttype in objecttypen (same UUID) and
   import again.
2. Delete the row in objecten (this also deletes the token permissions on
   it):

   ```bash
   kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
     "from objects.core.models import ObjectType as T; print(T.objects.get(uuid='<uuid>').delete())"
   ```

3. Run D1's check again; it must print `OK`.

If `objecten.configuration.data` still lists that UUID under `objecttypes`
(for example `esuite_productaanvraag_uuid`), the 4.10.0 configuration Job
creates it again as a local objecttype without versions, with
`is_imported=False`, so D6 fails on it. Either remove the UUID (and its
`permissions` entries) from the configuration before the deploy, or mark it
imported after the deploy:

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py shell -c \
  "from objects.core.models import ObjectType as T; print(T.objects.filter(uuid='<uuid>', is_imported=False).update(is_imported=True))"
kubectl --context "$CTX" -n "$NS" exec deploy/objecten -c objecten -- python /app/src/manage.py check_for_external_objecttypes
```

### The token script

`migrate-objecttypen-tokens.sh` (D2) reads the identifiers of objecttypen's
configured tokens from the ConfigMap of its configuration Job
(`objecttypen-configuration`, key `configuration.yaml`; `--configmap` if it is
named differently) and prints one line per token in the objecttypen database,
then a summary:

```text
Mode: dry-run (nothing written; --apply creates the tokens)
objecttypen identifier           sha256       action              objecten identifier
ibz                              d24861a81d2c objecten-wins       ibz (clients must switch to this objecten token)
integratieteam                   b5623e70fb01 exists-same-token   integratieteam
objecten                         104afcf76e6d skipped             - (in objecttypen configuration: merged by the values migration)
omc                              89a584eeda19 objecten-wins       omc (clients must switch to this objecten token)
openbeheer-token                 39d8c023a867 objecten-wins       openbeheer-token (clients must switch to this objecten token)
zaak                             9db4a7c06070 objecten-wins       zaak (clients must switch to this objecten token)
Summary: exists-same-token 1, objecten-wins 4, skipped 1
```

| Action | Meaning |
| --- | --- |
| `exists-same-token` | objecten already has this token. Nothing to do. |
| `objecten-wins` | objecten has this identifier with another token. Nothing is created; the clients of the objecttypen token switch (C4). |
| `skipped` | The identifier is in objecttypen's configuration and not yet in objecten: the values migration merges it and the 4.10.0 configuration Job creates it. |
| `created` | Created in objecten with the same identifier. |
| `error` | Cannot be created (an invalid field). Nothing is written; fix it by hand. |

It copies the token, identifier, `contact_person`, `email`, `organization`,
`application` and `administration`, and no rights: in objecten 3.6 a copied
token can do nothing, in Open Object 4 the objecttypes endpoints need only a
valid token (as in objecttypen 3.4), the objects endpoints check objecttype
permissions. Nothing in objecttypen is changed; running it again creates
nothing. To manage a copied token in the values later, add it to
`objecten.configuration.data` `tokenauth` **under the identifier the script
printed**; under another identifier the configuration Job fails on the
duplicate token.

Keep it. Objects, Open Formulieren and the ZAC, ITA, KISS and OMC

### Cookies: SameSite=Lax

`openformulieren.settings.cookieSamesite: None` (B2). In the SSCHostingSync
values every prod environment serves Open Forms on its own gemeente domain;
how DigiD/eHerkenning is connected lives in the Open Forms admin, so check
with the gemeente.

## Reference: Keycloak 26.8

### Behaviour changes

Upstream: <https://www.keycloak.org/docs/latest/upgrading/>.

- **Identity provider mappers no longer grant admin roles by default**
  (CVE-2026-12388, IN-3203). A mapper that grants an admin role, or adds users
  to a group that carries admin roles, is refused when created or updated and
  at broker login, unless the identity provider's config has
  `allowAdminRoleMapping: "true"`; the default is off, also for existing
  identity providers. Without it `keycloak-import-master-realm` fails with
  `Create method returned status Forbidden (Code: 403)`, nothing after the
  mapper is imported, and users who log in through the identity provider get
  no admin role. The chart does not set it itself: granting admin roles
  through an external identity provider stays an explicit choice per
  environment (B2). The chart's podiumd realm group `/administrators` carries
  no admin roles, so a mapper into it keeps working.
- **SMTP StartTLS is enforced** (CVE-2026-107121): C6.
- **Backchannel logout tokens from an external OIDC identity provider must be
  signed**, also with `Validate Signatures` off: such an identity provider
  needs its JWKS URL or public key configured.
- **An identity provider's client secret must be entered again** when its
  token URL changes (CVE-2026-15943).
- **Disabled clients are no longer in the token audience** (`aud`), and their
  roles not in `resource_access`.
- **Brute-force login failures are stored in the database**, so a lock-out
  survives a restart; slightly more database load.
- **Refresh tokens expire with the user session idle timeout**; clients
  refresh earlier.
- **Client secret rotation and the SCIM API are enabled by default**; PodiumD
  uses neither.
- **Database migration**: a column and rebuilt indexes on
  `OFFLINE_USER_SESSION` at the first start; above 300000 rows the indexes
  are built in the background.
- **Deprecated:** the client switch *Full Scope Allowed*, on for PodiumD's
  clients, logs a warning per client. No action yet.

### Rolling updates with update strategy Auto

`keycloak.update.strategy: Auto` (IN-3176). The operator's default,
`RecreateOnImageChange`, stops every Keycloak pod on any image change; with
`Auto` the operator first runs an update Job that checks whether the old and
the new version can run side by side, and rolls the pods one at a time when
they can: the same version from another registry, and a patch release in the
same major.minor. A minor or major upgrade is still recreated (one to two
minutes without logins; ZAC refreshes its token every minute, so its users may
lose their session). An environment that wants the old behaviour sets
`RecreateOnImageChange`. The optional `keycloak.podDisruptionBudget.enabled:
true` renders a budget `keycloak` with `maxUnavailable: 1`, so a node drain
evicts one Keycloak pod at a time.

### Environments without Prometheus

4.10.0 renders the Keycloak operator's ServiceMonitor RBAC by default: a
`Role` and `RoleBinding` that let the operator and the `keycloak`
ServiceAccount manage `servicemonitors` in the release namespace. An
environment without the `servicemonitors.monitoring.coreos.com` CRD
(`kubectl get crd servicemonitors.monitoring.coreos.com` answers `NotFound`)
can turn it off:

```yaml
keycloak-operator:
  enableServiceMonitor: false
```

With the CRD installed the Role is needed: the operator then manages a
ServiceMonitor for Keycloak, and without the Role the Keycloak CR stays
`InProgress`.

### Fresh installs and helm template

- The ServiceMonitor Role is rendered under `helm template` too (above).
- Set every enabled component's client secret
  (`<component>.configuration.secrets.keycloak_client_secret`, or
  `configuration.oidcSecret`): `helm template` cannot read a generated one
  back from `keycloak-podiumd-realm-secrets`, so it changes on every render
  and the realm import runs each time.
- Set `keycloak.hostname.hostname` to the public realm host on a fresh
  install; without it OIDC discovery hands out the admin host until the realm
  import has run. See [`keycloak-BASICS.md`](../apps/keycloak/keycloak-BASICS.md).
- Client `zac` has no direct access grants, by design: a setup step that acts
  as a ZAC beheerder logs in through the browser.

## Reference: ZAC 5.9.1

### Solr basic auth

Solr runs with `solrSecurity` on the SolrCloud. With the operator-managed Solr
(the default) nothing is set: the operator generates the `admin` password into
the Secret `zac-solr-solrcloud-security-bootstrap` and ZAC uses it. The Solr

### Office converter

Gotenberg now requires basic auth: `zac.office_converter.username` and
`.password` per environment (B2). The chart's `dummy` defaults fail the

### Memory

The ZAC container defaults change: memory request and limit 2Gi (was a 1Gi
request, no limit), `ephemeral-storage` 4Gi, and the heap is 75% of the
memory limit (`-XX:MaxRAMPercentage=75`) instead of `-Xmx1024m`. podiumd

### Documents up to 500 MB

podiumd follows the ZAC chart's defaults: `zac.maxFileSizeMB` 500 (was 150),
`zac.maxInMemoryFileSizeMB` 80 (preview, mail and WebDAV editing, which cannot

`zac.nginx.proxy_timeout` 1800s. ZAC uploads large documents to Open Zaak in
parts, so Open Zaak's nginx timeouts go from 300s to 1800s too
(`openzaak.nginx.config.proxyConnectTimeoutSeconds` and
`proxyReadTimeoutSeconds`). Per environment (B2): remove the two 150 keys
from the gemeente values, and allow 600 MB on the gateway routes in front of
zac-nginx and openzaak-nginx (NGINX Gateway Fabric's default is `1m`; ZAC
reaches Open Zaak through its external URL). The `ClientSettingsPolicy` unit
must be lowercase. The practical ceiling without a ZAC image change is about
768 MB; the hard limit is 2047 MB (the Documenten API stores `bestandsomvang`
as a 32-bit byte count).

### Behandelaar roltype

Since ZAC 5.6
([ZAC #6767](https://github.com/infonl/dimpact-zaakafhandelcomponent/pull/6767))
ZAC only uses a roltype whose omschrijving is exactly `Behandelaar` to assign
a zaak; without it `RoltypeNotFoundException` in the ZAC log, no CMMN
process, no ontvangstbevestiging. The chart's e2e zaaktype
(`create_required_catalogi_job.e2eTestZaaktype.create`) is fixed by the Job
itself: it publishes a new version with the roltype, and ZAC moves its
zaakafhandelparameters to it (before 4.10.0 this Job ran only where
`openzaak.enabled` was set explicitly, B3). A new zaaktype version has two
consequences for other clients: Open Zaak autorisaties given per zaaktype URL
only cover the old version, so a client with such rights must get them on the
new version too; tooling that looks up a zaaktype by identificatie finds two
versions and must use the one without `eindeGeldigheid`.

### OpenBao and Frank!Gateway

`openbao.enabled` and `frankgateway.enabled` are `false` by default; an
environment that keeps them off needs nothing from this section.

**Enabling OpenBao for the first time** (it holds the Frank!Gateway secrets):
a one-time setup per environment, then one script before and one after every
deploy (D7). Full flow:
[`frankgateway-openbao-activation.md`](../apps/frankgateway/frankgateway-openbao-activation.md).

1. **Key Vault, once.** The pipeline or Terraform creates three items, so
   nobody types a secret: `openbao-db-admin` (random password),
   `openbao-seal-key` (32 random alphanumeric characters; never regenerate it)
   and `openbao-unseal-key` (the literal text `pending-init`; the activation
   script writes OpenBao's recovery key there on its first run). Turn on soft
   delete and purge protection: losing `openbao-seal-key` loses everything
   stored in OpenBao.
2. **Database.** Create the database `openbao` and the role `openbao-admin`
   on the Azure PostgreSQL server and give the role rights on the `public`
   schema (owning the database is not enough on Azure; without the grant the
   `openbao-db-schema` Job fails with `permission denied for schema public`):

   ```sql
   GRANT ALL PRIVILEGES ON DATABASE "openbao" TO "openbao-admin";
   GRANT USAGE, CREATE ON SCHEMA public TO "openbao-admin";
   ```

3. **Permissions.** The deploy reads `openbao-db-admin` and
   `openbao-seal-key`. The activation step reads and writes
   `openbao-unseal-key`, creates Secrets and Jobs, execs into pods in the
   namespace and runs `helm get` on the release.
4. **Values.** Substitute `REP_OPENBAO_DB_PASSWORD_REP` and
   `REP_OPENBAO_SEAL_KEY_REP` (`openbao.seal.static.key`) like the other
   passwords; the render fails on a seal key that is not 32 bytes. Leave the
   OpenBao Keycloak client secret empty: the chart generates it.
5. **Pipeline steps.** Before every deploy `scripts/openbao-keycloak-setup.py`
   (the `openbao` client, the `uploaders` role and the `vault-uploaders`
   group); after every deploy `scripts/openbao-activate.sh` (initialises and
   configures the vault on the first run; afterwards it only checks, re-runs
   the `openbao-config` Job and exits 0). Not in the packaged chart: run them
   from a checkout of the deployed chart version.
6. **Afterwards nothing by hand.** The pods unseal themselves after a restart,
   the CronJob `openbao-token-renewal` renews both tokens weekly (alert on a
   failed run), and no root token is stored. Add the people who write the
   gateway's secrets to the Keycloak group `vault-uploaders`.

**An environment that already runs OpenBao with the Shamir seal** (no
`openbao.seal.static.key`) migrates once, by hand: deploy with the key set,
then `bao operator unseal -migrate` with the current unseal key
([§3.6.1](../apps/frankgateway/frankgateway-openbao.md#361-static-seal-unseal-without-an-operator-optional)).
Without the key `openbao-activate.sh` stops on the Shamir seal unless given
`--allow-shamir`, and every pod restart needs a manual unseal.

### Frank!Gateway: hardening and upstream TLS

Only environments with `frankgateway.enabled` (none in SSC yet).

- **https upstreams must present a valid certificate.**
  `frankgateway.upstreamTls.verify` (default `true`) turns on nginx
  `proxy_ssl_verify` with the image's system CA bundle; an upstream with a
  private CA or a self-signed certificate fails with a 502. Diginetwerk
  endpoints (a real BRP) typically use "Staat der Nederlanden Private Root CA
  – G1", which is not in that bundle: set `upstreamTls.verify: false` on the
  instance that calls them (usually `outway`). Check each outway route's
  upstream host from the cluster before the upgrade:
  `openssl s_client -connect <host>:443 -servername <host> </dev/null`;
  `Verify return code: 0 (ok)` keeps working. KvK (api.kvk.nl) and BAG
  (api.bag.kadaster.nl) work with verify on.
- **Hardened pods** (`frankgateway.securityContext`): fixed non-root user,
  read-only root filesystem, no capabilities, seccomp `RuntimeDefault`, no
  ServiceAccount token. The etcd members switch from root to uid 1001; on
  their first start the kubelet re-owns the existing PVC (`fsGroup`,
  `fsGroupChangePolicy: OnRootMismatch`), so the stored routes are kept. A
  CSI driver without fsGroup support needs a one-off `chown -R 1001:1001` of
  the etcd volumes, or `frankgateway.securityContext.enabled: false`.
- **Admin API**: only private source addresses (`frankgateway.admin.allowFrom`)
  and, with `frankgateway.networkPolicies`, only the seed and sync jobs; the
  Control API (9092) listens on loopback only. With the dashboard on, the
  opt-in `frankgateway.dashboard.networkPolicy.enabled` lets only the
  oauth2-proxy reach the shim and only the shim reach the dashboard; reach a
  dashboard without auth with `kubectl port-forward`.
- **`openbao-consumer-auth`** on an enabled inway route needs
  `frankgateway.networkPolicies.enabled: true` (B3).
- **1.1.3 breaking**: the `response-extractor` plugin's field map moves under
  `fields`; PodiumD's templates and seeded routes do not use it. The 1.1.4
  image runs as `apisix` by default; PodiumD sets the gateway's user itself
  (`frankgateway.users.gateway`, uid 636).

## Reference: Redis

### Why the upgrade empties Redis

redis-operator v0.27.0 renames the Redis append-only file from
`Appendonly.aof` to `appendonly.aof` (upstream PR #1904). Every `redis-ha`
pod restarts, finds no file under the new name and starts empty, and the
replicas then copy the empty master (on a test environment Redis went from
about 490,000 keys to about 890). What that means for users and queues, and
the queue check: C8. The old files: E3.

### Failover safeguards (IN-2961)

Three new values under `redis-operator.redis-ha`, all on by default:

- `topologySpreadConstraints`: the `redis-ha` pods go to different nodes
  where possible (`maxSkew: 1` on `kubernetes.io/hostname`, `ScheduleAnyway`).
- `pdb`: a PodDisruptionBudget with `maxUnavailable: 1`.
- `masterReadinessCheck.enabled`: a pod labelled `redis-role=master` that
  reports `role:slave` itself is NotReady and drops out of the
  `redis-ha-master` Service (IN-2869: apps that connected during a failover
  wrote to a read-only replica).

The `redis-ha` pods restart once, one at a time; each master change makes
every Celery worker restart once (`UNBLOCKED force unblock … (master ->
replica?)`), which is expected. redis-operator v0.27.0 also fixes the
`REPLICAOF` loop of v0.26.0 (upstream PR #1843). See
[`redis-ha.md`](../apps/redis/redis-ha.md). An environment that wants other
placement sets its own `topologySpreadConstraints`, or `[]`.

**Existing environments keep their placement**: the Redis volumes are zonal
disks, so a pod can only restart in the zone of its disk. To move a
**replica** (never the master) to another node, recreate it with a new volume;
it copies the data from the master again:

```bash
kubectl --context "$CTX" -n "$NS" get pods -l app=redis-ha -L redis-role
# pick a pod with redis-role=slave that shares a node with another redis-ha pod
kubectl --context "$CTX" -n "$NS" exec <replica> -c redis-ha -- \
  sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} info replication' # role:slave, master_link_status:up
kubectl --context "$CTX" -n "$NS" delete pvc redis-ha-<replica> --wait=false
kubectl --context "$CTX" -n "$NS" delete pod <replica>
```

The new pod briefly reports `role:master` while it is empty and is a replica
again within about a minute; it is never labelled master.

## Security headers at the edge (IN-3162)

PABC, ITA, OMC, Open Archiefbeheer and Open Beheer send no
`Strict-Transport-Security` and/or no `X-Content-Type-Options: nosniff`
([security-headers.md](../misc/security-headers.md)). HSTS belongs at the
edge; nosniff is the apps' job, and the edge sets it until the vendors do.
Not tied to the chart version: B1's `migrate-gateway-security-headers.py`
can run before or after the upgrade. It gives every HTTPRoute rule in
`ssl-gateway.yml` a `ResponseHeaderModifier` that sets
`Strict-Transport-Security: max-age=31536000` and
`X-Content-Type-Options: nosniff`:

- `set` replaces a value an app sends itself, so no header is sent twice. A
  rule that already has a `ResponseHeaderModifier` only gets the headers it
  lacks; a header the environment sets, adds or removes there keeps the
  environment's choice.
- Rules that redirect (`RequestRedirect`) or have no `backendRefs` are
  skipped.
- No `X-Frame-Options` or CSP: Open Formulieren is embedded in Open Inwoner,
  and only an app can decide whether it may be framed.
- The routes attach to both listeners, so HSTS is also sent over plain HTTP;
  browsers ignore it there.

The result validates against the Gateway API schema; `kubectl apply` of
`ssl-gateway.yml` needs no restart.

## Reference: other changes

### Namespace portability

Cluster-internal references no longer hard-code the `podiumd` namespace: Redis
connection strings use the bare `redis-ha-master`, Django `allowedHosts` the
wildcard `.svc.cluster.local` (it matches the service FQDN in every
namespace; exposure is in-cluster only), `clamavHost` the bare `clamav`, KISS
Kibana the bare `kiss-kb-http:5601`. In the `podiumd` namespace nothing
changes, also for a gemeente `podiumd.yml` that overrides one of them with
`<svc>.podiumd.svc.cluster.local`. Deploying to another namespace: three
operator watch-scopes cannot be templated and must be set to that namespace
(copy `charts/podiumd/ci/values-namespace-scope.example.yaml`, or see
[deploying-to-a-custom-namespace.md](../misc/deploying-to-a-custom-namespace.md)):

```yaml
eck-operator:
  managedNamespaces:
    - <namespace>
zac:
  solr-operator:
    watchNamespaces: "<namespace>"
    zookeeper-operator:
      watchNamespace: "<namespace>"
```

### Open Inwoner: KvK API configuration

Open Inwoner's KvK settings (the `KvKConfig` singleton) have no
setup-configuration step, so on a fresh install they stay empty and
eHerkenning users see no company data on Mijn profiel (IN-3183). New values,
all empty by default:

| Key | Meaning |
| --- | --- |
| `openinwoner.kvk.apiRoot` | KvK API root without version or endpoint, e.g. `http://api-proxy.podiumd.svc.cluster.local/api/` (a dotted host name or localhost: Django's URLField rejects `http://api-proxy/api/`). A root with a version (`.../api/v1`) fails the render. |
| `openinwoner.kvk.apiKey` | API key, stored in the Secret `openinwoner-kvk`. Leave empty when a proxy adds the key. |
| `openinwoner.kvk.existingSecret` / `existingSecretKey` | An existing Secret with the key, instead of `apiKey`. |
| `openinwoner.kvk.job.*` | Retries and resources of the Job. |

With `apiRoot` set, the Job `openinwoner-configure-kvk-<hash>` writes the root
and key into `KvKConfig`, also overwriting values set by hand in the admin,
and writes an empty key when neither `apiKey` nor `existingSecret` is set. A
changed root or key runs it again. KISS (`kiss.settings.kvk`) and ZAC
(`zac.kvkApi`) use the same KvK endpoint.
