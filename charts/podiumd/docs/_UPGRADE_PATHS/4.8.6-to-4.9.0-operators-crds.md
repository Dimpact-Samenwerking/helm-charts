# Operators & CRDs — PodiumD 4.8.6 → 4.9.0

Companion to [`4.8.6-to-4.9.0-upgrade.md`](4.8.6-to-4.9.0-upgrade.md).

Everything in [`4.8.5-to-4.9.0-operators-crds.md`](4.8.5-to-4.9.0-operators-crds.md)
applies unchanged (ECK Operator 3.4.0 → 3.5.0, redis-operator 0.25.0 → 0.26.1).
This page records only what differs for an environment coming from **4.8.6**.

| Component | Change | CRD impact | Action |
|---|---|---|---|
| keycloak-operator | Operator image `26.7.2` → `26.6.4`; adfinis chart `1.13.0` → `1.12.1` — a **downgrade**, see below | None on upgrade — Helm never removes or downgrades CRDs | Leave 4.8.6's CRDs in place; no manual step |

## Keycloak Operator rolls back

4.9.0 branched from 4.8.5 and never picked up 4.8.6's operator bump, so this
hop moves the operator *backwards* while the Keycloak **server** image stays on
`26.7.2` in both releases. Rationale and the full impact table are in the
[upgrade guide](4.8.6-to-4.9.0-upgrade.md#keycloak-operator-2672--2664-a-downgrade).

### CRDs installed by 4.8.6 stay behind

`helm upgrade` does not touch CRDs in either direction. After this hop the
cluster keeps:

- `keycloakoidcclients.k8s.keycloak.org` (v2alpha1) — new in adfinis 1.13.0
- `keycloaksamlclients.k8s.keycloak.org` (v2alpha1) — new in adfinis 1.13.0
- the additive `issuedVerifiableCredentials` / `verifiableCredentials` fields
  on `keycloakrealmimports.k8s.keycloak.org`

**Leave all three in place.** podiumd creates no `KeycloakOIDCClient` or
`KeycloakSAMLClient` resources, and the 26.6.4 operator ignores CRDs it has no
controller for. Deleting a CRD deletes every CR of that kind cluster-wide —
never do it as cleanup for this hop.

### ClusterRoles that do disappear

adfinis 1.13.0 templates `keycloakoidcclientcontroller-cluster-role` and
`keycloaksamlclientcontroller-cluster-role`; 1.12.1 does not. Helm removes both
during the upgrade. Expected, and no action — the 26.6.4 operator has no
reconcilers that need them.

### Verify after rollout

```bash
kubectl -n podiumd get deploy keycloak-operator \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
# expect quay.io/keycloak/keycloak-operator:26.6.4@sha256:...

kubectl -n podiumd get keycloak -o jsonpath='{.items[*].spec.image}{"\n"}'
# expect quay.io/keycloak/keycloak:26.7.2@sha256:9d1f1b2b...
```

The operator's `RELATED_IMAGE_KEYCLOAK` env and podiumd's own `keycloak.image`
must agree on the server digest — that invariant is unchanged by the operator
downgrade, and is the thing to check if Keycloak pods restart unexpectedly
after the upgrade.
