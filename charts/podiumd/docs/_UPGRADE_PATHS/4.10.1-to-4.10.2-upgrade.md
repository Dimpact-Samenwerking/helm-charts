## C. Per environment, before the deploy day

### C1. Frank!Gateway inway: the front door must forward the client certificate

Only for environments with a Frank!Gateway inway route that uses
`openbao-consumer-auth` (today only ontw-dim1, whose front door already does
this). Everything else: nothing.

From 4.10.2 the function checks the validity period of the client
certificate, read from the `X-Client-Cert` header the front door forwards
(see [the reference](#frankgateway-inway-validity-check-on-the-client-certificate-in-3445)).
Check that the rewrite rule set on the API listener writes `X-Client-Cert` =
`{var_client_certificate}` next to `X-Client-Cert-Fingerprint`; the full
header contract is in
[`frankgateway-routes.md`](../apps/frankgateway/frankgateway-routes.md#what-the-front-door-must-send).
Without it every call on the route answers 401
`client_certificate_pem_required` after the upgrade. A front door that cannot
forward the certificate needs `validity = false` on the route.

## Reference

### Frank!Gateway inway: validity check on the client certificate (IN-3445)

The Application Gateway runs in passthrough mode (architecture decision
IN-3287): it requests the client certificate but validates nothing, so an
expired certificate reaches the inway like any other and, with its
fingerprint registered in OpenBao, kept its access (measured on ontw-dim1,
test B3, IN-3411). From 4.10.2 the `openbao-consumer-auth` function can parse
the certificate the front door forwards in `X-Client-Cert` and refuse a call
outside the certificate's validity period: 401 with `client_certificate_expired`
or `client_certificate_not_yet_valid` in the body. With a fingerprint identity
the forwarded certificate must also be the one the fingerprint names
(`client_certificate_mismatch` otherwise: a broken rewrite rule, not a
caller). The check runs after the route's `allow` list, so a consumer that may
not use the route still gets 403. Nothing else changes: any CA is still
accepted, revocation is still removing the fingerprint from OpenBao.

The check is on by default (`validity = true`) and fails closed: without the
`X-Client-Cert` header the route answers 401 `client_certificate_pem_required`
([C1](#c1-frankgateway-inway-the-front-door-must-forward-the-client-certificate)).
No deployed environment has such a route yet apart from ontw-dim1's test
route, whose front door forwards the header.

Rollback: set `validity = false` on the route, or roll the chart back; no
data is involved. Options and answers:
[`frankgateway-routes.md`](../apps/frankgateway/frankgateway-routes.md#consumer-identities-from-openbao-inbound).
