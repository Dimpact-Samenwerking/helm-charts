# Upgrade guide: PodiumD 4.10.1 → 4.10.2

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

For environments already on **4.10.1**. The guide has three parts:

1. **The runbook** (sections A to F): what to run, in which order, and what
   to check. Written for the deploy pipeline.
2. **Component versions and changes**: the record of what moved in the chart.
3. **Reference**: the detail per topic, for when a step fails or a choice has
   to be made.

Companion documents:

- [`4.10.1-to-4.10.2-values-deltas.md`](4.10.1-to-4.10.2-values-deltas.md):
  the exact changes in a gemeente `podiumd.yml`, `services-gateway.yml` and
  `ssl-gateway.yml`.
- [`4.10.1-to-4.10.2-gemeente-specific.md`](4.10.1-to-4.10.2-gemeente-specific.md):
  findings per environment.

## B. Once per values repository

### B1. Render before the deploy day

| Render fails while | Fix |
| --- | --- |
| `openformulieren.customerInteractionsConfigJob.enabled` is `true`, setup-configuration runs, and `openformulieren.configuration.data` has no `zgw_consumers` service (with `zgw_consumers_config_enable: true`) whose `identifier` is `customerInteractionsConfigJob.serviceIdentifier` (default `openklant-api`), or that service's `api_type` is not `kc` (also when missing) | add the service ([values deltas](4.10.1-to-4.10.2-values-deltas.md)): this environment's Open Klant klantinteracties API, `api_type: kc`; or set `serviceIdentifier` to the identifier of the existing Open Klant service. | an `oidc_op_*_endpoint` under `oidc_db_config_admin_auth` in the `configuration.data` of Open Zaak, Open Notificaties, Objecten, Open Archiefbeheer, Open Klant, Open Formulieren, Open Inwoner, Referentielijsten, Open Beheer or Open VTB is on another host than this Keycloak (`keycloak.config.realmFrontendUrl`, `adminFrontendUrl`, `keycloak.hostname`, or the in-cluster `keycloak-service`) | correct the endpoint to the Keycloak host: the app's config Job would fail on it during the deploy, after its retries (IN-3625). ## C. Per environment, before the deploy day

### C1. Mirror the images

The registry the environment pulls from must hold everything in
[`images-4.10.2.yaml`](../images/images-4.10.2.yaml), by digest. Renamed
this release, so a mirror run by the old name misses it:

- `nginx/nginx-unprivileged` 1.31.9 (replaces the archived
  `nginxinc/nginx-unprivileged`).

A mirror kept under another path is fine, as long as it holds the 1.31.9
digest pulled from `docker.io/nginx/nginx-unprivileged`. That covers a
`repository:` override such as `<acr>/nginx-unprivileged` or
`<acr>/nginxinc/nginx-unprivileged` on any of the paths listed in
[nginx-unprivileged](#nginx-unprivileged-1317--1319). The old repository
never published 1.31.9, so a mirror that still syncs from
`docker.io/nginxinc/nginx-unprivileged` fails to pull on every nginx
sidecar, the API proxy and the Frank!Gateway dashboard shim.

Re-published under the same tag (the manifest marks it "digest changed"):

- `alpine/k8s` 1.37.2, now `sha256:7a82aeef…`. It runs the zookeeper-operator
  hooks, the redis-ha Jobs and CronJob, the ZAC restart Job and the Maykin
  configuration wait hook.

A mirror that skips a name and tag it already has keeps the old digest, and
the pull fails. Copy with `skopeo copy --all --preserve-digests`: without
`--preserve-digests` a copy can store the manifest under another digest.

### C2. Own admin automation: client scope `kc-admin-api`

Only for an environment with its own automation that calls Keycloak's admin
API with a service-account client of the master realm (client credentials),
next to the chart's `keycloak-operator` client.

Keycloak 26.8.2 answers the admin API with 401 to a client-credentials token
without the audience of the client scope `kc-admin-api`. The chart's
`keycloak-operator` client has that scope, so the chart's Jobs keep working;
a token from an admin-cli password login also still works. For each own
service-account client: Clients → the client → Client scopes → Add client
scope → `kc-admin-api` (Default), before the deploy. Without it that automation
fails after the upgrade with 401 on `/admin/realms/...`.

## D. The deploy run

### D1. `helm upgrade`

Run the deploy as usual.

### If the run fails

| Symptom | Fix |
| --- | --- |
| `ensure-keycloak-operator-sa` fails with `FATAL: podiumd-admin cannot log in to the master realm with a password`: client `keycloak-operator` exists in the master realm with another secret, and master's login flow refuses a password-only login (for example because it requires OTP) | set `keycloak-operator.jobs.ensureOperatorSa.clientSecret` to that client's secret, or enter the value of `keycloak-operator.jobs.ensureOperatorSa.clientSecret` as the client's secret in the admin console (Clients → keycloak-operator → Credentials), or delete the client so the next deploy creates it; then deploy again |
| a pod cannot pull `alpine/k8s:1.37.2` (the zookeeper-operator hook fails `helm upgrade`; the redis-ha label-master CronJob, the ZAC restart Job or a Maykin configuration wait hook stay in `ImagePullBackOff`) | the registry lacks the new digest: C1. |

## E. After the deploy

### E1. Delete a failed `keycloak-update-job` from the earlier upgrade

An environment that went from 4.9.x to 4.10.0 or 4.10.1 may still have the
`keycloak-update-job` that failed then (`NoSuchFileException` on
`quarkus-application.dat`; Keycloak was recreated and runs fine). 4.10.2 does
not remove it. Check and delete it:

```bash
kubectl --context "$CTX" -n "$NS" get job keycloak-update-job
kubectl --context "$CTX" -n "$NS" delete job keycloak-update-job
```

## Changes that need no action

- **The `keycloak-operator` client no longer depends on master's login
  flows** (podiumd-chart-55): `ensure-keycloak-operator-sa` creates a missing
  client with Keycloak's `kc.sh bootstrap-admin service`, straight against the
  Keycloak database, instead of logging in as `podiumd-admin` with a password.
  An environment whose master realm requires OTP in the direct grant flow then
  no longer hangs the realm imports. The Job has two init containers with the
  Keycloak image (`keycloak-operator.jobs.ensureOperatorSa.resources`). The
  client it creates is marked as a temporary admin in the admin console. A
  client that exists with another secret still needs a password login as
  `podiumd-admin`; when master refuses that, the Job fails at once (see
  [If the run fails](#if-the-run-fails)) instead of retrying for over an hour.
- **No failed `keycloak-update-job` on a minor Keycloak upgrade**: this hop
  keeps Keycloak 26.8.1, but an environment that goes from 4.9.x straight to
  4.10.2 changes 26.7 to 26.8. With `keycloak.update.strategy: Auto` (the
  default), a deploy that changes the running Keycloak's major or minor
  version (read from the Keycloak CR with Helm `lookup`) sets the CR's
  strategy to `RecreateOnImageChange` for that deploy; the next deploy writes
  `Auto` again, which shows as a CR change in `helm diff`. The operator then
  recreates Keycloak, as Auto does for such an upgrade anyway, but runs no
  update Job, which on the 26.7 → 26.8 hop failed and stayed behind. A render
  without cluster access (`helm template`, a GitOps render) or without the
  Keycloak CRD finds no CR and keeps Auto.
- **`openformulieren-configure-customer-interactions` runs after Open Forms'
  setup-configuration** (IN-3198): it is now a post-install/post-upgrade hook
  with weight 10, after `openformulieren-config`, which creates the Open Klant
  service it needs. As a plain Job it started at once and gave up after 20
  minutes while earlier hooks were still running, with "Service 'openklant-api'
  not found (yet)" also when the values were right. A failure of this Job now
  fails the deploy. Old `openformulieren-configure-customer-interactions-<hash>`
  Jobs are removed by the upgrade.

## Changes

### nginx-unprivileged 1.31.7 → 1.31.9

PodiumD 4.10.2 upgrades the shared **nginx-unprivileged** image to 1.31.9,
pinned at:

- `global.images.nginx.tag` `1.31.7` → `1.31.9`
- `openzaak.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `openarchiefbeheer.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `openklant.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `openformulieren.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `openinwoner.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `openbeheer.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `zac.nginx.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `apiproxy.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)
- `frankgateway.dashboard.auth.shim.image.tag` `1.31.7` → `1.31.9` (shares a YAML anchor with `global.images.nginx.tag`)

- Image / digest: see [`images-4.10.2.yaml`](../images/images-4.10.2.yaml).

The repository moves from `nginxinc/nginx-unprivileged` to
`nginx/nginx-unprivileged` (`global.images.nginx.repository`, shared by all
the paths above). Docker Hub archived the `nginxinc` repository; its last
release is 1.31.7. The new repository builds the same image (port 8080, PID
file in `/tmp`, uid 101), but with its own digests. Mirror it first:
[C1](#c1-mirror-the-images).

### keycloak 26.8.1 → 26.8.2

PodiumD 4.10.2 upgrades **keycloak** from app version 26.8.1
to 26.8.2.

- Image tag pin `keycloak.image.tag` `26.8.1` → `26.8.2` in
  `charts/podiumd/values.yaml`.
- Image tag pin `keycloak-operator.operator.config.keycloakImage.tag` `26.8.1` → `26.8.2` (shares a YAML anchor with `keycloak.image.tag`) in
  `charts/podiumd/values.yaml`.

- Image / digest: see [`images-4.10.2.yaml`](../images/images-4.10.2.yaml).

The 26.8.2 image runs Red Hat OpenJDK 21.0.13.1, with the fix for
CVE-2026-114938. The 26.8.1 tag was not rebuilt, so only the new version
brings the fix. The Keycloak pods restart once.

The admin API now requires the audience of the client scope `kc-admin-api` in
a client-credentials token: own service-account clients for admin automation
need that scope (C2).

### keycloak-operator 26.8.1 → 26.8.2 (chart 1.13.1, unchanged)

PodiumD 4.10.2 upgrades **keycloak-operator** from app version 26.8.1
to 26.8.2.

- Image tag pin `keycloak-operator.operator.image.tag` `26.8.1` → `26.8.2` in
  `charts/podiumd/values.yaml`.

- Image / digest: see [`images-4.10.2.yaml`](../images/images-4.10.2.yaml).

The operator moves with the server. Its CRDs are the same as in 26.8.1, so
`scripts/install-keycloak-operator-crds.sh` needs no extra run.
