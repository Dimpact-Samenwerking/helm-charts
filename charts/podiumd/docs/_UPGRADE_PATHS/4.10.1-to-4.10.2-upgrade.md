# Upgrade guide: PodiumD 4.10.1 → 4.10.2

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

For environments already on **4.10.1**. The guide has three parts:

1. **The runbook** (sections A to F): what to run, in which order, and what
   to check. Written for the deploy pipeline.
2. **Component versions and changes**: the record of what moved in the chart.
3. **Reference**: the detail per topic, for when a step fails or a choice has
   to be made.

Companion documents:

- [`4.10.1-to-4.10.2-values-deltas.md`](4.10.1-to-4.10.2-values-deltas.md):
  the exact changes in a gemeente `podiumd.yml`, `services-gateway.yml` and
  `ssl-gateway.yml`.
- [`4.10.1-to-4.10.2-gemeente-specific.md`](4.10.1-to-4.10.2-gemeente-specific.md):
  findings per environment.

## C. Per environment, before the deploy day

### C1. Mirror the images

The registry the environment pulls from must hold everything in
[`images-4.10.2.yaml`](../images/images-4.10.2.yaml), by digest. Renamed
this release, so a mirror run by the old name misses it:

- `nginx/nginx-unprivileged` (replaces the archived
  `nginxinc/nginx-unprivileged`), at the tag and digest of
  `nginx/nginx-unprivileged` in `images-4.10.2.yaml`.

A mirror kept under another path is fine, as long as it holds that digest,
pulled from `docker.io/nginx/nginx-unprivileged`. That covers a
`repository:` override such as `<acr>/nginx-unprivileged` or
`<acr>/nginxinc/nginx-unprivileged` on any of the paths listed in
[nginx-unprivileged](#nginx-unprivileged-1317--13110). The old repository
stopped at 1.31.7, so a mirror that still syncs from
`docker.io/nginxinc/nginx-unprivileged` fails to pull on every nginx
sidecar, the API proxy and the Frank!Gateway dashboard shim.

Re-published under the same tag (the manifest marks it "digest changed"):

- `alpine/k8s` 1.37.2, now `sha256:7a82aeef…`. It runs the zookeeper-operator
  hooks, the redis-ha Jobs and CronJob, the ZAC restart Job and the Maykin
  configuration wait hook.

A mirror that skips a name and tag it already has keeps the old digest, and
the pull fails. Copy with `skopeo copy --all --preserve-digests`: without
`--preserve-digests` a copy can store the manifest under another digest.

### C2. Client scope `kc-admin-api`: list the clients

Keycloak 26.8.2 answers the admin API with 401 to a client-credentials token
without the audience of the client scope `kc-admin-api`. The scope is new in
26.8.2: its database migration creates it in master and gives it only to
`admin-cli` and `security-admin-console`. On 26.8.1 it does not exist, so it
can only be added after the deploy ([E1](#e1-client-scope-kc-admin-api)).
Before the deploy day, list the clients that need it by hand:

- **The chart's `keycloak-operator` client:** created over REST by an earlier
  release, so it lacks the scope. `ensure-keycloak-operator-sa` adds it,
  after a password login as `podiumd-admin`. Nothing to do, except where
  master's direct grant flow requires more than a password (OTP): there that
  login fails. A client that the Job creates on a fresh install has the scope.
- **Own admin automation:** each own service-account client of the master
  realm that calls the admin API. From the moment Keycloak runs 26.8.2 until
  E1, that automation fails with 401 on `/admin/realms/...`: pause it during
  the deploy. A token from an admin-cli password login still works.

### C3. Open Inwoner: announce the one-time logout

Open Inwoner 2.5.1 signs its cached data, sessions included, and ignores the
unsigned entries 2.5.0 left behind
([openinwoner 2.5.0 → 2.5.1](#openinwoner-250--251-chart-270-unchanged)). So
**every resident and employee logged in to Open Inwoner is logged out once**
by the deploy; blocked login attempts and the notification limits are reset as
well. Announce it like a planned logout, and deploy outside peak hours.

While the web and worker pods roll, 2.5.0 and 2.5.1 pods share the cache: a
user who switches between an old and a new pod can be logged out more than
once in that window, and a request on a 2.5.0 pod can fail on a signed entry.
That ends when the rollout is done.

## D. The deploy run

### D1. `helm upgrade`

Run the deploy as usual, outside peak hours: ClamAV restarts (see
[Changes that need no action](#changes-that-need-no-action)), and with one
ClamAV pod the virus scan of file uploads is unavailable meanwhile.

### If the run fails

| Symptom | Fix |
| --- | --- |
| a pod cannot pull `alpine/k8s:1.37.2` (the zookeeper-operator hook fails `helm upgrade`; the redis-ha label-master CronJob, the ZAC restart Job or a Maykin configuration wait hook stay in `ImagePullBackOff`) | the registry lacks the new digest: C1. |
| `ensure-keycloak-operator-sa` fails with `FATAL: podiumd-admin cannot log in to the master realm with a password`: client `keycloak-operator` exists in the master realm with another secret or without client scope `kc-admin-api`, and master's login flow refuses a password-only login (for example because it requires OTP) | add `kc-admin-api` to the client ([E1](#e1-client-scope-kc-admin-api)); for the secret: set `keycloak-operator.jobs.ensureOperatorSa.clientSecret` to that client's secret, or enter the value of `keycloak-operator.jobs.ensureOperatorSa.clientSecret` as the client's secret in the admin console (Clients → keycloak-operator → Credentials), or delete the client so the next deploy creates it; then delete the Job and deploy again |
| `ensure-keycloak-operator-sa` fails after all its retries; each attempt ends with `podiumd-admin could not log in to the master realm (last status=…); retrying the Job` | Keycloak did not come up, or `podiumd-admin` stayed disabled: check the Keycloak pods and the `ensure-podiumd-admin-user` Job, fix that, then delete the Job and deploy again |

The Job, its pods and their logs are removed 10 minutes after it ends
(`ttlSecondsAfterFinished`): read the log in time, or in the cluster's log
store. A longer time would keep the Job, so the next deploy would neither run
it again nor accept a changed pod template.

## E. After the deploy

### E1. Client scope `kc-admin-api`

Once the Keycloak pods run 26.8.2, for each client listed in
[C2](#c2-client-scope-kc-admin-api-list-the-clients): Clients → the client →
Client scopes → Add client scope → `kc-admin-api`, Default.

- **Own admin automation:** then resume it.
- **`keycloak-operator`, only where master requires OTP:**
  `ensure-keycloak-operator-sa` has stopped with
  `FATAL: podiumd-admin cannot log in to the master realm with a password`.
  After adding the scope, run it again: delete the Job
  (`kubectl --context "$CTX" -n "$NS" delete job ensure-keycloak-operator-sa`)
  and deploy again.

### E2. Open Formulieren: empty its cache database

Open Forms 4.0.8 changed the format of its cached data; 4.0.9 fixes the code
paths that 4.0.8 broke with it, and Open Forms advises emptying the caches
after the deploy
([changelog](https://open-forms.readthedocs.io/en/stable/changelog.html)). Its
own example, `redis-cli flushall`, does **not** fit PodiumD: all apps share
redis-ha, and `flushall` empties every app's caches and Celery queues. Empty
only Open Formulieren's cache database: the number at the end of the
environment's `openformulieren.settings.cache.default` (`redis-ha-master:6379/9`
in `values.yaml`, so `<db>` is `9` unless the environment sets another).
`CTX` and `NS` are the environment's kube context and namespace; the master
comes from the RedisReplication status, which stays right while the pod
labels catch up after a failover:

```bash
MASTER=$(kubectl --context "$CTX" -n "$NS" get redisreplication redis-ha -o jsonpath='{.status.masterNode}')
kubectl --context "$CTX" -n "$NS" exec "$MASTER" -c redis-ha -- \
  sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} -n <db> FLUSHDB'
```

Effects: residents and employees logged in to Open Formulieren are logged out,
and a form in progress may have to be started again. The same database holds
the login lockouts (`openformulieren.settings.cache.axes`), so blocked login
attempts and failed-login counters start from zero. Do it right after the
deploy, outside peak hours. The Celery broker database
(`openformulieren.settings.celery.brokerUrl`, `/10`) stays as it is.

### E3. Open Formulieren: report of service fetch credentials

4.0.8 fixes service fetch configurations being readable without a login, and
adds a report of the configurations that send credentials in their headers
(`Authorization`, `X-Api-Key`, `Api-Key`). Run it once; it lists name, id and
the headers of each such configuration. Rotate the credentials it lists: they
could be read before this deploy.

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/openformulieren -- \
  python /app/bin/report_service_fetch_credentials_usage.py
```

### E4. Delete a failed `keycloak-update-job` from the earlier upgrade

An environment that went from 4.9.x to 4.10.0 or 4.10.1 may still have the
`keycloak-update-job` that failed then (`NoSuchFileException` on
`quarkus-application.dat`; Keycloak was recreated and runs fine). 4.10.2 does
not remove it. Delete it; the command does nothing where it does not exist.
The operator names it after the Keycloak CR, `<keycloak.name>-update-job`:
where `keycloak.name` is set, use that name.

```bash
kubectl --context "$CTX" -n "$NS" delete job keycloak-update-job --ignore-not-found
```

## F. Rollback

- **Open Inwoner:** 2.5.0 cannot read the signed entries 2.5.1 wrote. After
  `helm rollback`, empty Open Inwoner's cache database
  (`openinwoner.settings.cache.default`, `redis-ha-master:6379/11` in
  `values.yaml`; use the environment's own number for `<db>`) on the current
  redis-ha master; users are logged out once more. `CTX` and `NS` are the
  environment's kube context and namespace:

  ```bash
  MASTER=$(kubectl --context "$CTX" -n "$NS" get redisreplication redis-ha -o jsonpath='{.status.masterNode}')
  kubectl --context "$CTX" -n "$NS" exec "$MASTER" -c redis-ha -- \
    sh -c 'redis-cli --no-auth-warning ${REDIS_PASSWORD:+-a "$REDIS_PASSWORD"} -n <db> FLUSHDB'
  ```

  Leave the Celery database (`openinwoner.settings.celery.brokerUrl`, `/12`)
  alone.
- **Open Formulieren:** 4.0.7 cannot read the cache entries 4.0.9 wrote.
  After `helm rollback`, empty the cache database again with the commands of
  [E2](#e2-open-formulieren-empty-its-cache-database), with the same effects.

## Changes that need no action

- **`openformulieren-configure-customer-interactions` runs after Open Forms'
  setup-configuration** (IN-3198): it is now a post-install/post-upgrade hook
  with weight 10, after `openformulieren-config`, which creates the Open Klant
  service it needs. As a plain Job it started at once and gave up after 20
  minutes while earlier hooks were still running, with "Service 'openklant-api'
  not found (yet)" also when the values were right. `helm upgrade` now waits
  for this Job, at most 4 minutes (`activeDeadlineSeconds: 240`), within the
  `--timeout` Helm applies to each hook (default 5m), and a failure of this
  Job fails the deploy (with `--atomic`: rolls it back). Old
  `openformulieren-configure-customer-interactions-<hash>` Jobs are removed by
  the upgrade.
- **The `keycloak-operator` client no longer depends on master's login
  flows** (podiumd-chart-55): `ensure-keycloak-operator-sa` creates a missing
  client with Keycloak's `kc.sh bootstrap-admin service`, straight against the
  Keycloak database, instead of logging in as `podiumd-admin` with a password.
  An environment whose master realm requires OTP in the direct grant flow then
  no longer hangs the realm imports. The Job has two init containers with the
  Keycloak image (`keycloak-operator.jobs.ensureOperatorSa.resources`). The
  client it creates is marked as a temporary admin in the admin console. A
  client that exists with another secret still needs a password login as
  `podiumd-admin`; when master refuses that, the Job fails at once (see
  [If the run fails](#if-the-run-fails)) instead of retrying for over an hour.
- **KISS's Elasticsearch and Kibana restart once** (8.19.24 → 8.19.26): the
  ECK operator replaces the three Elasticsearch pods one at a time, then the
  single Kibana pod. Kibana is unavailable while its pod is replaced; KISS
  search keeps working when every KISS index has a replica
  ([kiss-eck 8.19.24 → 8.19.26](#kiss-eck-81924--81926)).
- **ClamAV restarts once** (1.5.4 → 1.5.5). It runs as one pod by default
  (its HPA can scale to five; several pods roll one at a time). With one pod,
  clamd loads its signature database at start, so the virus scan of file
  uploads in Open Formulieren and Open Inwoner cannot reach clamd until the
  pod is ready: up to about five minutes (the startup probe allows 60 s plus
  9 × 30 s). The deploy runs outside peak hours for this (D1).
- **No failed `keycloak-update-job` on a minor Keycloak upgrade**: this hop
  keeps Keycloak 26.8.1, but an environment that goes from 4.9.x straight to
  4.10.2 changes 26.7 to 26.8. With `keycloak.update.strategy: Auto` (the
  default), a deploy that changes the running Keycloak's major or minor
  version (read from the Keycloak CR with Helm `lookup`) sets the CR's
  strategy to `RecreateOnImageChange` for that deploy; the next deploy writes
  `Auto` again, which shows as a CR change in `helm diff`. The operator then
  recreates Keycloak, as Auto does for such an upgrade anyway, but runs no
  update Job, which on the 26.7 → 26.8 hop failed and stayed behind. A render
  without cluster access (`helm template`, a GitOps render) or without the
  Keycloak CRD finds no CR and keeps Auto.
- **ZaakBrug picks the zaaktype version by date** (1.27.3): `creeerZaak`
  creates a zaak under the zaaktype version that is valid on the zaak's start
  date (`ingangsdatumObject`), else under the most recent started version.
  Before, a zaaktype with several versions (future-dated or overlapping) could
  get another version. A StUF-to-ZGW zaak with such a zaaktype can therefore
  land on a different version than before the deploy; that is the fix, not a
  regression ([zaakbrug 1.27.1 → 1.27.3](#zaakbrug-1271--1273-chart-2336--2338)).

The repository moves from `nginxinc/nginx-unprivileged` to
`nginx/nginx-unprivileged` (`global.images.nginx.repository`, shared by all

release is 1.31.7. The new repository builds the same image (port 8080, PID

[C1](#c1-mirror-the-images).

HTTP/3, `try_files` with `alias`, `resolver`, `ssl_early_data`, the stream and
mail modules ([nginx changes](https://nginx.org/en/CHANGES)). Two changes in
1.31.9 reject malformed requests that were accepted before: header lines
without a colon, and a chunked request body with too much framing overhead.
Well-formed clients are not affected; a client that sends such requests gets
400 from the nginx sidecars, the API proxy and the Frank!Gateway dashboard
shim.

### openinwoner 2.5.0 → 2.5.1 (chart 2.7.0, unchanged)

PodiumD 4.10.2 upgrades **openinwoner** from app version 2.5.0
to 2.5.1.

- Image tag pin `openinwoner.image.tag` `2.5.0` → `2.5.1` in
  `charts/podiumd/values.yaml`.

- Image / digest: see [`images-4.10.2.yaml`](../images/images-4.10.2.yaml).

A security fix: Open Inwoner now signs the data it keeps in its Redis caches,
sessions included, with its `SECRET_KEY`, and ignores entries without a valid
signature
([changelog](https://docs.openinwoner.nl/en/v2.5.1/changelog.html)).

- **Every user is logged out once** after the upgrade: the old sessions have
  no signature. Blocked login attempts and the notification limits are reset
  for the same reason. Announce it beforehand ([C3](#c3-open-inwoner-announce-the-one-time-logout)).
- **Changing the `SECRET_KEY` later** logs everyone out again, unless the old
  value is kept as the fallback: `openinwoner.settings.secretKeyFallback`,
  which the chart passes as `SECRET_KEY_FALLBACK`.
- An entry with a bad signature is logged as `cache_signature_invalid` and
  counted in the OpenTelemetry metric `oip.cache.signature_invalid`. **A burst
