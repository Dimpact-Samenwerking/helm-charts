# Upgrade guide: PodiumD 4.10.1 → 4.10.2

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

For environments already on **4.10.1**. The guide has three parts:

1. **The runbook** (sections A to F): what to run, in which order, and what
   to check. Written for the deploy pipeline.
2. **Component versions and changes**: the record of what moved in the chart.
3. **Reference**: the detail per topic, for when a step fails or a choice has
   to be made.

This hop moves redis-ha from `quay.io/opstree/redis` v8.10.1 to the official
`docker.io/library/redis` 8.10.3-alpine. Every environment that overrides the
redis-ha image with an ACR mirror changes its repository (B1) and needs the new
image in its registry (C1). See
[redis-ha: official redis image](#redis-ha-official-redis-image).

Companion documents:

- [`4.10.1-to-4.10.2-values-deltas.md`](4.10.1-to-4.10.2-values-deltas.md):
  the exact changes in a gemeente `podiumd.yml`, `services-gateway.yml` and
  `ssl-gateway.yml`.
- [`4.10.1-to-4.10.2-gemeente-specific.md`](4.10.1-to-4.10.2-gemeente-specific.md):
  findings per environment.

## A. Once per cluster

Nothing for this hop.

## B. Once per values repository

### B1. Point the redis-ha image at library/redis

Run in SSCHostingSync and in ExternalsPodiumD, on the branch that takes 4.10.2:

```bash
S=<helm-charts>/charts/podiumd/scripts
G=<values repository>/applications/gemeenten
python3 "$S/migrate-redis-ha-image-4.10.2.py" --dry-run --gemeenten-dir "$G"  # preview
python3 "$S/migrate-redis-ha-image-4.10.2.py" --gemeenten-dir "$G"            # migrate
python3 "$S/migrate-redis-ha-image-4.10.2.py" --check --gemeenten-dir "$G"    # pipeline gate
```

| Script | Changes | Needs a person when |
| --- | --- | --- |
| `migrate-redis-ha-image-4.10.2.py` | `redis-operator.redis-ha.image.repository`: `[<registry>/]opstree/redis` → `[<registry>/]library/redis`; `quay.io/opstree/redis` → `docker.io/library/redis`; a flat `redis` next to a `registry:` key (an ACR mirror of opstree/redis) → `library/redis`. A `registry:` key stays as it is. | A `redis-ha.image.tag` override with a `v` prefix: remove the tag, the chart pins 8.10.3-alpine. |

The render fails while an override still names `opstree/redis` with a tag
without `v`, so a file the script missed shows up before the deploy.

## C. Per environment, before the deploy day

### C1. Mirror the image

The registry the environment pulls from must hold
`library/redis:8.10.3-alpine` by digest (see
[`images-4.10.2.yaml`](../images/images-4.10.2.yaml)): `acrprodmgmt.azurecr.io`,
and `acrtestmgmt.azurecr.io` for gene ontw. It is a new repository, so a mirror
run by the old name `opstree/redis` misses it. Keep `opstree/redis:v8.10.1` in
the registry for the rollback (F).

## D. The deploy run

### D1. `helm upgrade`

Run the deploy as usual.

### If the run fails

| Symptom | Cause and fix |
| --- | --- |
| The render fails: `redis-operator.redis-ha.image.repository is "…opstree/redis", the old opstree/redis image` | The values file was not migrated: B1. |
| The render fails: `… needs redis-operator.featureGates.GenerateConfigInInitContainer: true` | The environment turns the gate off; remove that override. |
| A redis-ha pod cannot pull `library/redis:8.10.3-alpine` | The registry lacks the image by digest: C1. |

## E. After the deploy

### E1. Check redis-ha

The new image rolls the three redis-ha pods one by one. Afterwards all three are
Ready, exactly one has the label `redis-role=master`, and its
`redis-cli info replication` shows `connected_slaves:2`.

## F. Rollback

Roll back the chart and the values file together: `helm rollback` to the 4.10.1
revision and revert the B1 change. 4.10.1 with `library/redis` renders
`<registry>/library/redis:v8.10.1`, which does not exist. The data on the
redis-ha volumes stays readable by v8.10.1 (same 8.10 line).

## Changes

### redis-operator - redis v8.10.1 → 8.10.3-alpine

The redis-ha image moves from `quay.io/opstree/redis` to the official
`docker.io/library/redis` (B1, C1); see
[redis-ha: official redis image](#redis-ha-official-redis-image).

PodiumD 4.10.2 upgrades the **redis-operator - redis** image to 8.10.3-alpine,
pinned at:

- `redis-operator.redis-ha.image.tag` `v8.10.1` → `8.10.3-alpine`

- Image / digest: see [`images-4.10.2.yaml`](../images/images-4.10.2.yaml).

## Reference

### redis-ha: official redis image

opstree has not published `quay.io/opstree/redis` 8.10.2 or 8.10.3. redis-ha
now runs the official `docker.io/library/redis`, so it follows Redis releases
without waiting for opstree. The `-alpine` variant is musl-based like the opstree
image.

The opstree image's entrypoint is not needed: the chart turns on the redis-operator
feature gate `GenerateConfigInInitContainer`, so the operator writes
`/etc/redis/redis.conf` in its `init-config` container and starts the redis
container with `redis-server /etc/redis/redis.conf`, bypassing the image
entrypoint. 4.10.1 already ran this way. Replication runs over the operator's
own Redis client (`SLAVEOF`), not through scripts in the image. The render fails
when the gate is off with an image other than `opstree/redis`.

What changes in the pods:

- The log shows `Failed to write PID file` at startup: `/var/run` is not
  writable for uid 1000 in the official image. Redis runs normally.
- The image is larger (39.5 MB against 17.9 MB compressed, amd64) because it
  ships the Redis modules. The operator's `redis-server` command does not load them, but image
  scans report their dependencies.
- Docker Hub rebuilds `8.10.3-alpine` when the Alpine base changes, so
  `verify-image-digests` reports it as a sliding digest more often.
