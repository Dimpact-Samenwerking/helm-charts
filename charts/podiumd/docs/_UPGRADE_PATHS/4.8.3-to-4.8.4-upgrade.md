# Upgrade guide: PodiumD 4.8.3 → 4.8.4

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

This is the upgrade guide for environments already on **4.8.3**.

## Component versions (4.8.4 vs 4.8.3)

| Component | App version | Helm chart | Notes |
| --- | --- | --- | --- |
| Open Inwoner Platform (OIP / "Portaal") | 2.4.2 | 2.4.0 | verify ZGW cache timeout override (see below) |
| Open Zaak | 1.27.4 | 1.14.2 (unchanged) | no action required |

## Changes

### Open Inwoner 2.3.1 → 2.4.2

- Helm chart `openinwoner` `2.2.1` → `2.4.0` (appVersion `2.4.2`) in
  `charts/podiumd/Chart.yaml`.
- Image tag pin `openinwoner.image.tag` `2.3.1` → `2.4.2` in
  `charts/podiumd/values.yaml`.

No new required values were found between these chart versions — the CMS
v3 → v4 one-time migration (`openinwoner.settings.cms4MigrationInitContainer`)
already shipped in 4.8.0 and needs no further action here.

**One-time data migration on first startup at 2.4.0**: the app reads
`ZGW_CASE_LIST_NUM_WORKERS`, `ZGW_CASE_LIST_FETCH_TIMEOUT`,
`CACHE_ZGW_ZAKEN_TIMEOUT` and `CACHE_ZGW_CATALOGI_TIMEOUT` directly from the
container environment **once**, to seed the new admin-configurable
`OpenZaakConfig`/`ZGWApiGroupConfig` fields that replace them. Whatever value
is present in the environment at that moment is what gets captured — after
that, the env vars are inert and the value only changes via the admin UI.

- Of these, podiumd only ever exposes `CACHE_ZGW_ZAKEN_TIMEOUT`, via
  `openinwoner.settings.cacheZgwZakenTimeout` (`charts/podiumd/values.yaml`).
  It defaults to `""` (unset) in this chart, so on an unmodified environment
  the migration captures the same app default (300s) that was already in
  effect — no behavior change.
- **Action required only if** an environment's `podiumd.yml` overrides
  `openinwoner.settings.cacheZgwZakenTimeout` with a non-empty value, or sets
  any of the other three vars directly (e.g. via `extraEnv`). Confirm the
  value is what you intend *before* the 4.8.4 rollout — once the pod starts
  on 2.4.0 and the migration runs, changing it afterward requires the admin
  UI, not the Helm value.
- The other three vars aren't exposed as podiumd values at all, so unless an
  environment has manually injected them, the migration just captures the
  app's upstream defaults — no action needed.

Image / digest: [`images-4.8.4.yaml`](../images/images-4.8.4.yaml). The ACR
mirror name is `maykinmedia/open-inwoner` — mirror the new `2.4.2` tag and
digest.

### Open Zaak 1.27.3 → 1.27.4

- Image tag pin `openzaak.image.tag` `1.27.3` → `1.27.4` in
  `charts/podiumd/values.yaml`. Patch release — Helm chart `openzaak`
  (`1.14.2`) is unchanged.

Image / digest: [`images-4.8.4.yaml`](../images/images-4.8.4.yaml). The ACR
mirror name is `openzaak/open-zaak` — mirror the new `1.27.4` tag and digest.

### Fix: Keycloak client PKCE attribute was a no-op

`<component>.configuration.pkceEnabled: true` (or the `zac`/`kiss`/`pabc`
equivalents) rendered `pkceCodeChallengeMethod: S256` as a top-level field on
the Keycloak client import. That field does not exist on the Keycloak client
schema, so Keycloak silently ignored it — PKCE was never actually enforced,
regardless of this setting.

Fixed to the correct nested client attribute:

```yaml
# before (no-op)                  # after
pkceCodeChallengeMethod: S256     attributes:
                                     pkce.code.challenge.method: S256
```

**No action** for the default `pkceEnabled: false` on every component — the
rendered client import is unchanged.

**Action required** only if an environment has `pkceEnabled: true` set for
any component (`openzaak`, `openarchiefbeheer`, `opennotificaties`,
`objecten`, `objecttypen`, `openklant`, `openformulieren`, `openinwoner`,
`referentielijsten`, `openbeheer`, `kiss`, `zac`, `ita`, `pabc`): PKCE (S256)
will now actually be enforced on that Keycloak client for the first time.
Confirm the corresponding app's OIDC client
(`mozilla_django_oidc >= 4.0.0` with `oidc_use_pkce: true`, or the
equivalent for non-Django apps) is configured to send a PKCE code
verifier before/while rolling out this upgrade, or login will start failing
with a PKCE-required error from Keycloak.

## Per-environment checklist

Read the whole guide once first. Then, for **every environment** you upgrade,
work through this list top to bottom.

### A. Prepare

- [ ] **ACR mirror**: mirror the 4.8.4 image set under the strip-registry
      names ([`images-4.8.4.yaml`](../images/images-4.8.4.yaml)) — new
      `maykinmedia/open-inwoner` tag `2.4.2` and `openzaak/open-zaak` tag
      `1.27.4`.
- [ ] If `pkceEnabled: true` is set for any component in this environment's
      `podiumd.yml`, confirm the app's OIDC client actually supports PKCE
      before deploying.
- [ ] Check this environment's `podiumd.yml` for a non-empty
      `openinwoner.settings.cacheZgwZakenTimeout` override (or any manually
      injected `ZGW_CASE_LIST_NUM_WORKERS` / `ZGW_CASE_LIST_FETCH_TIMEOUT` /
      `CACHE_ZGW_CATALOGI_TIMEOUT`). If set, confirm the value before
      deploying — Open Inwoner 2.4.0 captures it into the database once on
      first startup and it becomes admin-UI-managed afterward.

### B. Deploy

- [ ] Run the deploy pipeline / `helm upgrade`.
