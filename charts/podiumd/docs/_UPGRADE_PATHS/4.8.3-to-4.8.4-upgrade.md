# Upgrade guide: PodiumD 4.8.3 → 4.8.4

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

This is the upgrade guide for environments already on **4.8.3**.

## Component versions (4.8.4 vs 4.8.3)

| Component | App version | Helm chart | Notes |
| --- | --- | --- | --- |
| Open Inwoner Platform (OIP / "Portaal") | 2.4.2 | 2.4.0 | **plan a maintenance window** — data migration + config changes (see below) |
| Open Zaak | 1.27.4 | 1.14.2 (unchanged) | no action required |

## Changes

### Open Inwoner 2.3.1 → 2.4.2

- Helm chart `openinwoner` `2.2.1` → `2.4.0` (appVersion `2.4.2`) in
  `charts/podiumd/Chart.yaml`.
- Image tag pin `openinwoner.image.tag` `2.3.1` → `2.4.2` in
  `charts/podiumd/values.yaml`.

No new required values were found between these chart versions — the CMS
v3 → v4 one-time migration (`openinwoner.settings.cms4MigrationInitContainer`)
already shipped in 4.8.0 and needs no further action here.

**One-time data migration on first startup at 2.4.0**: the app reads
`ZGW_CASE_LIST_NUM_WORKERS`, `ZGW_CASE_LIST_FETCH_TIMEOUT`,
`CACHE_ZGW_ZAKEN_TIMEOUT` and `CACHE_ZGW_CATALOGI_TIMEOUT` directly from the
container environment **once**, to seed the new admin-configurable
`OpenZaakConfig`/`ZGWApiGroupConfig` fields that replace them. Whatever value
is present in the environment at that moment is what gets captured — after
that, the env vars are inert and the value only changes via the admin UI.

- Of these, podiumd only ever exposes `CACHE_ZGW_ZAKEN_TIMEOUT`, via
  `openinwoner.settings.cacheZgwZakenTimeout` (`charts/podiumd/values.yaml`).
  It defaults to `""` (unset) in this chart, so on an unmodified environment
  the migration captures the same app default (300s) that was already in
  effect — no behavior change.
- **Action required only if** an environment's `podiumd.yml` overrides
  `openinwoner.settings.cacheZgwZakenTimeout` with a non-empty value, or sets
  any of the other three vars directly (e.g. via `extraEnv`). Confirm the
  value is what you intend *before* the 4.8.4 rollout — once the pod starts
  on 2.4.0 and the migration runs, changing it afterward requires the admin
  UI, not the Helm value.
- The other three vars aren't exposed as podiumd values at all, so unless an
  environment has manually injected them, the migration just captures the
  app's upstream defaults — no action needed.

**Data migration, row-by-row — plan a maintenance window.** 2.4.0 adds
multi-address support for portal users and creates a `DigitalAddress` record
for every existing user who has an e-mail address or phone number
([gh#2611](https://github.com/maykinmedia/open-inwoner/issues/2611),
[gh#2615](https://github.com/maykinmedia/open-inwoner/issues/2615)). Upstream
explicitly documents this as row-by-row, not a bulk operation, and flags
longer migration time on installations with many users. **Action required**:
budget deploy-window time proportional to the portal's user count — the
portal is unavailable while the migration completes and this cannot be
skipped or deferred.

**`ZGW_LIMIT_NOTIFICATIONS_FREQUENCY` is dropped and its value is *not*
carried over** ([gh#1900](https://github.com/maykinmedia/open-inwoner/issues/1900)),
unlike the ZGW cache/worker vars above. `OpenZaakConfig.notification_frequency_limit`
always initialises to the upstream default of 900s regardless of what this
env var held. podiumd does not expose it as a chart value, so this only
matters for an environment injecting it manually (e.g. `extraEnv`) — if so,
re-enter the intended value via the admin UI after upgrading.

**Webhook notifications are now asynchronous**
([gh#1900](https://github.com/maykinmedia/open-inwoner/issues/1900)):
notifications are stored as a `NotificationRecord` and handed off to Celery
instead of processed in-request, and a new daily 03:00 beat task prunes old
records. A running Celery worker and celery-beat are now a hard precondition
for notification processing — podiumd runs `openinwoner-worker` and
`openinwoner-beat` at chart defaults, so this is **no action** for
environments using the chart as-is; only relevant if an environment has
scaled either to zero.

**Three new env vars render unconditionally; all default to current
behavior — no action required, but useful knobs to know about**:

- `ELASTICSEARCH_DSL_AUTOSYNC` / `ELASTICSEARCH_DSL_AUTO_REFRESH`
  ([gh#2589](https://github.com/maykinmedia/open-inwoner/issues/2589)),
  chart keys `openinwoner.settings.elasticsearch.dslAutosync` /
  `.dslAutoRefresh` (subchart default `true` for both, unchanged by podiumd).
  Set `dslAutosync: false` if admin actions 500 when Elasticsearch isn't
  guaranteed available — the search index then only updates via the periodic
  Celery task instead of synchronously.
- `OIDC_USE_LEGACY_ENDPOINTS`
  ([gh#2662](https://github.com/maykinmedia/open-inwoner/issues/2662)), chart
  key `openinwoner.settings.oidcUseLegacyEndpoints` (subchart default `true`,
  unchanged by podiumd). Deprecated upstream and will be removed in a later
  OIP release. Flip to `false` once every IdP's redirect-URI whitelist has
  been updated to the generic `/oidc/callback/` endpoint (instead of the
  legacy per-provider one, e.g. `/digid-oidc/callback/`).

**Document-status visibility is now admin-configurable**
([gh#2502](https://github.com/maykinmedia/open-inwoner/issues/2502)): the
default selection (`definitief`, `gearchiveerd`) matches current behavior —
no action required — but an **empty** selection in the admin disables status
filtering entirely, exposing documents in every status to portal users. Worth
a heads-up to whoever manages `OpenZaakConfig` post-upgrade.

### Fix: Keycloak client PKCE attribute was a no-op

`<component>.configuration.pkceEnabled: true` (or the `zac`/`kiss`/`pabc`
equivalents) rendered `pkceCodeChallengeMethod: S256` as a top-level field on
the Keycloak client import. That field does not exist on the Keycloak client
schema, so Keycloak silently ignored it — PKCE was never actually enforced,
regardless of this setting.

Fixed to the correct nested client attribute:

```yaml
# before (no-op)                  # after
pkceCodeChallengeMethod: S256     attributes:
                                     pkce.code.challenge.method: S256
```

**No action** for the default `pkceEnabled: false` on every component — the
rendered client import is unchanged.

**Action required** only if an environment has `pkceEnabled: true` set for
any component (`openzaak`, `openarchiefbeheer`, `opennotificaties`,
`objecten`, `objecttypen`, `openklant`, `openformulieren`, `openinwoner`,
`referentielijsten`, `openbeheer`, `kiss`, `zac`, `ita`, `pabc`): PKCE (S256)
will now actually be enforced on that Keycloak client for the first time.
Confirm the corresponding app's OIDC client
(`mozilla_django_oidc >= 4.0.0` with `oidc_use_pkce: true`, or the
equivalent for non-Django apps) is configured to send a PKCE code
verifier before/while rolling out this upgrade, or login will start failing
with a PKCE-required error from Keycloak.

## Per-environment checklist

Read the whole guide once first. Then, for **every environment** you upgrade,
work through this list top to bottom.

### A. Prepare

- [ ] **ACR mirror**: mirror the 4.8.4 image set under the strip-registry
      names ([`images-4.8.4.yaml`](../images/images-4.8.4.yaml)) — new
      `maykinmedia/open-inwoner` tag `2.4.2` and `openzaak/open-zaak` tag
      `1.27.4`.
- [ ] If `pkceEnabled: true` is set for any component in this environment's
      `podiumd.yml`, confirm the app's OIDC client actually supports PKCE
      before deploying.
- [ ] Check this environment's `podiumd.yml` for a non-empty
      `openinwoner.settings.cacheZgwZakenTimeout` override (or any manually
      injected `ZGW_CASE_LIST_NUM_WORKERS` / `ZGW_CASE_LIST_FETCH_TIMEOUT` /
      `CACHE_ZGW_CATALOGI_TIMEOUT`). If set, confirm the value before
      deploying — Open Inwoner 2.4.0 captures it into the database once on
      first startup and it becomes admin-UI-managed afterward.
- [ ] If a manually injected `ZGW_LIMIT_NOTIFICATIONS_FREQUENCY` is in use,
      note its value now — it is not carried over and must be re-entered via
      the admin UI after the upgrade.
- [ ] **Plan a maintenance window for Open Inwoner** sized to the portal's
      user count: 2.4.0 runs a row-by-row `DigitalAddress` data migration on
      first startup (one row per existing user with an e-mail address or
      phone number) and the portal is unavailable while it completes.

### B. Deploy

- [ ] Run the deploy pipeline / `helm upgrade`.

### C. Verify

- [ ] Open Inwoner: the `openinwoner` pod(s) complete startup (the
      `DigitalAddress` migration runs as part of pod startup, not a separate
      Job — watch `kubectl -n podiumd logs` for migration progress on a large
      user base).
- [ ] Portal login (DigiD/OIDC) succeeds and "Mijn Zaken" / search results
      load.
- [ ] `openinwoner-worker` and `openinwoner-beat` are `Running` with no
      errors — both are hard preconditions for notification processing as of
      2.4.0.
- [ ] Spot-check a profile page shows the expected e-mail/phone as a
      `DigitalAddress` (confirms the migration completed rather than timing
      out).
