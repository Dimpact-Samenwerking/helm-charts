# Operators & CRDs — PodiumD 4.9.0 → 4.9.1

Companion to [`4.9.0-to-4.9.1-upgrade.md`](4.9.0-to-4.9.1-upgrade.md).

| Component | Change | CRD impact | Action |
|---|---|---|---|
| keycloak-operator | Images `26.6.4` → `26.7.3`; adfinis chart `1.12.1` → `1.13.0` | **Yes** — one existing CRD gets new (additive) fields, and adfinis 1.13.0 adds **two brand-new CRDs** with matching controllers | **Apply CRDs manually** before/during rollout — see below; `helm upgrade` never touches CRDs |

Diffed adfinis `keycloak-operator` chart 1.12.1 vs 1.13.0's bundled `crds/` directly (not just the upgrade doc's usual "byte-identical" spot check):

## `keycloakrealmimports.k8s.keycloak.org` — additive schema change only

Two new optional array fields appear on the user-representation schema
(`issuedVerifiableCredentials`, `verifiableCredentials`), used by the
OID4VCI verifiable-credentials work added in Keycloak 26.7.0. Diff is
purely additive (new optional properties, nothing removed or retyped) —
existing `KeycloakRealmImport` CRs remain valid as-is.

`keycloaks.k8s.keycloak.org` is byte-identical between 1.12.1 and 1.13.0.

## Two new CRDs: `KeycloakOIDCClient` and `KeycloakSAMLClient` (v2alpha1)

Adfinis 1.13.0 bundles two CRDs podiumd's operator subchart has never shipped
before — `keycloakoidcclients.k8s.keycloak.org` and
`keycloaksamlclients.k8s.keycloak.org` — plus a dedicated `ClusterRole` for
each (`keycloakoidcclientcontroller-cluster-role`,
`keycloaksamlclientcontroller-cluster-role`), templated automatically and
requiring no podiumd values change. podiumd doesn't create any `KeycloakOIDCClient`/
`KeycloakSAMLClient` resources itself, but the operator Deployment's own
reconcilers for these two new controllers start unconditionally — **if the
CRDs aren't present in the cluster, the operator is at risk of failing to
register those controllers on startup.** Not verified against a live
operator pod in this pass; treat as a hard prerequisite rather than a maybe.

## Part 2 (26.7.2 → 26.7.3 image bump): no further CRD changes

The second half of this hop's Keycloak change — the image-only bump to
`26.7.3` — does **not** touch CRDs at all. CRDs come from the adfinis chart,
which stays pinned at `1.13.0` (no chart has been published targeting
`26.7.3` yet). The CRD impact above is entirely from the `1.12.1` → `1.13.0`
chart bump (Part 1).

### Action required

Apply the CRDs **before** the `helm upgrade` that bumps the operator image,
same ordering as every prior CRD-impacting hop. How depends on which deploy
path the environment uses — the two are independent and a fix in one does
**not** cover the other.

#### ExternalsPodiumD (Azure DevOps — the `ontw-*` / `test-*` environments)

Run the **Haven** pipeline with component `keycloak-operator-crds`. It resolves
the adfinis chart version, applies that chart's CRDs server-side, and waits for
each to reach `Established`:

| Parameter | Value |
|---|---|
| `target` | the environment, e.g. `ontw-dim1` |
| `component` | `["keycloak-operator-crds"]` |
| `keycloakOperatorVersion` | `1.13.0` when deploying podiumd from a **branch**; leave **blank** once 4.9.1 is released |

Run on `ontw-dim1` 2026-09-09 (build 35674): the cluster had only
`keycloaks` and `keycloakrealmimports` beforehand; all four CRDs are now
applied and `Established`.

> **Leave `keycloakOperatorVersion` blank only when the environment's
> `config.yml` already names the podiumd version being deployed.** Blank means
> "derive from `config.yml`", so during a branch deploy — where `config.yml`
> still names the previously *released* chart — it resolves the **old**
> operator version (4.9.0 → 1.12.1) and applies the old CRD set, which is
> exactly the failure this component exists to prevent.

#### podiumd-infra (GitHub Actions — the `*.pd.test-rig.nl` QA rigs)

`scripts/mini-helm-deploy.sh` applies the CRDs itself, but on `main` its loop
still lists only the original two filenames. The four-CRD fix exists on
`feature/johnb00-podiumd-4.9.0` and **has not been merged**, so any rig
deploying 4.9.1 from `main` hits the crash-loop. Merge that fix, or apply the
one-off below first.

#### Manual fallback (either path)

```bash
helm repo add adfinis https://charts.adfinis.com --force-update
helm show crds adfinis/keycloak-operator --version 1.13.0 \
  | kubectl apply --server-side --force-conflicts --field-manager=helm -f -
```

`--field-manager=helm` so the chart's later reconcile sees itself as the
existing owner rather than fighting the apply for field ownership.

> **Do not use `charts/podiumd/scripts/install-keycloak-operator-crds.sh`.**
> Its `CRD_FILES` array lists only `keycloaks` and `keycloakrealmimports`, and
> its defaults are pinned to Keycloak 26.6.1 / adfinis chart 1.11.4 — artefacts
> of the 4.7.0-era problem it was written for. Run as-is against 4.9.1 it
> installs the wrong two CRDs and leaves the operator crash-looping, while
> appearing to succeed.

#### Why the adfinis chart rather than upstream

Both helper scripts fetch CRDs from `keycloak/keycloak-k8s-resources` by
*Keycloak* version, which needs a Keycloak-version → CRD-filename mapping kept
in step by hand — and that mapping is precisely what went stale. Taking the
CRDs from the adfinis chart the operator is actually deployed from removes the
mapping entirely: the CRDs cannot drift from the operator, and a chart bump
that adds a CRD is picked up automatically.
