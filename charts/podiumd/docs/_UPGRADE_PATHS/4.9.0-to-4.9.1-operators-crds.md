# Operators & CRDs — PodiumD 4.9.0 → 4.9.1

Companion to [`4.9.0-to-4.9.1-upgrade.md`](4.9.0-to-4.9.1-upgrade.md).

| Component | Change | CRD impact | Action |
|---|---|---|---|
| keycloak-operator | Images `26.6.4` → `26.7.3`; adfinis chart `1.12.1` → `1.13.0` | **Yes** — one existing CRD gets new (additive) fields, and adfinis 1.13.0 adds **two brand-new CRDs** with matching controllers | **Apply CRDs manually** before/during rollout — see below; `helm upgrade` never touches CRDs |

Diffed adfinis `keycloak-operator` chart 1.12.1 vs 1.13.0's bundled `crds/` directly (not just the upgrade doc's usual "byte-identical" spot check):

## `keycloakrealmimports.k8s.keycloak.org` — additive schema change only

Two new optional array fields appear on the user-representation schema
(`issuedVerifiableCredentials`, `verifiableCredentials`), used by the
OID4VCI verifiable-credentials work added in Keycloak 26.7.0. Diff is
purely additive (new optional properties, nothing removed or retyped) —
existing `KeycloakRealmImport` CRs remain valid as-is.

`keycloaks.k8s.keycloak.org` is byte-identical between 1.12.1 and 1.13.0.

## Two new CRDs: `KeycloakOIDCClient` and `KeycloakSAMLClient` (v2alpha1)

Adfinis 1.13.0 bundles two CRDs podiumd's operator subchart has never shipped
before — `keycloakoidcclients.k8s.keycloak.org` and
`keycloaksamlclients.k8s.keycloak.org` — plus a dedicated `ClusterRole` for
each (`keycloakoidcclientcontroller-cluster-role`,
`keycloaksamlclientcontroller-cluster-role`), templated automatically and
requiring no podiumd values change. podiumd doesn't create any `KeycloakOIDCClient`/
`KeycloakSAMLClient` resources itself, but the operator Deployment's own
reconcilers for these two new controllers start unconditionally — **if the
CRDs aren't present in the cluster, the operator is at risk of failing to
register those controllers on startup.** Not verified against a live
operator pod in this pass; treat as a hard prerequisite rather than a maybe.

## Part 2 (26.7.2 → 26.7.3 image bump): no further CRD changes

The second half of this hop's Keycloak change — the image-only bump to
`26.7.3` — does **not** touch CRDs at all. CRDs come from the adfinis chart,
which stays pinned at `1.13.0` (no chart has been published targeting
`26.7.3` yet). The CRD impact above is entirely from the `1.12.1` → `1.13.0`
chart bump (Part 1).

### Action required

Helm only auto-installs a chart's `crds/` on first install, never on upgrade,
so the two new CRDs must be applied by hand on existing clusters. Use one of:

- `charts/podiumd/scripts/install-keycloak-operator-crds.sh` with
  `--keycloak-version 26.7.3`. Since `1631d9ba` (2026-10-07) the script also
  installs `keycloakoidcclients` and `keycloaksamlclients` when the Keycloak
  version publishes them (from 26.7.0). Older copies of the script install only
  `keycloaks` and `keycloakrealmimports`, and the 26.7.3 operator then
  crash-loops with `Informer startup error ... keycloaksamlclients ... Not
  Found` (hit on ontw-dim2).

  ```bash
  charts/podiumd/scripts/install-keycloak-operator-crds.sh \
    --context <kube-context> --keycloak-version 26.7.3
  ```

- apply the CRDs directly from the adfinis chart as a one-off:

  ```bash
  helm show crds adfinis/keycloak-operator --version 1.13.0 \
    | kubectl --context <kube-context> apply --server-side --force-conflicts -f -
  ```

- ExternalsPodiumD: the Haven pipeline component `keycloak-operator-crds`
  (branch `feat/haven-keycloak-operator-crds`, not merged yet) does the same
  `helm show crds` apply from a pipeline; it was used for ontw-dim1.

Either way, apply CRDs **before** the `helm upgrade` that bumps the operator
image, same ordering as every prior CRD-impacting hop.
