# Values deltas — PodiumD 4.8.5 → 4.9.0

**No gemeente `podiumd.yml` changes are required for this hop.**

Both changes ship entirely in the chart — image tags in `values.yaml` plus the
matching `Chart.yaml` dependency bumps:

- **ZAC** app `5.0.2 → 5.6.0`, chart `1.0.297 → 1.0.301`.
- **ZGW Office Add-in** frontend + backend `v0.9.313 → 0.11.0`, chart
  `0.0.89 → 0.0.91`. The new tags carry no `v` prefix.

Every environment checked overrides `registry`/`repository` for these images
(their own ACR mirror) but never `tag`, so the new tags/digests apply from the
chart defaults automatically.

The only prerequisite is mirroring the new ZAC `5.6.0` and ZGW Office Add-in
`0.11.0` digests — listed in
[`images-info.yaml`](../images/images-info.yaml).

> Mirror from `images-info.yaml`, **not** from
> [`images-4.9.0.yaml`](../images/images-4.9.0.yaml). The latter describes the
> 4.9.0 integration branch, which holds ZAC at `5.1.0` and the Add-in at
> `v0.9.352`; those versions are not what this branch pins.

## Scope of the "no changes required" claim

The claim covers the chart contract: no key in a gemeente `podiumd.yml` has to
be added, renamed or removed for the chart to render and deploy. It was
verified end-to-end on `jim00`, which upgraded 4.8.5 → this branch in place
with no values edits and came up healthy (ZAC `/health/ready` `overall: UP`,
all workloads ready).

It is not a statement about application behaviour across five ZAC minor
versions. An environment that configures ZAC beyond the chart defaults — BRP
protocollering, PABC integration — should still read the ZAC 5.1 → 5.6 release
notes before upgrading.
