# Gemeente-specific notes — PodiumD 4.10.0 → 4.10.1

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## All environments: Open Archiefbeheer cannot delete objects in Objecten (IN-2784)

Open Archiefbeheer's Objecten token, the `tokenauth` item
`identifier: openarchiefbeheer` in `objecten.configuration.data`, has no
`permissions` in most environments. Objecten then gives that token no access
to any object: only an `is_superuser` token sees every object type
(`objects/token/permissions.py` and `filter_for_token` in Open Object 4.1.0).
When Open Archiefbeheer destroys a zaak, it deletes the zaak's related objects
in Objecten (`DELETE /objects/{uuid}?zaak=<zaak url>`, the Objecten plugin of
its external registers in 2.0.0 and 2.1.x). A delete needs `read_and_write` on
the object's type, so destroying a zaak with a productaanvraag object fails
with 403.

Checked on SSCHostingSync `main` (`cc5a747`, 78 files) and ExternalsPodiumD
`feature/info-podiumd-4.10` (`bac1db4`, 6 files) on 2026-11-01:

- **71 files** have the item without `permissions`: 68 in SSCHostingSync, 3 in
  ExternalsPodiumD. zwol prod has the item twice; keep one.
- **asse accp** already has `read_and_write` on
  `REP_ZAC_PRODUCTAANVRAAG_UUID_REP`.
- **12 files** have no such item, or no `objecten.configuration.data`: the 8
  SSCHostingSync stubs of the ExternalsPodiumD environments, gene ontw, and
  dimp ontw and test and icat ontw in ExternalsPodiumD.

`scripts/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py` adds to
each item without `permissions` or `is_superuser`:

```yaml
permissions:
  - object_type: "REP_ZAC_PRODUCTAANVRAAG_UUID_REP"
    mode: read_and_write
```

`REP_ZAC_PRODUCTAANVRAAG_UUID_REP` is the existing `zac-productaanvraag-uuid`
Key Vault secret; no new secret is needed. An item that already has
`permissions` is left alone, with a CHECK note when it lacks this one. Checked
on copies of the files above: 71 files migrated, only the 3 lines per item
added, 0 errors, and a second run changes nothing.

```bash
python3 charts/podiumd/scripts/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py --dry-run --gemeenten-dir <SSCHostingSync>/applications/gemeenten
python3 charts/podiumd/scripts/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py --gemeenten-dir <SSCHostingSync>/applications/gemeenten
python3 charts/podiumd/scripts/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py --gemeenten-dir <ExternalsPodiumD>/applications/gemeenten
```

Objects of other object types linked to a zaak still fail the destruction:
give the token `read_and_write` on those types too when an environment
destroys such zaken.

Environments that go from 4.9.6 straight to 4.10.1, never running 4.10.0
(the 4.9.5 → 4.9.6 → 4.10.1 path in `4.9.5-to-4.9.6-upgrade.md`), need the
same step: their values have the same item without `permissions`.
