## OpenBao docs moved into the Frank!Gateway docs

The OpenBao documentation is now one runbook,
[`frankgateway-openbao.md`](../apps/frankgateway/frankgateway-openbao.md).
`docs/apps/openbao/openbao-BASICS.md` and
`docs/apps/openbao/podiumd-component-openbao.md` remain as pointers to it.

`scripts/openbao-mint-config-token.sh` now requires `KUBE_CONTEXT` and passes
it to every `kubectl` call; it no longer uses the current context. It also
takes the root token from `BAO_ROOT_TOKEN_FILE` (for example
`<(az keyvault secret show …)`), so the token stays out of the environment.
`BAO_ROOT_TOKEN` and the silent prompt still work.

## Open Formulieren config Jobs mount `extraVolumes`

The umbrella Jobs `openformulieren-configure-customer-interactions` and
`openformulieren-configure-clamav` now mount `openformulieren.extraVolumes` /
`extraVolumeMounts`, so `EXTRA_VERIFY_CERTS` resolves
([IN-3023](https://dimpact.atlassian.net/browse/IN-3023)). Both Jobs are named
after a checksum of their pod template, so a changed input no longer makes
`helm upgrade` fail on an immutable Job. Each gets a new name and runs once more
on the next deploy; both are idempotent. Helm removes the old fixed-name
`openformulieren-configure-clamav` Job.

## Grafana: monitoring-logging 1.0.18 drops `offline_access` (no podiumd change)

Since 4.9.1 the Keycloak realm no longer grants `offline_access`, and Keycloak
rejects a login that asks for it (`invalid_scope`, *"Login provider denied
login request"* in Grafana)
([IN-2882](https://dimpact.atlassian.net/browse/IN-2882)). monitoring-logging
1.0.18 removes the scope from Grafana's chart default
(`grafana.grafana.ini.auth.generic_oauth.scopes`).

An environment that pins `scopes` in its own `monitoring.yml` must leave
`offline_access` out as well. As of 2026-09-30 none in ExternalsPodiumD or
podiumd-infra still requests it. Details and verification:
[`upgrade-from-1.0.17-to-1.0.18.md`](../../../monitoring-logging/docs/upgrade-from-1.0.17-to-1.0.18.md).

## OpenBao static seal (opt-in)

`openbao.seal.static.key` lets the OpenBao pods unseal themselves after every
restart, so Frank!Gateway no longer answers 503 until someone unseals by hand.
Without a key nothing changes: the seal stays Shamir. Details, rotation and
risks: [`frankgateway-openbao.md`](../apps/frankgateway/frankgateway-openbao.md)
§3.6.1.

Switching an environment on (ADO `ExternalsPodiumD`):

1. Terraform creates `openbao-seal-key` in the environment Key Vault; the
   environment's `podiumd.yml` sets
   `openbao.seal.static.key: "REP_OPENBAO_SEAL_KEY_REP"`.
2. Deploy. On a fresh vault the pipeline's post-deploy OpenBao check fails
   this run (the pods are not initialised yet); that is expected.
3. **Fresh vault:** run `openbao_bootstrap.py` against the running OpenBao. It
   initialises with a recovery key; store it as `openbao-unseal-key` and the
   root token as `openbao-root-token`, then deploy again
   ([§5.2](../apps/frankgateway/frankgateway-openbao.md#52-scripted-bootstrap-and-unseal-ado-externalspodiumd)). **Existing Shamir vault:** migrate once
   with `bao operator unseal -migrate` on one pod, then restart the other pods
   one at a time (§3.6.1); the pipeline does not migrate and fails the deploy
   while a pod is in migration mode.
4. Continue with the runbook: config token (§5 step 5), `openbao-config` Job
   (§5 step 6), Frank!Gateway reader token (§5 step 7), verify (§6), revoke the
   root token (§5 step 8).

## ITA 3.3.2 change of default value

The default for `ita.verlopenContactverzoekHerinneringNotificatie.enabled`
changes from `true` to `false`. The notification emails that are sent contain
an error. This  will be fixed in a later version.

If a gemeente has `ita.verlopenContactverzoekHerinneringNotificatie.enabled` explicitly set to true, this local override should be removed.
