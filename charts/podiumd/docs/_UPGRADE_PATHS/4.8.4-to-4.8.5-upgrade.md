# Upgrade guide: PodiumD 4.8.4 → 4.8.5

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

This is the upgrade guide for environments already on **4.8.4**.

Companion for this hop:

- [`4.8.4-to-4.8.5-values-deltas.md`](4.8.4-to-4.8.5-values-deltas.md) —
  every gemeente `podiumd.yml` key to add/change.

## Component versions (4.8.5 vs 4.8.4)

| Component | App version | Helm chart | Notes |
| --- | --- | --- | --- |
| Open Beheer | 0.9.1 | 0.1.3 (unchanged) | no action required |
| ZAC (zaakafhandelcomponent) | 5.0.2 | 1.0.297 | **action required** only if BRP protocollering (iConnect) is in use — see below |

## Changes

### Open Beheer `0.9.0` → `0.9.1`

4.8.5 bumps the **Open Beheer** application image from `0.9.0` to `0.9.1`. The
`openbeheer` Helm chart stays at `0.1.3`.

0.9.1 brings improved session management, UI experience, branding, and stability.
Highlights relevant for operators:

- **`SESSION_EXPIRE_AT_BROWSER_CLOSE`** — new env var allowing sessions to end on
  browser close. Not yet exposed as a named `settings.*` values key in chart `0.1.3`.
  The application default is `False` (sessions persist until `SESSION_COOKIE_AGE`
  expires, unchanged from 0.9.0).
- **`SESSION_COOKIE_AGE`** — already configurable via `openbeheer.settings.sessionCookieAge`;
  no change.
- CSP fix: selectielijstklasse results now fetched via BFF instead of direct browser call.
- Broken breadcrumbs fix.
- Automatic redirect to the login page when a user's session expires.
- Updated branding and logo.

The uWSGI `--master` workaround (`settings.uwsgi.master: "1"`) **remains required** —
0.9.1 does not fix the upstream image. See
[openbeheer-known-issues.md](../apps/openbeheer/openbeheer-known-issues.md).

#### Action required

- No config, schema, or migration changes.
- Image / digest: see [`docs/images/images-4.8.5.yaml`](../images/images-4.8.5.yaml).

### ZAC 5.0.1 → 5.0.2 (Helm chart 1.0.251 → 1.0.297)

**The image tag and the Helm chart version deliberately move at different
speeds this hop.** The chart line is bumped to 1.0.297, whose bundled
defaults are tested upstream against app **5.5.0** — but the image is kept
pinned to **5.0.2**, a same-line patch of 5.0.1 (not a jump to 5.5.0), so
this release does not pull in the 5.1–5.4 application behavior changes.
5.0.2 contains exactly one fix: BRP verwerkingregister-extension-with-zaaktype
is now configurable (see below) — that's also the reason for the chart bump,
since the chart needs 1.0.297 to expose that as a value at all.

Reviewed the chart's default-values diff between 1.0.251 and 1.0.297, plus
the upstream app release notes and the actual template/source differences
between the v5.0.1 and v5.0.2 tags (not just the chart). Two things are
relevant to podiumd's config:

#### New in the chart, but a no-op with this image: application-side PKCE (`zac.auth.enablePkce`)

Chart 1.0.297 templates a new `AUTH_ENABLE_PKCE` env var
(`zac.auth.enablePkce`) for application-side PKCE. **This has no effect with
the 5.0.2 image pinned here** — checked the actual v5.0.2 and v5.0.1 source
directly: neither has any PKCE handling at all. PKCE support was added to
ZAC after 5.0.2 (first appearing in the 5.1.x line, per PR
[infonl/dimpact-zaakafhandelcomponent#6490](https://github.com/infonl/dimpact-zaakafhandelcomponent/pull/6490)).
podiumd's existing `zac.auth.pkceEnabled` (the Keycloak-**client** side
switch) keeps its "currently a no-op for ZAC" character for as long as the
image stays on 5.0.2, now for a documented reason rather than "ZAC doesn't
support PKCE at all."

**No action** — both default to `false`. Do **not** turn on
`zac.auth.enablePkce`/`pkceEnabled` for ZAC on this release; it won't do
anything useful until the image is later bumped past the point where ZAC
gained PKCE support.

#### New, and functional with this image: `zac.brpApi.protocollering.verwerking.extendWithZaaktype`

This is the actual feature 5.0.2 ships (confirmed present in the v5.0.2 app
source, unlike PKCE above). Chart 1.0.297 adds `extendWithZaaktype` under
`verwerking`, controlling whether the verwerking register value is extended
with the zaaktype
(`<register>@<zaaktype>` vs. `<register>` alone) — iConnect requires it
`true`, eServices/2Secure `false`. The chart's own bundled default already
sets this to `""`, and podiumd now also sets it explicitly to `false` for
clarity, so there is **no render risk either way** — the template guard that
requires the key to be present (`fail` if `verwerking.header` is set and the
key is entirely absent) is satisfied by the chart's default regardless of
what podiumd or a gemeente `podiumd.yml` sets. Verified by rendering with
the key removed at every layer — it still renders successfully with the
key emitted as `""`.

**Action required** only for an environment that already has
`zac.brpApi.protocollering.verwerking.header` set for **iConnect** — the
default/empty value behaves as "not extended," which is *wrong* for
iConnect (register must be extended with the zaaktype). Set
`extendWithZaaktype: true` explicitly for those environments; eServices/2Secure
environments can leave it at the `false` default. See
`docs/apps/zac/zac-brp-protocollering.md` for the vendor-specific examples
referenced from `values.yaml`.

#### Removed upstream: `additionalAllowedFileTypes`

The chart's top-level `additionalAllowedFileTypes` default and its template
reference (`ADDITIONAL_ALLOWED_FILE_TYPES`) were removed entirely. podiumd
never set this value — **no action**.

#### Chart defaults now harden pod/container security contexts

`podSecurityContext`/`securityContext` defaults were added across the ZAC
main pod, the OPA sidecar, the Gotenberg sidecar, the Solr init containers,
and the `signaleren` CronJob (`seccompProfile: RuntimeDefault`,
`allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, drop all
capabilities, non-root UID/GID on the CronJob). The `signaleren` CronJob also
gets explicit resource requests/limits for the first time (was `{}`).
podiumd doesn't override any of these fields, so the new hardened defaults
apply automatically on upgrade.

**No action required**, but **verify** pods start cleanly after the upgrade
— a newly-enforced `readOnlyRootFilesystem` can surface a latent
write-to-disk assumption that previously went unnoticed.

#### Sidecar images: intentionally left unchanged

Open Policy Agent, Gotenberg and Solr are all left at their current pins
(`1.17.1-static`, `8.34.0`, `9.10.1-slim`) — **not** bumped to the chart's
newer bundled defaults (OPA `1.19.0-static`, Gotenberg `8.35.0`, a newer
Solr digest for the same tag). Those defaults are what ZAC 5.5.0 is tested
against; since this release deliberately keeps the image on 5.0.2, chasing
the 5.5.0-era sidecar versions would be speculative and untested against
the image actually running.

Image / digest: [`images-4.8.5.yaml`](../images/images-4.8.5.yaml).

## Per-environment checklist

Read the whole guide once first. Then, for **every environment** you upgrade,
work through this list top to bottom. The gemeente-values edits (phase B)
are detailed key-by-key in
[`4.8.4-to-4.8.5-values-deltas.md`](4.8.4-to-4.8.5-values-deltas.md).

### A. Prepare

- [ ] **ACR mirror**: mirror the 4.8.5 image set under the strip-registry
      names ([`images-4.8.5.yaml`](../images/images-4.8.5.yaml)) — new
      `maykinmedia/open-beheer` tag `0.9.1` and `infonl/zaakafhandelcomponent`
      tag `5.0.2`. No sidecar image changes this hop (OPA/Gotenberg/Solr
      pins are unchanged).
- [ ] If `zac.brpApi.protocollering.verwerking.header` is already set for
      **iConnect** in this environment's `podiumd.yml`, add
      `extendWithZaaktype: true` — the default (`false`/unset) silently
      does not extend the register, which is incorrect for iConnect (no
      render failure either way, this is a correctness fix, not a blocker).
- [ ] Do **not** enable `zac.auth.pkceEnabled` / `zac.auth.enablePkce` for
      ZAC on this release — the pinned 5.0.2 image has no PKCE support yet.

### B. Deploy

- [ ] Run the deploy pipeline / `helm upgrade`.

### C. Verify

- [ ] Open Beheer: `settings.uwsgi.master: "1"` is still set (the uWSGI
      `--master` workaround remains required on 0.9.1); confirm the login
      redirect and breadcrumbs behave as expected.
- [ ] ZAC pod, OPA sidecar, Gotenberg sidecar, and the `signaleren` CronJob
      all start cleanly under the newly-hardened security contexts (watch
      for read-only-filesystem write failures in pod logs/events).
- [ ] If BRP protocollering is enabled: confirm
      `BRP_VERWERKINGSREGISTER_EXT_WITH_ZAAKTYPE` is set as expected in the
      ZAC ConfigMap.
