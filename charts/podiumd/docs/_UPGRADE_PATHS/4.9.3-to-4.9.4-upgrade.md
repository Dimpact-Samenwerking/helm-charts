# Upgrade guide: PodiumD 4.9.3 → 4.9.4

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

## Before you deploy (every environment)

- **Do not enable the `cms4_migration` init container.** Per-environment
  values must not set `openinwoner.settings.cms4MigrationInitContainer: true`.
  With the init container on, Open Inwoner does not start: the init container
  crashes on 2.4.5 (`FieldError: Unsupported lookup 'node__site_id'`) and the
  web pod never gets past it. Remove such an override; the chart default is
  `false`.
- **Back up the whole `openinwoner` database.** The upgrade is one-way: the
  `cms_treenode` table is removed with all its contents (see below).
- **Mirror the new image.** `maykinmedia/open-inwoner` 2.4.5 must be in the
  registry the environment pulls from; it is listed in
  [`images-4.9.4.yaml`](../images/images-4.9.4.yaml). Environments that pull
  from the old component-named mirror `<acr>/openinwoner` need 2.4.5 there too,
  or a switch to `<acr>/maykinmedia/open-inwoner` (see the gemeente-specific
  notes).

## After you deploy (every environment)

- **Check the CMS.** Maykin asks to check that CMS pages, the page tree, and
  editing and publishing pages in the admin work correctly after the upgrade.
- **Search index:** rebuilt automatically. With
  `openinwoner.settings.searchIndexInitContainer: true` (the chart default; no
  SSC environment overrides it), every Open Inwoner web pod
  start runs `migrate` followed by `search_index --rebuild -f`. An environment
  that switched the init container off must rebuild by hand, so that page titles
  show correctly in search results:

  ```bash
  kubectl --context <kube-context> -n <namespace> exec deploy/openinwoner -c openinwoner -- python /app/src/manage.py search_index --rebuild -f
  ```

- **Monitoring:** Grafana dashboards or alerts that filter on the service name
  `openinwoner` must use the per-role names (see "Notable fixes"). Only relevant
  where the OpenTelemetry overlay is on; the monitoring-logging dashboards
  themselves keep working.

## Changes

### openinwoner 2.4.3 → 2.4.5 (chart 2.4.0, unchanged)

PodiumD 4.9.4 upgrades **openinwoner** from app version 2.4.3
to 2.4.5.

- Image tag pin `openinwoner.image.tag` `2.4.3` → `2.4.5` in
  `charts/podiumd/values.yaml`.

`charts/podiumd/values.yaml` also changes
`openinwoner.settings.cms4MigrationInitContainer` from `true` to `false`
(see below).

2.4.5 is a bugfix release, but it includes 2.4.4, which is a patch release in
name only (upstream
[compare v2.4.3...v2.4.5](https://github.com/maykinmedia/open-inwoner/compare/v2.4.3...v2.4.5)).
2.4.4 upgrades django-cms 4.1.10 → 5.0.11, django-treebeard 4.4 → 5.3.1 and
weasyprint 68.1 → 70.0, and sets the default `OTEL_SERVICE_NAME` per role
(`openinwoner-web`, `openinwoner-celery-worker`, ...). Dashboards or alerts
that filter on `openinwoner` may need to change. There are no new settings or
environment variables. Helm chart `openinwoner` stays
at `2.4.0` in `charts/podiumd/Chart.yaml`.

**The upgrade is one-way in practice.** 2.4.5 upgrades django-cms to 5.0.11.
Its migration `cms 0037_merge_page_treenode` copies the page tree from
`cms_treenode` into new columns on `cms_page` (`path`, `depth`, `numchild`,
`parent_id`, `site_id`). `cms 0038_alter_page_site` then **removes the
`cms_treenode` table with all its contents**, and `cms 0039` drops the
`Page.languages` field and removes duplicate `PageURL` rows. Once any 2.4.5 pod
has started, a 2.4.3 pod fails every request with
`ProgrammingError: relation "cms_treenode" does not exist`.

django-cms ships only a partial, lossy way back. Run from the **2.4.5** image
(the 2.4.3 image does not have migrations 0037–0041), `migrate cms 0036` rebuilds
`cms_treenode` from `cms_page`. It does not restore the `Page.languages` data or
the removed `PageURL` duplicates, and it is untested by Maykin and by us. The only
reliable rollback to 4.9.3 is a restore of the whole `openinwoner` database
(restoring only the table is not enough: `cms_page` and the migration state have
changed too). Take a backup of the `openinwoner` database before upgrading.
Maykin's release notes for 2.4.4/2.4.5 do not mention the table removal or a
backup.

**The `cms4_migration` init container is switched off.** The one-time
Django CMS v3 → v4 migration has run in every environment since 4.8.0.
Against django-cms 5.0.11 the command crashes with
`FieldError: Unsupported lookup 'node__site_id'`, so with the init container
on, the web pod never starts and Open Inwoner is down. Per-environment values
must not enable it: an environment that sets
`openinwoner.settings.cms4MigrationInitContainer: true` in its own values
must remove that override before deploying 4.9.4 (see the values deltas).
Maykin's own chart (up to 2.6.0) still defaults to `true`, so values copied
from its examples turn it back on.

**Scripts that set a homepage or move CMS pages need a transaction.** The
django-cms and django-treebeard versions in 2.4.5 lock the page tree in
`Page.set_as_homepage()` and `Page.move_page()`, and the lock asserts an
active database transaction. A script that calls either method through
`manage.py shell` (autocommit) now fails with
`AssertionError: _lock_tree_roots requires an active transaction`. Wrap such
code in `django.db.transaction.atomic()`, as upstream did for its own
`create_homepage` test helper (2847).

Not affected: the CMS admin (its set-home, move and copy views run in a
transaction), `cms.api.create_page` (atomic itself) and publishing through
djangocms-versioning. Open Inwoner's REST API has no CMS page endpoints. The
regression seed in `podiumd-testautomation` (`seed-oi-cms-pages.sh`) calls
`set_as_homepage()` and needed this fix.

Notable fixes:

- OpenTelemetry works again in the web pod: uWSGI no longer runs with
  `--lazy-apps` (2831), and each role exports its own `OTEL_SERVICE_NAME`
  (`openinwoner-web`, `-celery-worker`, `-celery-beat`, `-celery-monitor`)
  instead of the generic `openinwoner` (2832). This only matters for
  environments with the `values-enable-observability.yaml` overlay. Grafana
  dashboards or alerts that filter on `service.name="openinwoner"` must
  use the per-role names.
- Questions (vragen) are created and the vragen cache is invalidated even
  when creating the interne taak fails; registration failures are logged
  (2878).
- Non-standard digital address changes are pushed to OpenKlant (2852).
- Notifications skip opted-out users instead of aborting (2807).
- Better error handling in the ZGW and KIC `setup_configuration` steps
  (2594), zaken cache key fixes (2786), template-injection hardening of
  `RenderableTag` (2776), django-cms 5.0.11 and dependency security bumps.
