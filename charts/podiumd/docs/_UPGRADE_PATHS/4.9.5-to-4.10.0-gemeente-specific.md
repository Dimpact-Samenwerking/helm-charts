# Gemeente-specific notes — PodiumD 4.9.5 → 4.10.0

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## SSC environments (SSCHostingSync): Objecten 4 migration test

`scripts/migrate-objecten-4.1.0.py` was run over a copy of all 78
SSCHostingSync environments (SSCHostingSync `main`, 2026-10-07): 70 with
objecten/objecttypen, and 8 stubs without. All 70 migrate without errors, a
second run changes nothing, and 67 of the 70 render against the 4.10.0 chart
(the 3 exceptions are below). The general steps are in
[`4.9.5-to-4.10.0-values-deltas.md`](4.9.5-to-4.10.0-values-deltas.md).

`zaak` (in all 70 environments) and `omc` (in 69 of them) exist in both objecten and
objecttypen with different tokens. The objecten token wins, and the script
rewrites the consumers in the values (`zac.objecttypenApi`, the OMC
objecttypen token). Check clients outside the values per environment, see
"Read this first" in the values-deltas doc.

These environments need an extra decision or fix:

### The 8 stubs: environments deployed from ExternalsPodiumD

dim1, dim2, dim3, dimp, icat, info and mayk `ontw`, and dimp `test`. In
SSCHostingSync their `podiumd.yml` is a stub with an `ignored` file, because
they are deployed from the ExternalsPodiumD repo. The script leaves both their
`podiumd.yml` and their `services-gateway.yml` alone. Their objecttypen keeps
running until that environment itself is upgraded to 4.10.0 from
ExternalsPodiumD; only then should SSC repoint its `objecttypen-nginx`
ExternalName (or HTTPRoute) to objecten. Agree the moment with the team that
deploys it.

### dim1 (accp), gene (accp)

- `objecten.image.repository` is `acrprodmgmt.azurecr.io/objecten`, a mirror
  under the old component-named scheme; the other 68 use
  `<acr>/maykinmedia/objects-api`. The script maps both to
  `acrprodmgmt.azurecr.io/maykinmedia/open-object`, the name
  `mirror-strip-registry.py` gives the new image. Nothing extra to do, but
  check the diff for these two.
- `zac.brpApi.apiKey` is a plain string. The 4.10.0 chart needs a map
  `{header: <name>, value: <key>}`; without it the render fails. Fix by hand.

### gene (ontw)

- `objecten.image.repository` points at the test registry
  `acrtestmgmt.azurecr.io`. Mirror `maykinmedia/open-object` (4.1.0) into that
  registry as well, not only into `acrprodmgmt`.

### rott (test)

- The OMC chart requires `omc.settings.omc.auth.jwt.secret` to be at least 64
  characters. In the values template it is a `REP_..._REP` placeholder (23
  characters), so a render of the unsubstituted template fails on it; the
  other environments use longer placeholder names. Check that the real secret
  the pipeline substitutes is at least 64 characters. Unrelated to the
  objecten migration.
- `omc.settings.notify.api.key` is the placeholder
  `REP_NOTIFY_CREDENTIALS_OMC_REP`, which does not match the OMC schema
  pattern for a Notify API key (`<name>-<uuid>-<uuid>`). Check that the real
  value has that form. Unrelated to the objecten migration.
- The only environment whose objecttypen tokens use `value_from` with
  `objecttypen.configuration.secrets`. The script resolves them; check the
  moved secrets in the diff.

### dimp (accp): live check, 2026-10-07

- Tokens: `token-2` and `token-3` exist only in the objecttypen database
  (`migrate-objecttypen-tokens.sh` copies them). `omc`, `Portaal` and `zaak`
  exist in both with different tokens: the objecten token wins.
- Objecttypes: objecttypen has 16, objecten 15, and none is imported yet.
  Run `import_objecttypes objecttypen-api` before the upgrade.

### dim1 (ontw): live check, 2026-10-07 (deployed from ExternalsPodiumD)

- Tokens: `ibz`, `omc`, `openbeheer-token` and `zaak` exist in both with
  different tokens. `ibz` belongs to an external party, which must switch to
  the objecten `ibz` token. Open Beheer's token is rewritten by the script.
- One objecttype that was deleted in objecttypen still existed in objecten
  (0 objects); it was removed on 2026-10-07.
- Unrelated to objecten: the chart only requires
  `keycloak.config.clients.datamigratie.oidcUrl` while that client is enabled
  (the chart default). dim1 has no datamigratie and sets
  `keycloak.config.clients.datamigratie.enabled: false`. Environments without
  datamigratie need the same line.

### zwol (prod)

- `objecten.configuration.data` already lists the tokenauth item
  `openarchiefbeheer` twice (same token). Harmless for setup-configuration,
  but remove the duplicate when touching the file.

## SSC environments: Open Forms 4.0 API group fields

`scripts/migrate-openforms-4.0-api-groups.py` was run over copies of every
environment in SSCHostingSync `main` and ExternalsPodiumD `main`
(2026-10-15).

- **SSCHostingSync:** 70 of the 78 environments set the removed fields; the
  other 8 have no `openformulieren.configuration.data`. Each of the 70 has
  the same shape:
  - `objects_api.groups[0]` (`objects-apis`): `catalogue_domain` and `catalogue_rsin`;
  - `objects_api.groups[1]` (`objects-openzaak-api`): those two plus the three
    `document_type_*` fields;
  - `zgw_api.groups[0]` (`openzaak`): `catalogue_domain` and `catalogue_rsin`.
- **ExternalsPodiumD:** all 8 environments are affected, with the same shape.

All 78 migrate without errors, and the diffs only remove lines (9 per
environment). A second run changes nothing. Open Forms 4.0.2's own
`setup_configuration --validate-only` rejects every unmigrated configuration
with `extra_forbidden` and accepts all 78 migrated ones; it also accepts
them after `migrate-objecten-4.1.0.py`.

The Objects API service URLs need a second change, which
`migrate-objecten-4.1.0.py` now makes too. After the host rewrite,
`objecttypen-api` has the same `api_root` as `objecten-api`, and
`zgw_consumers` allows each `api_root` only once, so Open Formulieren's config
job would fail on `zgw_consumers_service_api_root_key`. `setup_configuration
--validate-only` doesn't touch the database, so it doesn't catch this. The
script removes `objecttypen-api` and points `objecttypes_service_identifier`
at `objecten-api` (77 environments: 70 SSCHostingSync and 7 ExternalsPodiumD,
ontw-dim1 was fixed by hand; Open Beheer the same in 8). In 73 of them
`objecten-api` sent the old objecttypen token
(`REP_OBJECTEN_CREDENTIALS_OBJECTTYPEN_TOKEN_REP`, no objecten token); the
script switches it to the `formulier` token. That assumes the `formulier`
token's Key Vault secret exists, as the objecten config already uses it. Open
Zaak's `objecten-api` (zaakobject validation) sends the same old token in 77
environments (70 SSCHostingSync, 7 ExternalsPodiumD). Open Zaak keeps it, and
the script adds an objecten `tokenauth` item `openzaak` with that token,
`read_only` on the objecttypes of the `zaak` item (the ZAC productaanvraag
objecttype). `zaak` is ZAC's own token, so Open Zaak no longer needs it. No
new Key Vault secret is needed, but the secret's value must differ from every
other objecten token of the environment. Check the kept token in the 4
environments it isn't switched for (`esuite` or already `formulier`): see
[`4.9.5-to-4.10.0-values-deltas.md`](4.9.5-to-4.10.0-values-deltas.md), "One
zgw_consumers service per api_root".

## rott (prod)

- `openformulieren.extraEnvVars` sets `ELASTIC_APM_ENVIRONMENT` and
  `openformulieren.settings.elasticapm` has a token. Open Forms 4.0 removes
  Elastic APM; with `elasticapm.url: ''` it was already off. Both can be
  removed (optional cleanup).
