## openformulieren 3.5.8 → 4.0.2 (chart 1.12.0 → 1.13.0)

- Key `openformulieren.settings.cookieSamesite` was added.
- Key `openformulieren.settings.celery.resultBackend` was added.
- Key `openformulieren.configuration.job.ttlSecondsAfterFinished` was removed.
- Key `openformulieren.settings.celery.resultBackendl` was removed.

`cookieSamesite` is set to `Lax`. The chart turns it into `SESSION_COOKIE_SAMESITE`,
`CSRF_COOKIE_SAMESITE` and `LANGUAGE_COOKIE_SAMESITE`. Before 4.10.0 these
were unset, so Open Forms' own default applied: `None` on HTTPS, which every
environment uses. **This changes cookie behaviour from `None` to `Lax`.**

`Lax` keeps working for forms opened directly and for forms embedded on a
site under the gemeente's own domain (for example `formulier.<gemeente>.nl`
embedded on `www.<gemeente>.nl`), and for the return from DigiD or
eHerkenning via OIDC: that callback is a top-level GET. It breaks forms
embedded with the SDK on a site under another domain, and a direct SAML
DigiD/eHerkenning login with an HTTP-POST ACS: the browser does not send a
`Lax` cookie with those cross-site requests. An environment that embeds
forms that way or logs in through SAML POST keeps the old behaviour with:

```yaml
openformulieren:
  settings:
    cookieSamesite: None
```

In SSCHostingSync `bfc60c3` (2026-10-09) every prod environment serves Open
Forms on its own gemeente domain, and the only extra CORS origin is
`mijn.enschede.nl` (same site). Embeds on other domains are not in the
values, and neither is how DigiD/eHerkenning is connected (that is set up in
the Open Forms admin); check with the gemeente.

`settings.celery.resultBackendl` is renamed because chart 1.13.0 fixed the
typo: with the old name, `CELERY_RESULT_BACKEND` renders empty. An
environment that sets `resultBackendl` itself must rename it; none in
SSCHostingSync `bfc60c3` does.

`configuration.job.ttlSecondsAfterFinished` is removed because chart 1.13.0
dropped it: the setup-configuration job is now a Helm hook that is replaced
on every install or upgrade.

## Namespace portability

No `podiumd.yml` changes are required for deployments in the `podiumd` namespace.

If you deploy into a **different** namespace, set the three operator watch-scopes to
that namespace (they cannot be templated in `values.yaml`):

```yaml
eck-operator:
  managedNamespaces:
    - <namespace>
zac:
  solr-operator:
    watchNamespaces: "<namespace>"
    zookeeper-operator:
      watchNamespace: "<namespace>"
```

See `charts/podiumd/ci/values-namespace-scope.example.yaml` and
`docs/misc/deploying-to-a-custom-namespace.md`. Redis, ClamAV and Kibana use bare
service names, which resolve in the release namespace. `allowedHosts` uses
`.svc.cluster.local`, which matches every namespace.

A gemeente `podiumd.yml` that overrides one of these values with an explicit
`<svc>.podiumd.svc.cluster.local` keeps working in the `podiumd` namespace. Replace it
only when moving to another namespace.
