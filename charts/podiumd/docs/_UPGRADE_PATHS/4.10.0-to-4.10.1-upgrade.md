## Before you deploy (every environment)

Give Open Archiefbeheer's Objecten token `read_and_write` on the
productaanvraag object type, so destroying a zaak can delete its related
objects in Objecten (IN-2784). Run it in the values repositories before
`helm upgrade`; it only edits `podiumd.yml` files, can be run again (a second
run changes nothing) and needs no cluster rights. Environments that go from
4.9.6 straight to 4.10.1 need the same step. Background:
[Reference: Open Archiefbeheer's Objecten permissions](#reference-open-archiefbeheers-objecten-permissions-in-2784).

```bash
S=charts/podiumd/scripts/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py
python3 $S --dry-run --gemeenten-dir <SSCHostingSync>/applications/gemeenten   # preview
python3 $S --gemeenten-dir <SSCHostingSync>/applications/gemeenten             # migrate
python3 $S --check --gemeenten-dir <SSCHostingSync>/applications/gemeenten     # gate: exit 0
```

Repeat for `<ExternalsPodiumD>/applications/gemeenten`. Resolve every CHECK
note before the deploy: see the
[gemeente-specific notes](4.10.0-to-4.10.1-gemeente-specific.md).

## Open Archiefbeheer logs to stdout (IN-3284)

- **Application logs move from a file to stdout.** The podiumd chart now sets
  `openarchiefbeheer.settings.logging.toStdout: true` (with `level: INFO`).
  The openarchiefbeheer chart writes `LOG_STDOUT=False` unless this is set,
  so OAB logged to a file in the container, which Grafana does not collect.
  After the upgrade the OAB logs, such as destruction list processing and
  OIDC login errors, show in Grafana.
- **Celery worker and beat log at `info` instead of `warning`.**
  `openarchiefbeheer.settings.celery.logLevel` goes from `warning` to `info`.
  On `warning` beat logs only its startup banner and the worker a few lines
  a day, so they hardly showed in the Grafana Logs dashboard.
- **More log volume in Loki.** Both changes increase the number of OAB log
  lines.
- An environment that sets `openarchiefbeheer.settings.logging` or
  `openarchiefbeheer.settings.celery.logLevel` in its `podiumd.yml` keeps its
  own value. No SSC environment sets them today.

## Keycloak public hostname for fresh installs (IN-3281)

- **New value, off by default: `keycloak.hostname.useRealmFrontendUrl`.**
  When `keycloak.hostname.hostname` is empty, it makes Keycloak's public
  hostname fall back to `keycloak.config.realmFrontendUrl` instead of
  `keycloak.config.adminFrontendUrl`. It is meant for fresh installs, where
  the admin host as public hostname makes logins fail until the realm import
  has run (see `docs/apps/keycloak/keycloak-BASICS.md`).
- **No action for existing environments.** With the default, the rendered
  Keycloak CR is the same as in 4.10.0, and Keycloak does not restart.
- **Turning it on** where `realmFrontendUrl` differs from `adminFrontendUrl`
  moves the public hostname to the realm host and restarts Keycloak. Admin
  console and admin REST URLs stay on `keycloak.hostname.admin`; the admin
  console login stays on the admin host only while the `import-master-realm`
  Job runs, which needs `keycloak-operator.jobs.ensureOperatorSa.clientSecret`.

## Reference: Open Archiefbeheer's Objecten permissions (IN-2784)

Open Archiefbeheer's Objecten token, the `tokenauth` item
`identifier: openarchiefbeheer` in `objecten.configuration.data`, has no
`permissions` in most environments. Objecten then gives that token no access
to any object: only an `is_superuser` token sees every object type. When Open
Archiefbeheer destroys a zaak, it deletes the zaak's related objects in
Objecten (`DELETE /objects/{uuid}?zaak=<zaak url>`). A delete needs
`read_and_write` on the object's type, so destroying a zaak with a
productaanvraag object fails with 403.

The script adds to each such item without `permissions` or `is_superuser`:

```yaml
permissions:
  - object_type: "REP_ZAC_PRODUCTAANVRAAG_UUID_REP"
    mode: read_and_write
```

- `REP_ZAC_PRODUCTAANVRAAG_UUID_REP` is the existing `zac-productaanvraag-uuid`
  Key Vault secret; no new secret is needed.
- The object type must be in `objecttypes.items` of the same
  `objecten.configuration.data`, by this uuid or by name
  `Productaanvraag-Dimpact`. Objecten's configuration job runs that step before
  `tokenauth` and fails on a permission for an unknown object type. Without it,
  the script leaves the file alone with a CHECK note.
- An item that already has `permissions` is left alone, with a CHECK note when
  it lacks this one.
- Objects of other object types linked to a zaak still fail the destruction:
  give the token `read_and_write` on those types too when an environment
  destroys such zaken.

## Objecttypen job: new Productaanvraag-Dimpact version when the schema changed

The `create-required-objecttypen` job used to add a version only to an
objecttype without one, so a newer schema in the chart never reached an
existing objecttype. It now also publishes a new version for each objecttype
listed in `objecten.create_required_objecttypen_job.updateExistingVersions`
(default: `Productaanvraag-Dimpact`) when the `jsonSchema` of its latest
version differs from the chart's `files/objecttypen/<name>.json`; objecttypes
not listed are never updated. On an existing environment the first deploy of
4.10.1 can therefore add a new Productaanvraag-Dimpact version; later deploys
skip it while the schema is unchanged.

To keep the old behaviour, set the list to empty in the gemeente's
`podiumd.yml`:

```yaml
objecten:
  create_required_objecttypen_job:
    updateExistingVersions: []
```
