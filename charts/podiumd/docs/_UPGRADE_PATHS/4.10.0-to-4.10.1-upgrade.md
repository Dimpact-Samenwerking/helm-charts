> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

For environments already on **4.10.0**. Environments on 4.9.6 go straight to
4.10.1 with [`4.9.6-to-4.10.1-upgrade.md`](4.9.6-to-4.10.1-upgrade.md) instead. The guide has three parts:

## A. Once per cluster

Nothing for this hop.

## B. Once per values repository: migrate the values files

Everything in this section changes files under
`applications/gemeenten/<gemeente>/<env>/`, not the cluster. Do it once,
review the diff against the
[values deltas](4.10.0-to-4.10.1-values-deltas.md), commit.

### B1. Run the two scripts

Both scripts only edit `podiumd.yml` files and need no cluster rights. They
keep comments, quoting and `REP_..._REP` placeholders, show a unified diff
with `--dry-run`, and change nothing on a second run. Run them from a
checkout of the 4.10.1 chart; the scripts are not in the packaged chart.

```bash
pip install ruamel.yaml
S=charts/podiumd/scripts
G=<values repository>/applications/gemeenten

# 1. Preview: a unified diff per file, nothing written
for s in migrate-objecten-openarchiefbeheer-permissions-4.10.1.py migrate-objecten-kiss-logboek-permission-4.10.1.py; do
  python3 "$S/$s" --dry-run --gemeenten-dir "$G"
done

# 2. Migrate
python3 "$S/migrate-objecten-openarchiefbeheer-permissions-4.10.1.py" --gemeenten-dir "$G"  # OAB token: read_and_write on productaanvraag
python3 "$S/migrate-objecten-kiss-logboek-permission-4.10.1.py" --gemeenten-dir "$G"        # KISS logboek token: read_only on Activiteitenlog

# 3. Pipeline gate: exit 1 while a file still needs migrating
rc=0
for s in migrate-objecten-openarchiefbeheer-permissions-4.10.1.py migrate-objecten-kiss-logboek-permission-4.10.1.py; do
  python3 "$S/$s" --check --gemeenten-dir "$G" || rc=1
done
[ "$rc" -eq 0 ]
```

Run it for `<SSCHostingSync>` and for `<ExternalsPodiumD>`.

| Script | Changes | Needs a person when |
| --- | --- | --- |
| `migrate-objecten-openarchiefbeheer-permissions-4.10.1.py` | Gives Open Archiefbeheer's Objecten `tokenauth` item `read_and_write` on the productaanvraag object type, so destroying a zaak can delete its objects (IN-2784). | It prints a CHECK note. See [Open Archiefbeheer's Objecten permissions](#reference-open-archiefbeheers-objecten-permissions-in-2784). |
| `migrate-objecten-kiss-logboek-permission-4.10.1.py` | Gives the `tokenauth` item that holds KISS's logboek token `read_only` on the Activiteitenlog object type, so KISS shows ITA's activities (kiss-2). | It prints a CHECK note. See [KISS's logboek token](#reference-kisss-logboek-token-kiss-2). |

Resolve every CHECK note before the deploy. The ones found in the values
repositories are in the
[gemeente-specific notes](4.10.0-to-4.10.1-gemeente-specific.md).

### B3. Render before the deploy day

Render the migrated values (`helm template` with the 4.10.1 chart) for every
environment. Two render guards changed:

| The render fails while | Fix |
| --- | --- |
| `keycloak.config.clients.monitoring.secret` or `.datamigratie.secret` is empty while that client's `oidcUrl` is set and `enabled` is not `false` | set it. Without an `oidcUrl` the client is not created and needs no secret (see [Changes that need no action](#changes-that-need-no-action)). |
| `openinwoner.extraEnvVars` sets a variable that Open Inwoner 2.5.0 ignores (the message names them) | move the setting to `openinwoner.configuration.data` and remove the variable; the list is in [Open Inwoner 2.5.0](#reference-open-inwoner-250-in-3332). |

## C. Per environment, before the deploy day

Set the target once; every command below names it:

```bash
CTX=<kube-context-of-the-environment>   # never the current context
NS=podiumd
```

### C1. Mirror the images

The registry the environment pulls from must hold everything in
[`images-4.10.1.yaml`](../images/images-4.10.1.yaml), by digest:
`openformulieren/open-forms` 4.0.7, `maykinmedia/open-inwoner` 2.5.0 and the
other new versions in that file.

Mirror by digest, not by tag: six images were re-published under the same
tag with a new digest (`curlimages/curl` 8.23.0, `postgres` 16.15-alpine,
`keycloak` and `keycloak-operator` 26.8.1, `solr` 9.11.0-slim, `clamav`
1.5.4; the manifest marks them "digest changed"). A mirror that skips a
name and tag it already has keeps the old digest, and the pull fails. Copy
with `skopeo copy --all --preserve-digests`: without `--preserve-digests` a
copy can store the manifest under another digest.

### C2. Check the Keycloak clients of disabled components

The realm import now deletes the client of every component that is not
installed (`<component>.enabled: false`), with its service-account user and
role mappings. Make sure nothing outside the chart logs in with such a
client. See
[Keycloak clients of components that are not installed](#reference-keycloak-clients-of-components-that-are-not-installed).

### C3. Check Open Forms' service certificate bundles

Open Forms 4.0.7 is an image change only: no database migrations, no new
settings. One behaviour changes (4.0.4; 4.0.5 for SOAP and StUF): where extra
root certificates are added to Open Forms' trust store, a service with its own
server certificate bundle is now verified with that bundle. A call that worked
on 4.0.2 fails when that bundle is outdated. In the Open Forms admin, check the
server certificate bundle of every service that has one, before the deploy.

### C4. Plan the window

- **OpenBao restarts**: its server configuration changes. With the static
  seal the pods unseal themselves; with the Shamir seal they stay sealed, and
  nothing can read a secret from OpenBao, until D2.
- **redis-ha restarts once**, one pod at a time: its readiness probe changes.
- **Open Formulieren** rolls to 4.0.7.
- **Open Inwoner** rolls to 2.5.0; its migration converts every notification
  record, which takes longer with a large table (C5). The migration is one way:
  see F.
- **Keycloak is recreated once**: its update check fails on the 4.10.0 pod
  template, so the operator stops every pod and starts them again; logins fail
  until Keycloak is back. From 4.10.1 on, a patch release rolls the pods one at
  a time.
- **A first KISS website, with `networkPolicies.enabled`**: add it in a deploy
  after the 4.10.1 one. Its crawler hook runs before Helm updates the
  Elasticsearch NetworkPolicy, so in the 4.10.1 deploy it still meets the 4.10.0
  policy.

### C5. Count Open Inwoner's notification records

Before `helm upgrade`, still on 2.4.9. The 2.5.0 migration converts every row
of this table separately. The count only reads: run it any time, as often as
needed. It needs `kubectl exec` rights in `NS`.

```bash
kubectl --context "$CTX" -n "$NS" exec deploy/openinwoner -c openinwoner -- \
  python /app/src/manage.py shell -c \
  "from notifications.models import NotificationRecord; print(NotificationRecord.objects.count())"
```

With hundreds of thousands of rows, prune first:
`python /app/src/manage.py prune_notification_records --dry-run` (same `exec`)
shows what the configured retention deletes, the command without `--dry-run`
deletes it. An interrupted prune leaves the records it did not reach; run it
again.

## D. The deploy run

Per environment, in this order. `CTX` and `NS` as set in C.

### D1. `helm upgrade`

Only when the previous deploy ran less than 10 minutes ago: a Job still there
from it blocks `helm upgrade` (`field is immutable`), and `openbeheer-config`,
which is not a hook, is not run again. Delete them first; safe to run twice:

```bash
kubectl --context "$CTX" -n "$NS" delete job --ignore-not-found \
  create-required-objecttypen-job create-required-catalogi-job import-master-realm-job ensure-podiumd-admin-user \
  openbeheer-config
```

Then run the deploy as usual, with the migrated `podiumd.yml`.

### D2. OpenBao environments only

After the deploy, as after every deploy,
`charts/podiumd/scripts/openbao-activate.sh` from a checkout of the 4.10.1
chart. With the Shamir seal it unseals the restarted pods; with the static
seal it finds them unsealed. Safe to run twice; `--check` changes nothing
and only reports the status.

### If the run fails

| Symptom | Cause and fix |
| --- | --- |
| the render fails on `keycloak.config.clients.<monitoring or datamigratie>.secret` | B3. |
| the render fails on `openinwoner.extraEnvVars` | B3. |
| a pod cannot pull `open-forms:4.0.7`, `open-inwoner:2.5.0`, `curl:8.23.0` or `solr:9.11.0-slim` | the registry lacks the image by digest: C1. |
| OpenBao answers `503` and reports it is sealed | Shamir seal after the restart: D2. |
| `helm upgrade` cannot change a Job (`field is immutable`) | a Job from a deploy less than 10 minutes earlier: D1, then deploy again. |
| `keycloak-update-job` fails with `NoSuchFileException` on `quarkus-application.dat` | expected once: the operator recreates Keycloak (C4). Delete the failed Job. |
| an Open Forms registration or prefill call fails on the server certificate | the service's own certificate bundle is outdated: C3. |
| the Objecten configuration Job fails on a permission for an unknown object type | a permission added by hand for an object type that is not in `objecttypes.items` of the same `objecten.configuration.data`: add the object type or remove the permission. |

## E. After the deploy

### E1. Smoke tests

- Open Formulieren: the admin pages render (4.0.7 fixes blank admin pages)
  and a test form submits.
- KISS: a contact's ITA activities show.
- Open Archiefbeheer: a destruction list with a zaak that has a
  productaanvraag object is processed; its logs show in Grafana.
- OpenBao environments: the Frank!Gateway answers through its inways.
- Open Inwoner: a DigiD login (or the mock) reaches 'Mijn profiel'.

### E2. Open Inwoner: browser policies and content

Checks in the browser and the admin; they change nothing and can be repeated.
Background: [Open Inwoner 2.5.0](#reference-open-inwoner-250-in-3332).

- **Technical administrator**: open the public site and the admin, also
  logged in as staff, and check custom JavaScript, embedded widgets, map tiles
  and embedded Open Formulieren forms. A blocked source shows as an error in
  the browser console; add it in the CSP settings in the admin. Only as a last
  resort, set `openinwoner.settings.cspReportOnly: true` (or
  `permissionsPolicyReportOnly: true` for location or camera) and deploy
  again; the policy is then reported but not enforced.
- **Functional administrator**: check the content the data migrations
  changed:
  - rich text with links: links with a scheme other than `http`, `https`,
    `mailto` or `tel` are removed; the migration logs each one as a warning;
  - the CMS page tree: the user menu only shows 'Mijn profiel', so every other
    part, including the new 'Mijn vragen' page, must be a published page;
  - the footer and the login banner (their plugin lists are now applied);
  - the colours, where they were never set;
  - the contact form page;
  - 'Mijn vragen' and 'Mijn profiel', which use OpenKlant (its service moves
    to `auth_type=api_key`).
- **Both**: change OIDC, ZGW service and site settings in the values, not in the admin: every deploy overwrites them.

## F. Rollback

- **Keycloak clients of disabled components**: `helm rollback` to 4.10.0 runs
  the old realm import, which creates the clients again with the secrets kept
  in `keycloak-podiumd-realm-secrets`. Role mappings added by hand to their
  service-account users do not come back.
- **Open Inwoner**: 2.5.0 migrates its database one way (the notification
  record key, the content clean-up). Going back to 2.4.9 needs the Open Inwoner
  database restored from the backup taken before the deploy.
- **Everything else**: `helm rollback podiumd <last 4.10.0 revision>`. The
  Objecten permissions added in B1 can stay.

## Changes that need no action

One line each. The chart handles them; an environment that sets the key
itself keeps its own value.

- **The Elasticsearch NetworkPolicy always admits KISS's crawler hook**, also
  without a website, under the Job name KISS gives it (also with an empty
  `kiss.fullnameOverride`); for a first website see C4.
- **Open Archiefbeheer logs to stdout** (`openarchiefbeheer.settings.logging.toStdout: true`,
  level `INFO`) and its Celery worker and beat at `info` instead of `warning`
  (IN-3284): its logs show in Grafana, with more lines in Loki.
- **New, off by default: `keycloak.hostname.useRealmFrontendUrl`** (IN-3281):
  for fresh installs; see [Keycloak public hostname](#reference-keycloak-public-hostname-for-fresh-installs-in-3281).
- **Keycloak clients `monitoring` and `datamigratie` are only created with an
  `oidcUrl`**: set one, or `enabled: false`, and the realm keeps the same
  clients.
- **`keycloak-repair-client-scopes` and `pabc-keycloak-groups` run on the
  podiumd ServiceAccount without a token** (IN-1824).
- **`keycloak-repair-client-scopes` reads all client state up front**; its CPU
  limit and that of the realm import Jobs go to `"2"`.
- **Configuration Jobs retry in their container** every 5 s for up to 10
  minutes, instead of the Job back-off.
- **`openbao-activate.sh` is faster**: `helm get metadata` in the preflight,
  and no rollout wait when no old gateway token is revoked.
- **Frank!Gateway re-reads OpenBao every 300 s** (IN-3417): a removed consumer
  or a rotated API key takes effect without a gateway restart. The gateway
  pods restart once.
- **redis-ha replicas close app connections older than 10 seconds** on a pod
  that runs as a replica, so an app does not stay on a replica where every
  write fails with `READONLY`.
- **New Job `zac-restart-after-openzaak-config-<revision>`**
  (`zac.restartAfterOpenzaakConfig.enabled`, on): restarts ZAC only when it
  started before Open Zaak had its client; on a normal upgrade it does
  nothing. A deploy script that restarts ZAC for this can drop that step.
- **The objecttypen job can update existing objecttypes, off by default**
  (`objecten.create_required_objecttypen_job.updateExistingVersions`, IN-2890):
  see [Reference: objecttype schema updates](#reference-objecttype-schema-updates-in-2890).
- **Zaakbrug's JDBC entry in the docs has no name**, so any release name
  works.
- **ZAC's office converter memory limit is 2Gi instead of 1Gi**
  (`zac.office_converter.resources`, podiumd-chart-39): large Word files with
  many photos no longer OOM-kill Gotenberg. The pod restarts once.
- **The Maykin apps' configuration Jobs retry 12 times instead of 6**
  (`<app>.configuration.job.backoffLimit`, podiumd-chart-31), so on a fresh
  install they outlast Keycloak still pulling its image.
- **More memory for large documents**: Open Formulieren requests 1792Mi
  instead of 1Gi, its worker 1536Mi instead of 1Gi and Open Zaak 1Gi instead
  of 512Mi; ZAC's nginx memory limit is 256Mi instead of 128Mi. The pods
  restart once.
- **Open Inwoner 2.5.0 needs no values change** (IN-3332): see
  [Open Inwoner 2.5.0](#reference-open-inwoner-250-in-3332).
- **Open Inwoner's browser report endpoint `/api/reporting-api/` is on and rate
  limited in its nginx** (`openinwoner.settings.reportingApi`,
  `openinwoner.nginx.config.reportingApiRateLimit`).
- **New Open Inwoner settings, off by default**: `settings.enableInteractiveChecks`,
  `settings.showLabelEnvironment`, `settings.customProduct`,
  `settings.cache.notificationThrottle` and `beat.livenessProbe`.

## Reference: Open Archiefbeheer's Objecten permissions (IN-2784)

Open Archiefbeheer's Objecten token, the `tokenauth` item
`identifier: openarchiefbeheer` in `objecten.configuration.data`, has no
`permissions` in most environments. Objecten then gives that token no access
to any object: only an `is_superuser` token sees every object type. When Open
Archiefbeheer destroys a zaak, it deletes the zaak's related objects in
Objecten (`DELETE /objects/{uuid}?zaak=<zaak url>`). A delete needs
`read_and_write` on the object's type, so destroying a zaak with a
productaanvraag object fails with 403.

The script adds to each such item without `permissions` or `is_superuser`:

```yaml
permissions:
  - object_type: "REP_ZAC_PRODUCTAANVRAAG_UUID_REP"
    mode: read_and_write
```

- `REP_ZAC_PRODUCTAANVRAAG_UUID_REP` is the existing `zac-productaanvraag-uuid`
  Key Vault secret; no new secret is needed.
- The object type must be in `objecttypes.items` of the same
  `objecten.configuration.data`, by this uuid or by name
  `Productaanvraag-Dimpact`. Objecten's configuration job runs that step before
  `tokenauth` and fails on a permission for an unknown object type. Without it,
  the script leaves the file alone with a CHECK note.
- An item that already has `permissions` is left alone, with a CHECK note when
  it lacks this one.
- Objects of other object types linked to a zaak still fail the destruction:
  give the token `read_and_write` on those types too when an environment
  destroys such zaken.

## Reference: objecttype schema updates (IN-2890)

The `create-required-objecttypen` job adds a version only to an objecttype
without one, so a newer schema in the chart does not reach an objecttype that
already has a version. For each objecttype named in
`objecten.create_required_objecttypen_job.updateExistingVersions` (empty by
default), the job publishes a new version when the `jsonSchema` of the latest
**published** version differs from the chart's `files/objecttypen/<name>.json`.
Draft versions are ignored. Objecttypes not listed are never updated.

A listed objecttype's own published versions are superseded by the chart's
schema on every deploy, so only opt in for a type the environment does not
publish versions of itself. To opt in, in the gemeente's `podiumd.yml`:

```yaml
objecten:
  create_required_objecttypen_job:
    updateExistingVersions:
      - Productaanvraag-Dimpact
```

The first deploy after opting in can add a new version; later deploys skip
the type while the schema is unchanged.

## Reference: KISS's logboek token (kiss-2)

KISS reads the ITA Activiteitenlog (logboek) from Objecten with
`kiss.settings.logboek.token`, on the object type at the end of
`kiss.settings.logboek.objectTypeUrl` (`REP_ITA_ACTIVITEITENLOG_UUID_REP`).
In most environments that token is the one of the `contact` `tokenauth` item,
whose permissions do not include the Activiteitenlog. Objecten then answers
200 with an empty list, so KISS shows no ITA activity and nothing reports an
error.

The script adds to each `tokenauth` item whose `token` equals
`kiss.settings.logboek.token` (the same value or the same `REP_..._REP`
placeholder):

```yaml
  - object_type: "REP_ITA_ACTIVITEITENLOG_UUID_REP"
    mode: read_only
```

- `read_only` is enough: KISS only reads the logboek; its Objecten proxy
  refuses anything but `GET`.
- An item with `is_superuser: true` or with any permission on the object type
  is left alone. An item without `permissions` gets a CHECK note.
- The token is matched exactly. When `kiss.settings.logboek.token` is another
  placeholder or a literal value for the same secret, the script cannot see
  that and reports a CHECK note: add the permission by hand to the item that
  holds KISS's logboek token.
- The object type must be in `objecttypes.items` of the same
  `objecten.configuration.data`, by this uuid or by name `Activiteitenlog`;
  without it the script leaves the file alone with a CHECK note.
- Values split over several files (KISS in one, Objecten in another) are not
  covered: the script needs both in the same file.
- A file with `kiss.enabled: false` is not edited. When its matching item lacks
  the permission, a CHECK note says so: an overlay may enable KISS, and then
  the permission is added there or by hand.

## Reference: Keycloak clients of components that are not installed

Before 4.10.1 the podiumd realm got a client for every component, enabled or
not; only openvtb, zaakbrug and the Frank!Gateway dashboards were guarded. Now
each client, its client roles, its entries in the groups' `clientRoles`, the
OpenBao uploaders group, the ZAC roles mapper and the ZAC and PABC
service-account users are only rendered for a component that is installed.

The realm import (keycloak-config-cli with remote state) deletes the clients
it created before once they leave the render, with their service-account
users and role mappings. Roles, groups and identity providers are not
deleted, and clients created by hand are not touched. The client secrets stay
in the Secret `keycloak-podiumd-realm-secrets`, so turning a component on
again recreates its client with the same secret.

## Reference: Keycloak public hostname for fresh installs (IN-3281)

`keycloak.hostname.useRealmFrontendUrl` (default `false`): when
`keycloak.hostname.hostname` is empty, Keycloak's public hostname falls back
to `keycloak.config.realmFrontendUrl` instead of
`keycloak.config.adminFrontendUrl`. It is meant for fresh installs, where the
admin host as public hostname makes logins fail until the realm import has
run (see `docs/apps/keycloak/keycloak-BASICS.md`).

- With the default, the Keycloak CR renders as in 4.10.0 and Keycloak does
  not restart.
- Turning it on where `realmFrontendUrl` differs from `adminFrontendUrl`
  moves the public hostname to the realm host and restarts Keycloak. Admin
  console and admin REST URLs stay on `keycloak.hostname.admin`; the admin
  console login stays on the admin host only while the `import-master-realm`
  Job runs, which needs `keycloak-operator.jobs.ensureOperatorSa.clientSecret`.

## Reference: Open Inwoner 2.5.0 (IN-3332)

Upstream release notes:
[Open Inwoner 2.5.0 changelog](https://github.com/maykinmedia/open-inwoner/blob/v2.5.0/CHANGELOG.rst).

- **Removed environment-variable configuration.** 2.5.0 ignores every variable
  that starts with `KIC_`, `ADMIN_OIDC_`, `DIGID_OIDC_`, `DIGID_SAML_`,
  `EHERKENNING_OIDC_`, `EHERKENNING_SAML_`, `CMS_` or `SITE_` (except
  `SITE_ID`), most `ZGW_` variables, `OIP_ORGANIZATION`,
  `ACTION_REQUIRED_DEADLINE_DAYS` and `SEARCH_ZERO_RESULTS_TEXT`. The
  configuration goes in `openinwoner.configuration.data` (setup-configuration
  YAML); the render fails while `openinwoner.extraEnvVars` still sets one. The
  steps `oidc_db_config`, `zgw_consumers` and `sites_config` are unchanged.
  `openinwoner.settings.extraEnvVars` is not read by the subchart: variables
  there never reach the pods.
- **The configuration Job overwrites admin changes.** It runs on every
  `helm upgrade` and overwrites every field of the steps in
  `openinwoner.configuration.data`: `oidc_db_config_admin_auth` (also the
  DigiD, eHerkenning and eIDAS OIDC clients), `zgw_consumers` and
  `sites_config`. An admin change to them is lost at the next deploy: change
  them in the values. This is how setup-configuration works ("Running
  setup-configuration more than once" in the 2.5.0 docs), not a 2.5.0 change.
- **Embedded Open Formulieren forms.** The Content Security Policy must allow
  the Open Formulieren host: set `OPEN_FORMS_DOMAIN` in
  `openinwoner.extraEnvVars`, or add the host in the CSP settings in the
  admin. `OPEN_FORMS_DOMAIN` works as in 2.4; new in 2.5.0 is that the policy
  also applies to staff.
- **ClamAV and KvK.** 2.5.0 adds setup-configuration steps for both
  (`site_config`, `kvk_config`). The chart keeps its own Jobs
  (`openinwoner.clamavConfigJob`, `openinwoner.kvk`); the fields they write
  are unchanged.
- **Browser report endpoint.** Browsers send Content Security Policy and
  Permissions Policy violations to `/api/reporting-api/`, without
  authentication. The nginx sidecar limits it to 10 requests per minute with a
  burst of 10. Behind the gateway nginx sees the gateway's address, so all
  browsers share that limit; reports above it get 429 and are dropped, the
  site itself is not affected. `openinwoner.settings.reportingApi.enabled: false`
  turns the endpoint off.
- **Celery beat liveness probe.** 2.5.0 schedules a check task every minute,
  so `openinwoner.beat.livenessProbe.enabled: true` restarts a beat that
  stopped scheduling tasks.
- **Announced for the next feature release:** all logs as JSON, including the
  web server's, and only uncaught errors to Sentry.
