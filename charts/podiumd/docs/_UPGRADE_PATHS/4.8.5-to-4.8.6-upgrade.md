# Upgrade guide: PodiumD 4.8.5 → 4.8.6

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

This is the upgrade guide for environments already on **4.8.5**.

## Component versions (4.8.6 vs 4.8.5)

| Component | App version | Helm chart | Notes |
| --- | --- | --- | --- |
| Keycloak Operator (server + operator images) | 26.6.4 → 26.7.2 | 1.12.1 → 1.13.0 | security update, spans 26.7.0/26.7.1/26.7.2; **CRD changes — apply manually, see [operators-crds](4.8.5-to-4.8.6-operators-crds.md)** |

## Changes

### Keycloak 26.6.4 → 26.7.2 (security, spans three upstream releases)

4.8.6 bumps the Keycloak server **and** operator images from `26.6.4` to
`26.7.2`, and the adfinis `keycloak-operator` chart dependency from `1.12.1`
to `1.13.0` (`appVersion` 26.7.2). This hop skips over `26.7.0` and `26.7.1`
directly to `26.7.2`, so all three releases' fixes apply.

`26.7.0` is a **feature** release (SCIM API preview, multi-cluster HA preview,
step-up authentication for SAML clients, Identity Brokering API v2) plus 4
CVE fixes. `26.7.1` and `26.7.2` are pure patch releases, together fixing
another 19 CVEs. Combined, this hop resolves **23 CVEs**. The two most
relevant to a standard podiumd deployment (Fine-Grained Admin Permissions v2
and SAML identity brokering are not enabled here, so those CVEs are lower
priority for us):

- **CVE-2026-18963** — unauthenticated account takeover via a reset-credentials
  flow bypass.
- **CVE-2026-15571** — predictable account-linking hash enables account
  takeover via a malicious OIDC client.
- **CVE-2026-9796** — admin role rename TOCTOU bypasses `checkAdminRoles`,
  realm-wide privilege escalation from `manage-clients`.
- **CVE-2026-4629** — privilege escalation via hardcoded role mapper
  injection in `manage-clients`.

Full lists: [26.7.0](https://github.com/keycloak/keycloak/releases/tag/26.7.0),
[26.7.1](https://github.com/keycloak/keycloak/releases/tag/26.7.1),
[26.7.2](https://github.com/keycloak/keycloak/releases/tag/26.7.2).

#### Action required

The image pins are already in `values.yaml` and
[`images-4.8.6.yaml`](../images/images-4.8.6.yaml). **But this hop does
change CRDs** — unlike 4.7.4's Keycloak bump, where the CRDs were verified
byte-identical. Diffed adfinis 1.12.1 vs 1.13.0's bundled `crds/` directly:
one existing CRD gets additive-only new fields, and **two brand-new CRDs**
(`KeycloakOIDCClient`, `KeycloakSAMLClient`) ship with their own operator
controllers/RBAC. `helm upgrade` never applies CRD changes — apply them
manually before rollout. See
[`4.8.5-to-4.8.6-operators-crds.md`](4.8.5-to-4.8.6-operators-crds.md) for
the full breakdown and the exact commands.

> **Caveat — operator image digest pinning differs from every other image.**
> The operator image is rendered by the adfinis subchart, which builds the ref
> as `repository:tag@sha256:{{ operator.image.sha }}` using a **separate `sha`
> field** — not by appending a digest to the tag. So, unlike `keycloak.image`
> (and all other PodiumD images, which take `tag: "<ver>@sha256:<digest>"`),
> the operator's `tag` must be **just the version**, with the digest in the
> sibling `sha` field:
>
> ```yaml
> keycloak-operator:
>   operator:
>     image:
>       tag: "26.7.2"        # NOT "26.7.2@sha256:…"
>       sha: "f6079999aa773f1846de01c9014d19c3c677d35570361fd7c01c0830836e4041"
> ```
>
> Embedding `@sha256:...` directly in `tag` produces an invalid **double
> digest** at render time (`…:26.7.2@sha256:xxx@sha256:yyy`) once the template
> appends the separate `sha` field. This hop also found the adfinis 1.13.0
> chart's own bundled default `operator.image.sha` to be stale (it doesn't
> match any manifest published under the `26.7.2` tag), so the explicit
> override above is required, not optional.
