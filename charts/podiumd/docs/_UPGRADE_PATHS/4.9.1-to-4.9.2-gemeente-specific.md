# Gemeente-specific notes — PodiumD 4.9.1 → 4.9.2

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## All gemeenten — OpenArchiefbeheer's Objecten token has no permissions scope

Objecten's `tokenauth` item for `identifier: openarchiefbeheer` grants
OpenArchiefbeheer's token unrestricted access, unlike every other tokenauth
item in the same file (`zaak`, `ita`, `omc`, ...), which already scope access
via a `permissions` block. This was checked directly against every gemeente
`podiumd.yml` in both `ExternalsPodiumD` and `SSCHostingSync` (84 files,
2026-09-16):

- **69 files** have the `openarchiefbeheer` tokenauth item without
  `permissions` — effectively every accp/prod environment, plus `dim1 (ontw)`.
- **15 files** need no action: either no `objecten` section at all, or
  OpenArchiefbeheer has no Objecten tokenauth item configured yet (`dim2`,
  `dimp` ontw/test, `icat` ontw/test, `info` ontw, `mayk` ontw, `gene` ontw).

**Action**: run
[`charts/podiumd/scripts/migrate-objecten-openarchiefbeheer-permissions-4.9.2.py`](../../scripts/migrate-objecten-openarchiefbeheer-permissions-4.9.2.py)
against both gemeenten directories (`--dry-run` first) as part of the 4.9.2
rollout, on every environment — not just a subset. It adds:

```yaml
permissions:
  - object_type: "REP_ZAC_PRODUCTAANVRAAG_UUID_REP"
    mode: read_only
```

to the `openarchiefbeheer` tokenauth item, matching the restriction already
used for the same object type elsewhere (e.g. the `omc` tokenauth item).
`REP_ZAC_PRODUCTAANVRAAG_UUID_REP` resolves to the existing
`zac-productaanvraag-uuid` Key Vault secret — no new secret needed. The script
only touches files where the item exists and has no `permissions` yet, so it
is safe to re-run and a no-op on the 15 files above.
