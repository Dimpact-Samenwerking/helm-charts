# Gemeente-specific notes — PodiumD 4.9.1 → 4.9.2

Findings for this hop that apply to a **specific gemeente or environment** —
not to the release in general — are collected here: data quirks, local
overrides, hosting particulars, incident follow-ups.

## Gemeenten that have activated KISS, on `accp` and `prod`

In KISS 3.x, in PodiumD 4.9.x, KISS is abandoning Elastic Enterprise Search.
With this change, the way KISS queries Elasticsearch has also changed.
Where this used to be done via a meta-engine in Enterprise Search, KISS now
queries the Elasticsearch indices directly.
As a consequence all indices now show up in the interface, even if they
contain no data. And the KISS helm-chart creates an index for every
syncJob in the helm-values.

The sources that are indexed vary per gemeente, especially where Kennisbank
and VAC are cocerned. Some use Kennisbank not VAC, some use VAC not Kennisbank.
And some don't use either of them, but use only a website or also a Sharepoint
crawler.

PodiumD and KISS has by default been enabled for most gemeenten, also with
three syncJobs defined: Kennisbank, VAC and Smoelenboek. To prevent the empty
indices to show up in the interface, the values for each Gemeente that has
activated Contact should match the actual search sources that gemeente uses.
And before deploy the obsolete indices should be deleted.

The steps described below should be executed on both ACCP and PROD environments
of each gemeente.

Below that is a list, per gemeente, of the actual sources they use, the indices
that need to deleted, and the correct values-snippet for `<gemeente>/accp/podiumd.yml` .
`<gemeente>/prod/podiumd.yml` should be changed accordingly.

### Steps to follow

1. Delete the indicated indices:
   a. Change the Kubectl context to the context of the gemeente in question
   b. For each index, run the script [`charts/podiumd/scripts/delete-es-index.sh`](../../scripts/delete-es-index.sh).
   For instance `./<path-to-the-script>/delete-es-index.sh "search-vac"`
2. Update the values for `kiss.settings.syncjobs` in `podiumd.yml` before deploying PodiumD 4.9.2

## Gemeenten that use Open Formulieren together with Open Klant

Open Formulieren can read and write communication preferences (e-mail address,
phone number) of a citizen or company in Open Klant. It does this through the
**Communication preferences** prefill plugin and the **Profile**
(`customerProfile`) form component. Upstream documentation:
[communication_preferences.rst](https://github.com/open-formulieren/open-forms/blob/3.5.8/docs/configuration/prefill/communication_preferences.rst).

Until now no gemeente `podiumd.yml` defines this connection. From 4.9.2 the
connection is part of the standard PodiumD configuration: the commented example in
[`values.yaml`](../../values.yaml) (`openformulieren.configuration.data` →
`zgw_consumers.services`, and `openklant.configuration.data` → `tokenauth.items`)
shows the reference setup.

This applies to every gemeente/environment where both `openklant.enabled` and
`openformulieren.enabled` are `true`. That is all `test`, `accp` and `prod`
environments at the time of writing.

### Steps to follow

1. **Create the token secret** (once per environment)
   * Generate a new random token, for example `openssl rand -hex 20`.
   * Store it in the environment's Key Vault as
     `openklant-credentials-openformulieren-token`. Also add the name to the
     secret list in `keyvault.tfvars`.
   * Map it in the deploy pipeline next to the other Open Klant tokens:
     `OPENKLANT_CREDENTIALS_OPENFORMULIEREN_TOKEN: $(openklant-credentials-openformulieren-token)`.
     The placeholder `REP_OPENKLANT_CREDENTIALS_OPENFORMULIEREN_TOKEN_REP` is then
     available in `podiumd.yml`.

2. **Register the token in Open Klant.** In `<gemeente>/<env>/podiumd.yml`, add
   an item under `openklant.configuration.data` → `tokenauth.items`:

   ```yaml
             - identifier: openformulieren
               token: "REP_OPENKLANT_CREDENTIALS_OPENFORMULIEREN_TOKEN_REP"
               contact_person: Dimpact
               email: servicedesk@dimpact.nl
   ```

3. **Add the Klanten API service to Open Formulieren.** In the same file, add a
   service under `openformulieren.configuration.data` →
   `zgw_consumers.services`. Use the environment's own Open Klant hostname
   (`acc-openklant.<domein>` on accp, `openklant.<domein>` on prod), the same
   one the other components use for their `klanten-api` service:

   ```yaml
             - identifier: openklant-api
               label: Open Klant - Klantinteracties API
               api_root: "https://acc-openklant.<domein>/klantinteracties/api/v1/"
               api_type: kc
               auth_type: api_key
               header_key: Authorization
               header_value: "Token REP_OPENKLANT_CREDENTIALS_OPENFORMULIEREN_TOKEN_REP"
   ```

   * `api_type` **must** be `kc` (Klanten API). Otherwise the API group Job (step 4)
     rejects the service, and it does not show up in the admin dropdown.
   * Make sure `zgw_consumers_config_enable: true` is set (it is already set in
     every gemeente that configures Open Formulieren services).

4. **Enable the Customer interactions API group Job.** Open Formulieren
   3.5.x has no setup-configuration step for the "Customer interactions API
   group", so it cannot be set in `configuration.data`. The chart creates it
   with the opt-in Job `openformulieren-configure-customer-interactions`
   (see [`templates/openformulieren-configure-customer-interactions.yaml`](../../templates/openformulieren-configure-customer-interactions.yaml)).
   In the same file, add:

   ```yaml
   openformulieren:
     customerInteractionsConfigJob:
       enabled: true
   ```

   The defaults (`serviceIdentifier: openklant-api`, `groupIdentifier:
   open-klant`, `groupName: Open Klant`) match the service from step 3. Only
   override them if you used a different service identifier.

5. **Deploy PodiumD 4.9.2.**
   * The `openklant` and `openformulieren` setup-configuration Jobs create the
     token and the service.
   * The `openformulieren-configure-customer-interactions` Job then creates (or
     updates) the API group. If the service does not exist yet, the Job fails
     and Kubernetes retries it (`backoffLimit: 15`, `activeDeadlineSeconds:
     1200`) until the setup-configuration Job has run. A few failed pods
     right after deploy are expected. The Job is idempotent.
   * The Job name ends in a checksum of its pod template, for example
     `openformulieren-configure-customer-interactions-4f5b668e3f`. A change to
     the image or to a `customerInteractionsConfigJob` value gives a new Job
     that runs again. With unchanged inputs, Helm recreates the Job on the
     next deploy after `ttlSecondsAfterFinished` (600 s) has removed the
     finished one.
   * Check the result with
     `kubectl logs -n podiumd $(kubectl get jobs -n podiumd -o name | grep openformulieren-configure-customer-interactions)`.
     It should end with
     `Customer interactions API group 'open-klant' created (service 'openklant-api').`
     On later deploys it says `updated`.

   *Fallback (manual):* if you cannot use the Job, create the group once in
   the Open Formulieren admin: **Configuration** > **Configuration overview**
   > **Prefill plugins** > **Communication preferences** > **Manage API
   groups** > **Add customer interactions API group**. Use Name `Open Klant`
   and Identifier `open-klant`, and select `Open Klant - Klantinteracties API`.

6. **Verify the result.**
   * In Open Klant admin, **API tokens** lists the `openformulieren` token.
   * In Open Formulieren admin, **Configuration** > **Configuration overview**
     shows the Communication preferences plugin with a green status.
   * Optional: in a test form, add the **Profile** component and a user-defined
     variable with the Communication preferences prefill. Then log in with DigiD
     (or eHerkenning) and check that the known addresses are prefilled.

## All gemeenten: set `nodeSelector` on every component

In [`values.yaml`](../../values.yaml) a number of components have
`nodeSelector: {}`, so the chart does not choose a node pool for them. Their
pods can then be scheduled on any node, the system pool included.

> **Required:** logs of a component are **only visible in Grafana** when its
> pods run on the `userpool` node pool. Set the `nodeSelector` below for
> **every** component in the list, or the logs of that component will be
> missing from Grafana.

```yaml
nodeSelector:
  kubernetes.azure.com/agentpool: userpool
```

This applies to every gemeente and every environment (`ontw`, `test`, `accp`
and `prod`). Set it in `<gemeente>/<env>/podiumd.yml` before deploying
PodiumD 4.9.2. Also set it for components that are disabled in an
environment, so it is correct when they are turned on later.

| Frank gateway dashboard auth shim | `frankgateway.dashboard.auth.shim.nodeSelector` |
| OpenBao configuration Job | `openbao.configuration.job.nodeSelector` |
| OpenBao database schema Job | `openbao.database.schemaJob.nodeSelector` |

Keep a `nodeSelector` that a gemeente already sets in its `podiumd.yml`, as
long as it points to the `userpool`.

### Note on KISS Elasticsearch `nodeSets`

`kiss-eck.eck-elasticsearch.nodeSets` is a list. Helm replaces a list as a
whole, it does not merge it. So when you set the `nodeSelector` here, copy the
**complete** nodeSet from `values.yaml` (`name`, `count` and `config`), not
only `podTemplate`. Leaving out `count` or `config` changes the Elasticsearch
cluster. If the environment already overrides `nodeSets` (for example with
`volumeClaimTemplates`), add `podTemplate` to that nodeSet and keep the rest.
