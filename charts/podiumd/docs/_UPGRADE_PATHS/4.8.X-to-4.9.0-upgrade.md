# Upgrade guide: PodiumD 4.8.X → 4.9.0 (DRAFT — exact source patch version not yet assigned)

> **Status: scaffold.** This guide accompanies the `objecten`/`objecttypen` →
> `openobject` chart merge. The underlying diff was drafted as patch files
> under `patches/` at the repo root and has since been applied to
> `charts/podiumd/`'s working tree (unstaged, not yet committed). `4.8.X`
> here is a literal placeholder for whichever 4.8.x patch release the
> environment is running before this merge lands, since the exact source
> version still needs to be confirmed with the team; the actual
> per-environment rollout order also still needs confirmation before this
> guide is finalized. See
> `docs/apps/objecten/openobject-migration.md` for the full research and
> design-decision record this guide is based on.

## What this release does

Merges the separate **Objecten** (Objects API) and **Objecttypen**
(Objecttypes API) subcharts into Maykin's single **Open Object 4.0**
application (`openobject` chart, aliased to `objecten` — every Kubernetes
object, DNS name, public hostname, and values.yaml key keeps the name
`objecten`). See
[`docs/apps/objecten/objecten-BASICS.md`](../apps/objecten/objecten-BASICS.md)
for the resulting (merged) app shape — that doc was updated in place rather
than adding a separate `openobject` doc, since `objecten` is what survives.

## Precondition — must complete before this release is rolled out to an environment

Per `docs/apps/objecten/openobject-migration.md` section A: for **every** environment, before
the chart-level swap below is deployed there —

1. Confirm `objecten` is already running chart 2.12.1 / appVersion ≥3.6.1
   (already the default in this repo's `values.yaml`, but the *running* app
   version in each environment must be confirmed independently).
2. Run `/app/src/manage.py import_objecttypes <service_slug>` against that environment's
   `objecten` app, where `<service_slug>` is the `zgw_consumers` service
   identifier already pointing at that environment's `objecttypen` instance.
   **To look it up**: log into that environment's `objecten` Django admin →
   **Configuratie → Services** (`/admin/zgw_consumers/service/`). There will
   be one or more Services configured there pointing at an Objecttypen API —
   use the `slug` field of the right one as `<service_slug>` (check the URL
   column if more than one is present).
3. Run `check_for_external_objecttypes` and confirm it prints `OK`.
4. Only then deploy the chart change described below to that environment.

**If this is skipped or incomplete**: the Open Object 4.0 container fails at
startup (and blocks its own DB schema migrations) when any objecttype remains
unimported. Recovery means rolling the release back to `objecten` 3.6.1,
fixing the remaining objecttypes, and retrying steps 2–3.

`objecttypen` (the running service, not just its database) must stay up and
serving requests through this entire window — `objecten` still depends on it
for live objecttype resolution until the actual cutover in step 4.

## Chart-level changes

- `Chart.yaml`: `objecten` + `objecttypen` dependency entries replaced by a
  single `openobject` entry, `alias: objecten`, `condition: objecten.enabled`.
- `values.yaml`: the `objecttypen:` block is deleted; `objecten:` is
  restructured in place. Full old-key → new-key mapping table in
  `docs/apps/objecten/openobject-migration.md` section C. Highlights:
  - `objecten.nameOverride` **and** `objecten.fullnameOverride` both set to
    `objecten` (both required — see H.1 in the migration doc for why one
    alone isn't enough).
  - New required value `objecten.settings.siteDomain` — **H.2 decided**: the
    existing `<env>-objecten` hostname survives unchanged; the former
    `<env>-objecttypen` hostname is retired (no DNS/redirect work needed for
    the surviving one).
  - Redis: **H.3 decided** — keeps `objecten`'s existing DB 1 (cache) / DB 2
    (celery); `objecttypen`'s old DB 0 is freed. See
    [`redis-ha-databases.md`](../apps/redis/redis-ha-databases.md).
  - `objecten.persistence.mediaMountSubpath` must stay `objecten/media`
    (chart default changed to `openobject/media`) to avoid an unintended
    media-path move.
  - Image: `maykinmedia/open-object`, tag
    `4.1.0@sha256:7738cb8161d221d0a286d39d9d270c35024ff78123c296ceb46f3d9dda7208f9`
    (digest pinned; also recorded in `docs/images/images-4.9.0.yaml`).
- Templates: `create-required-objecttypen.yaml` and
  `create-required-catalogi.yaml` repointed from `.Values.objecttypen.*` to
  `.Values.objecten.*`; the admin token for the `create-required-objecttypen`
  job moves from a plain `objecttypen.configuration.token` to a `tokenauth`
  item with `is_superuser: true` (H.5).
- Keycloak: the two OIDC clients (`objecten`, `objecttypen`) merge into one
  (`objecten`) — realm config, realm secrets, and the realm-import Job all
  drop every `objecttypen`-specific entry.
- KISS adapter: **H.7 decided** — `kiss.adapter.objecten.*` and
  `kiss.adapter.objecttypen.*` collapse into one `kiss.adapter.objecten.*`
  block; `adapter-config.yaml`/`adapter-secret.yaml` updated accordingly.
- Downstream consumer defaults repointed to the merged host: `zac.objectenApi`
  / `.objecttypenApi`, ITA's four `.type` URLs, and the commented
  `openformulieren`/`openbeheer` `zgw_consumers` examples.

## Per-environment checklist

### A. Prepare (per environment, before this release)

- [ ] Confirm running `objecten` appVersion ≥3.6.1 (not just chart-pinned).
- [ ] Run `/app/src/manage.py import_objecttypes <service_slug>` and confirm
      `check_for_external_objecttypes` prints `OK` (see Precondition above).
- [ ] Audit this environment's `podiumd.yml` for use of the two fields
      upstream 4.0.0 removes: `objecttypes.items[].service_identifier` and
      `tokenauth.items[].{fields,use_fields}` — these are silently
      rejected/ignored post-upgrade.
### B. Deploy

- [ ] Confirm the pinned `maykinmedia/open-object` image digest in
      `values.yaml` still matches the tag (`/verify-image-digests`) — it may
      have moved since this guide was drafted.
- [ ] Run `helm upgrade --atomic`.
- [ ] Confirm the `objecten` config Job completes.
- [ ] Confirm the `create-required-objecttypen` Job succeeds against the
      merged app.
- [ ] Confirm web/worker pods go Ready; admin UI reachable at the chosen
      hostname with Keycloak login.
- [ ] Confirm `/api/v2/objects` and `/api/v2/objecttypes` both answer with a
      valid consumer token.
- [ ] **Celery smoke test** — Open Object 4.0 fixes a bug where
      `CELERY_BROKER_URL` was actually wired to `CELERY_RESULT_BACKEND`;
      runtime behavior changes even though the values look unchanged.

### C. Rollback runbook (if the cutover fails)

**Failure signature**: the `openobject`/`objecten` pods enter `CrashLoopBackOff`
right after the `helm upgrade`, the container logs an unimported-objecttype
error during startup, and the config Job's own DB schema migrations never
complete. This is a **hard container-level check** in Open Object 4.0 (per
`docs/manual/migration.rst`, cited in
`docs/apps/objecten/openobject-migration.md` section A.6), not a soft
pre-flight warning — `helm upgrade --atomic` should itself auto-rollback the
Helm release on this failure, but treat that as a safety net, not the primary
recovery path, since it only reverts the Helm release object, not any
partially-applied Job/PVC state.

1. **Confirm this is the unimported-objecttype failure, not something else.**
   Check the failing pod's logs (`kubectl -n podiumd logs deploy/objecten
   --previous`) for the startup error naming specific `ObjectType` UUIDs. If
   the failure looks unrelated (image pull, DB connectivity, OOM), diagnose
   that instead — don't assume every failed cutover is this scenario.
2. **Roll the release back to `objecten` 3.6.1.** If `helm upgrade --atomic`
   already reverted the release, verify it actually landed on the prior
   `objecten`/`objecttypen` two-subchart revision
   (`helm history podiumd -n podiumd`); if not, or if `--atomic` wasn't used,
   run `helm rollback podiumd <prior-revision> -n podiumd` explicitly.
   Confirm both the `objecten` and `objecttypen` deployments (the old,
   separate ones) come back Ready — `objecttypen` must still be live for this
   rollback to leave the environment in a working state, consistent with the
   precondition note above that it stays up through the entire cutover
   window.
3. **Identify the offending objecttypes.** Re-run
   `check_for_external_objecttypes` against the rolled-back `objecten` 3.6.1
   app; it lists the exact `ObjectType` UUIDs that are still not
   `is_imported=True`.
4. **For each offending UUID, check whether it still exists in the live
   `objecttypen` instance:**
   - **Still exists there** → re-run
     `/app/src/manage.py import_objecttypes <service_slug>` (same slug as the original
     precondition step) — it upserts on `uuid`, so it's safe to re-run and
     will pick up anything missed the first time.
   - **Already deleted from `objecttypen`** → per the migration guide, it can
     never be imported. Remove the stale `ObjectType` row manually from
     `objecten`'s own database (Django admin, *Configuration → Object types*,
     or a direct DB delete) — do not attempt to re-import it.
5. **Re-verify**: run `check_for_external_objecttypes` again and confirm it
   prints `OK` for every objecttype, with no exceptions.
6. **Retry the cutover** from step B above (same `helm upgrade --atomic`,
   same pinned image digest) once step 5 is clean. Do not retry blindly
   without re-running step 5 — a partial fix that still leaves one UUID
   unimported reproduces the exact same startup failure.
7. **If the failure recurs after a clean `check_for_external_objecttypes`**,
   this is no longer the known unimported-objecttype scenario — treat it as a
   new incident (check image digest match, DB migration errors in the config
   Job logs, etc.) rather than repeating steps 3–4.
