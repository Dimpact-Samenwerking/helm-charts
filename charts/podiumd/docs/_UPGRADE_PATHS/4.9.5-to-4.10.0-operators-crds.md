# Operators & CRDs — PodiumD 4.9.5 → 4.10.0

Companion to [`4.9.5-to-4.10.0-upgrade.md`](4.9.5-to-4.10.0-upgrade.md).

| Component | Change | CRD impact | Action |
| --- | --- | --- | --- |
| keycloak-operator | Images `26.7.3` → `26.8.1`; adfinis chart `1.13.0` → `1.13.1` | **Yes**, additive fields on two existing CRDs | **Apply the 26.8.1 CRDs** before the `helm upgrade`; `helm upgrade` never touches CRDs |
| redis-operator | Image `v0.26.0` → `v0.27.0`; chart `0.26.1` → `0.27.0` | Description text only compared with the 0.26.1 CRDs; real (optional) schema additions compared with older CRDs | Optional; see [redis-operator](#redis-operator) |

The CRDs come from upstream
[`keycloak-k8s-resources`](https://github.com/keycloak/keycloak-k8s-resources)
26.8.1, not from the adfinis chart: adfinis 1.13.1 targets Keycloak 26.7.4.
Diffed against the 26.7.3 CRDs:

- `keycloaks.k8s.keycloak.org`: new optional fields
  `schedulingGroup.podGroupName` and `userAnnotations`. Additive only.
- `keycloakrealmimports.k8s.keycloak.org`: the organization representation
  gets `organizationLinks` (with `organizationId`, `membershipType`,
  `autoMembership`) for the many-to-many identity provider linking of 26.8.0.
  Additive for PodiumD, which defines no organizations in the realm import.
- `keycloakoidcclients` and `keycloaksamlclients`: byte-identical.

Existing `Keycloak` and `KeycloakRealmImport` CRs stay valid as they are.

## Action required

Apply the CRDs the way your environment applies cluster changes, **before**
the `helm upgrade` that bumps the operator image. CRDs are cluster-scoped: do
it once per cluster, with cluster-admin rights. Other PodiumD namespaces on the
same cluster that are still on 4.9.x keep working, because the changes only
add optional fields.

```bash
charts/podiumd/scripts/install-keycloak-operator-crds.sh \
  --context <kube-context> --keycloak-version 26.8.1
```

Check afterwards that the CRDs are established and carry the new fields:

```bash
kubectl --context <kube-context> get crd keycloaks.k8s.keycloak.org \
  -o jsonpath='{.status.conditions[?(@.type=="Established")].status}'
```

Without `--keycloak-version` the script takes the chart's Keycloak pin
(`keycloakImageVersion` in `values.yaml`), which is 26.8.1 in 4.10.0.

PodiumD creates no `KeycloakOIDCClient` CRs, so the new 26.8.0 rule that
Secrets referenced by such a CR need the label
`operator.keycloak.org/kind: KeycloakOIDCClient` needs no action. An
environment that added its own `KeycloakOIDCClient` CRs labels their Secrets
before upgrading.

## redis-operator

Upstream's v0.27.0 release notes say to apply the CRDs by hand, because
`helm upgrade` doesn't update them. For PodiumD this is optional:

- The 0.27.0 CRDs differ from the 0.26.1 CRDs in description text only.
  A cluster with older CRDs gets real schema additions (ontw-dim1:
  `redisreplications` grew by about a quarter), all of them new optional
  fields.
- A cluster can have even older CRDs installed (johnb00 had pre-0.26 ones,
  without `spec.podManagementPolicy` and the Sentinel affinity fields). That
  still works: the `RedisReplication` PodiumD renders only uses
  `clusterSize`, `initContainer`, `kubernetesConfig`, `podSecurityContext`,
  `redisExporter` and `storage`, which every one of those CRD versions has.

Apply them to keep the cluster's CRDs in step with the operator, once per
cluster, with cluster-admin rights:

```bash
charts/podiumd/scripts/install-redis-operator-crds.sh --context <kube-context> --version 0.27.0
```

The script applies with `--server-side --force-conflicts`. Where the CRDs
were first installed by `helm upgrade --server-side` (the SSC Applications
pipeline), the field manager `helm` owns `.spec.versions`, and a server-side
apply without `--force-conflicts` fails with
`conflict with "helm": .spec.versions`. Helm never updates CRDs from a
chart's `crds/` directory after the first install, so taking over these
fields changes nothing for later deploys. `--force-conflicts` takes the fields
from every field manager, not only `helm`: on a cluster where Argo CD or Flux
manages these CRDs with server-side apply, that tool reverts the change or
reports drift on its next sync, so update the CRDs there instead.

The script refuses a `--version` older than 0.27.0 unless `--allow-downgrade`
is given: the forced apply would replace the newer schema and prune its fields
from the Redis CRs. It compares with its own default, not with the CRDs on the
cluster (chart-installed CRDs carry no version). A `v` prefix (`v0.27.0`) is
accepted and stripped; anything other than `X.Y.Z` is refused. It then waits until all four CRDs (`redis`,
`redisclusters`, `redisreplications`, `redissentinels`) are `Established`, and
exits with an error when one is not.
