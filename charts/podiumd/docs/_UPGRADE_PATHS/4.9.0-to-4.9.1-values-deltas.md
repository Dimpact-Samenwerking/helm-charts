## pabc 1.1.1 (unchanged): declarative seeding of the base authorisation setup

Two new keys, **both default `false`**, so an environment that does nothing
keeps the behaviour it had in 4.9.0.

- **`pabc.datasetConfigMap.enabled`** (default `false`,
  [IN-2004](https://dimpact.atlassian.net/browse/IN-2004)) renders
  `files/pabc-dataset.json` into a `pabc-dataset` ConfigMap.
- **`pabc.seedJob.enabled`** (default `false`, requires
  `pabc.datasetConfigMap.enabled`) is the one-shot Job that runs the
  `pabc-migrations` image once with `JSON_DATASET_PATH` pointing at that
  ConfigMap, loading the `zaakafhandelcomponent` application, its application
  roles, functional roles matching the Keycloak group names, and the mappings
  that mirror the `zac` client roles those groups hold.

### When to enable

On an environment whose PABC database is still empty. Without any PABC
content ZAC resolves no application roles at all and every user lands on
"u heeft geen toestemming om deze pagina te bekijken", however healthy
Keycloak looks.

### Seeding REPLACES all PABC content

The migration service deletes all applications, application roles, functional
roles, domains, entity types and mappings before inserting the dataset. On an
environment that has already been curated through the PABC UI, leave both keys
disabled: enabling them throws that curation away.

The Job name carries a checksum of the dataset and of the rendered pod
template, so it runs once and then stays put across upgrades. A chart version
bump on its own does not re-seed. Editing `files/pabc-dataset.json`, or
changing something that alters the Job itself such as the migrations image
tag, yields a new Job name and deliberately seeds again. The completed Job
object is the "already seeded" marker, which is why it carries no
`ttlSecondsAfterFinished` and must not be deleted by hand.

See [`../apps/pabc/pabc-iam-migration.md`](../apps/pabc/pabc-iam-migration.md)
for switching an environment from the old IAM setup to this one, and
[`../apps/pabc/enabling-pabc.md`](../apps/pabc/enabling-pabc.md) for the
values snippet.

## Breaking — Frank!Gateway (only when `frankgateway.enabled: true`)

Released 4.9.0 shipped one gateway with a single etcd member, its routes as
files inside the chart and its BAG/KVK keys as env vars from a Secret. 4.9.1
is the traffic-class split: three instances (`inway` / `outway` / `internal`)
on one three-member etcd, routes from the values file only, credentials from
OpenBao at request time. The upgrade also recreates etcd — see
[Part 5 of the upgrade guide](4.9.0-to-4.9.1-upgrade.md#part-5--frankgateway-image-104--110)
**before** running it.

| 4.9.0 | 4.9.1 |
| --- | --- |
| one gateway, keys directly under `frankgateway.*` | `frankgateway.instances.{inway,outway,internal}` — shared keys stay under `frankgateway.*`, per-class overrides under the instance |
| chart-shipped route files (BAG, KVK×3, BRP) | gone — routes are `frankgateway.instances.<class>.routes.<id>`, the Admin API body as YAML; copy the reference bodies from [`frankgateway-routes.md`](../apps/frankgateway/frankgateway-routes.md) |
| `frankgateway.apiKeys.existingSecret` / `envNames` (env vars in the route) | **removed; the render fails while it is set.** Keys live in OpenBao at `<mount>/frankgateway` (`bag_api_key`, `kvk_api_key`); routes read them at request time with the gateway's reader token (`frankgateway.openbao.tokenSecret`). `openbao.enabled: true` is required. Delete the `frankgateway-api-keys` Secret and its Key Vault entries once the routes work — nothing references them any more. |
| `frankgateway.routes.seed` | `frankgateway.seed.enabled` |
| `frankgateway.routes.job.*` | `frankgateway.seed.job.*` |
| callers use `http://frankgateway:9080` | `http://frankgateway-outway:9080` (external APIs) or `http://frankgateway-internal:9080` (app-to-app); the `frankgateway` Service no longer exists |

The render fails, naming the key, for every removed key above. New optional
keys: `frankgateway.seed.prune` (default `false`) deletes `managed-by: iac`
routes that are not in the render;
`frankgateway.instances.<class>.clientCertificates.<name>.openbaoPath` pulls an
outbound client certificate from OpenBao into APISIX SSL object `client-<name>`
on `frankgateway.clientCertSync.schedule` (default every 5 minutes); inbound
consumer identities are read from OpenBao by the new `openbao-consumer-auth`
Lua (no values key — see
[`frankgateway-routes.md`](../apps/frankgateway/frankgateway-routes.md)).
The client-cert sync and the request-time Lua are a bridge for APISIX 3.16
only: the next Frank!Gateway release supports `$secret://` for these cases and
retires them, so expect those keys to change again; the OpenBao paths do not.

**Defaults that flip without an error** — set them explicitly if the 4.9.0
behaviour is wanted:

| default | 4.9.0 | 4.9.1 |
| --- | --- | --- |
| `frankgateway.dashboard.enabled` | `true` | `false` — the dashboard, its Ingress and its Keycloak client disappear unless set per instance (`instances.<class>.dashboard.enabled`) |
| `frankgateway.replicas` | `1` | `2`, hard-spread across nodes |
| `frankgateway.etcd.replicas` | `1` | `3`, hard-spread across nodes — together at least 3 schedulable nodes |
| `frankgateway.resources.requests.memory` | `256Mi` | `384Mi` per gateway pod |
| `frankgateway.etcd.resources.requests.memory` | `128Mi` | `192Mi` per member, ×3 |

Hook objects were renamed (`-apply-routes`/`-routes` → `-seed`); delete the
orphaned ConfigMaps once:
`kubectl -n podiumd delete configmap -l app.kubernetes.io/component=frankgateway-routes`.
