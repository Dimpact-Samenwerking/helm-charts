# Upgrade guide: PodiumD 4.9.0 → 4.9.1

> See the Confluence Releases page for the agreed application
> targets: <https://dimpact.atlassian.net/wiki/spaces/PCP/pages/7602191/Releases+PodiumD>.

> **⚠️ This hop breaks Grafana login on every environment.** The realm
> hardening in 4.9.1 strips the `offline_access` scope from the `monitoring`
> Keycloak client, and Grafana still asks for it. Each gemeente's
> `monitoring.yml` needs one line changed — see
> [Grafana login](#1-grafana-login--remove-offline_access-from-each-gemeentes-monitoringyml).
> This is a values change, not a chart change, and it is required whether you
> upgrade to 4.9.1 or are already on it.

## Required manual steps

### 1. Grafana login — remove `offline_access` from each gemeente's `monitoring.yml`

**Per gemeente, per environment.** The chart default does not reach the
environments: all 19 `monitoring.yml` files pin `scopes` themselves, and a
values file always wins over the chart.

```diff
  # applications/gemeenten/{gemeente}/{omgeving}/monitoring.yml
-      scopes: openid email profile offline_access roles
+      scopes: openid email profile roles
```

Find every file that still needs it:

```bash
grep -rn "offline_access" applications/gemeenten/*/*/monitoring.yml
```

- Deploy the **`monitoring`** release only. Do **not** upgrade or redeploy the
  `podiumd` release for this — the change works on the PodiumD version deployed
  today and does not wait for a chart release.
- **test-rott, acc-asse and acc-gron are broken now** (already on 4.9.1); the
  rest break the moment they do this hop. Make the values change **before or
  together with** the upgrade and Grafana never breaks.

### 2. Apply the Keycloak CRDs before `helm upgrade`

`helm upgrade` never applies CRD changes. The adfinis chart bump 1.12.1 → 1.13.0
carries them — the breakdown and the exact commands are in
[`4.9.0-to-4.9.1-operators-crds.md`](4.9.0-to-4.9.1-operators-crds.md).

### 3. Zaakbrug (only if `zaakbrug.enabled: true`)

- Mirror `docker.io/wearefrank/zaakbrug:1.26.18` to `acrprodmgmt`
  ([`images-4.9.1.yaml`](../images/images-4.9.1.yaml)).
- The sub-chart still has no `extraVolumes`/`extraVolumeMounts` support, so the
  post-deploy `kubectl patch` that mounts ConfigMap
  `zaakbrug-oauth-role-mapping` at `/opt/frank/resources/` is **still
  required**, and the deploy must still avoid `helm --wait` / `--atomic`. See
  [`zaakbrug-deploy.md`](../apps/zaakbrug/zaakbrug-deploy.md).
- No `podiumd.yml` changes. The Frank console and its Keycloak client, roles
  and secrets are unchanged.

## Breaking — Keycloak image pinning moved to a split `tag`/`sha`

As of 4.9.1 neither `keycloak.image` nor the operator's own image accepts an
embedded digest. `tag` is **just the version**, with the digest in a sibling
`sha` field:

```yaml
keycloak:
  image:
    tag: "26.7.3"        # NOT "26.7.3@sha256:…"
    sha: "ff4257d0d64efbe99ed1ddfaf07765cc3c36dc7518bf8324d41961327f441c54"
keycloak-operator:
  operator:
    image:
      tag: "26.7.3"      # NOT "26.7.3@sha256:…"
      sha: "e3856fd1aeb404f0e6ae2180b01875c8eeebd3748b0e5d955da77b5d41095ae4"
```

An environment still pinning the pre-4.9.1 way (`tag: "26.7.2@sha256:…"`, no
separate `sha`) renders a double digest — `…:26.7.3@sha256:xxx@sha256:yyy` — and
the pod never starts. Nobody does this today (checked helm-charts, podiumd-infra
and ExternalsPodiumD), but it is exactly what a Keycloak hotfix would look like.

The explicit `sha` override is required, not optional: adfinis 1.13.0's bundled
default is stale, since no chart has been cut for `26.7.3` yet.
