### Keycloak Operator (server) 26.7.2 → 26.7.3 (chart 1.12.1 → 1.13.0)

PodiumD 4.9.1 upgrades **Keycloak Operator (server + operator images)** from app version 26.7.2
to 26.7.3.

- Helm chart `keycloak-operator` `1.12.1` → `1.13.0` in
  `charts/podiumd/Chart.yaml`.
- Image tag pin `keycloak-operator.operator.config.keycloakImage.tag` `26.7.2` → `26.7.3` in
  `charts/podiumd/values.yaml`.
- Image / digest: see [`images-4.9.1.yaml`](../images/images-4.9.1.yaml).

#### Part 1 — completing the inconsistent 4.9.0 Keycloak pin (26.6.4 → 26.7.2, security, spans three upstream releases)

4.9.0 bumped the Keycloak **server** image (`keycloak.image` and the
operator's `config.keycloakImage` default) to `26.7.2`, and the adfinis
`keycloak-operator` chart dependency to `1.13.0` (`appVersion` 26.7.2) — but
left the **operator's own image** (`keycloak-operator.operator.image`) at
`26.6.4`. This hop completes that bump, bringing the operator image itself
in line with the rest.

The 26.7.2 line spans upstream `26.7.0`/`26.7.1`/`26.7.2` (23 CVEs total).
`26.7.0` is also a **feature** release (SCIM API preview, multi-cluster HA
preview, step-up authentication for SAML clients, Identity Brokering API
v2). The two CVEs most relevant to a standard podiumd deployment (Fine-Grained
Admin Permissions v2 and SAML identity brokering are not enabled here, so
FGAP/SAML-broker CVEs are lower priority for us):

- **CVE-2026-18963** — unauthenticated account takeover via a reset-credentials
  flow bypass.
- **CVE-2026-15571** — predictable account-linking hash enables account
  takeover via a malicious OIDC client.

Full lists: [26.7.0](https://github.com/keycloak/keycloak/releases/tag/26.7.0),
[26.7.1](https://github.com/keycloak/keycloak/releases/tag/26.7.1),
[26.7.2](https://github.com/keycloak/keycloak/releases/tag/26.7.2).

#### Part 2 — further security bump, image-only (26.7.2 → 26.7.3, published 2026-08-31)

`26.7.3` is a large security release — **20 CVEs**, including
**CVE-2026-19729** (incomplete fix for CVE-2026-9083 — relative path
traversal still enables filesystem probing in 26.6.4) and **CVE-2026-18209**
(incomplete fix for a `redirect_uri` OIDC response-parameter injection —
the forbidden-parameter check only inspected the query string, not the URL
fragment). It also fixes two post-26.7.2 regressions: sustained high CPU
after upgrade (`#51523`) and admin-API per-request cost growing
super-linearly with realm count since 26.7.1 (`#51554`/`#51707`).

Full list: [26.7.3](https://github.com/keycloak/keycloak/releases/tag/26.7.3).

**This bump is image-only.** The adfinis `keycloak-operator` chart has not
published a version targeting `26.7.3` as of this writing — it's still
`1.13.0` (`appVersion` 26.7.2). `keycloak.image`,
`keycloak-operator.operator.image`, and
`keycloak-operator.operator.config.keycloakImage` are all pinned ahead of
the chart line to `26.7.3`; the `keycloak-operator` Chart.yaml dependency
stays at `1.13.0` until adfinis catches up. **No further CRD changes** are
introduced by this part — CRDs come from the chart, which is unchanged (see
[operators-crds](4.9.0-to-4.9.1-operators-crds.md)).

#### Action required

The image pins are already in `values.yaml` and
[`images-4.9.1.yaml`](../images/images-4.9.1.yaml). **This hop does change
CRDs** (from Part 1's chart bump) — see
[`4.9.0-to-4.9.1-operators-crds.md`](4.9.0-to-4.9.1-operators-crds.md) for
the full breakdown and the exact commands. `helm upgrade` never applies CRD
changes; apply them manually before rollout.

> **Caveat — operator (and now keycloak.image) digest pinning uses a separate
> `sha` field, not an embedded tag digest.**
> The operator image is rendered by the adfinis subchart, which builds the ref
> as `repository:tag@sha256:{{ operator.image.sha }}` using a **separate `sha`
> field** — not by appending a digest to the tag. **This hop also moves
> `keycloak.image` to the same split shape** (via a YAML anchor/alias onto
> `keycloak-operator.operator.config.keycloakImage`, see
> `templates/_helpers.tpl`'s `podiumd.image` helper) — so as of 4.9.1, neither
> `keycloak.image` nor the operator's own image take an embedded
> `tag: "<ver>@sha256:<digest>"` anymore. Both need `tag` as **just the
> version**, with the digest in the sibling `sha` field:
>
> ```yaml
> keycloak:
>   image:
>     tag: "26.7.3"        # NOT "26.7.3@sha256:…"
>     sha: "ff4257d0d64efbe99ed1ddfaf07765cc3c36dc7518bf8324d41961327f441c54"
> keycloak-operator:
>   operator:
>     image:
>       tag: "26.7.3"        # NOT "26.7.3@sha256:…"
>       sha: "e3856fd1aeb404f0e6ae2180b01875c8eeebd3748b0e5d955da77b5d41095ae4"
> ```
>
> Embedding `@sha256:...` directly in `tag` produces an invalid **double
> digest** at render time (`…:26.7.3@sha256:xxx@sha256:yyy`) once the template
> appends the separate `sha` field. The adfinis 1.13.0 chart's own bundled
> default `operator.image.sha` is stale regardless (it doesn't know the
> `26.7.3` tag exists at all, since no chart has been cut for it yet), so the
> explicit override above is required, not optional.
>
> **If an environment still pins `keycloak.image.tag` the pre-4.9.1 way**
> (`tag: "26.7.2@sha256:9d1f1b2b…"`, no separate `sha`) — the chart's own
> `sha` anchor still renders alongside it, producing exactly the double-digest
> break above and a pod that never starts. Nobody does this today (checked
> helm-charts, podiumd-infra, and ExternalsPodiumD), but it's exactly what a
> Keycloak-version hotfix would look like, so watch for it: switch to the
> split `tag`/`sha` form above instead.

### FrankGateway image 104 → 1.1.0

`ghcr.io/wearefrank/frank-gateway` moves from the pre-SemVer build `104` to the
first official release `1.1.0` (built 2026-08-14, digest
`sha256:2f944fdbc16883e4b586aaa20f04928cd33afc7efc78d37012d2c7acb62f55bd`).
Both are `FROM apache/apisix:3.16.0-ubuntu`, so this is **not** an APISIX
upgrade: ports (9080/9443), the Lua path and the entrypoint are unchanged.

What 1.1.0 adds: two WeAreFrank plugins, `auth-zen` (AuthZEN access
evaluation) and `merge-config` (merges YAML fragments into a standalone
`apisix.yaml`), plus Apache-2.0 licensing and semantic-release tagging. The
image's own `conf/config.yaml` enables `merge-config`, but this chart replaces
that file wholesale with its rendered config and runs APISIX in etcd mode, which
never reads `apisix.yaml` — so the plugin has no effect here. Verify once after
the first rollout: `apisix version` in a gateway pod reports 3.16.0, the pod
has 0 restarts, and `/usr/local/apisix/conf/apisix.yaml` is not being written.

Do not pin `latest`: it is one commit ahead of `1.1.0` and moves.

Only environments with `frankgateway.enabled: true` are affected — none of the
gemeenten today. For those, the image is the smallest part of this hop; the
rest is below.

#### Frank!Gateway etcd is recreated, not upgraded

4.9.1 changes the etcd StatefulSet in ways Kubernetes refuses to apply in
place: `serviceName` (`frankgateway-etcd` → `frankgateway-etcd-headless`) and
`podManagementPolicy` (unset → `Parallel`) are immutable, so `helm upgrade`
against a running 4.9.0 gateway fails at apply with `Forbidden: updates to
statefulset spec for fields other than 'replicas', 'ordinals', 'template',
'updateStrategy', 'persistentVolumeClaimRetentionPolicy' and 'minReadySeconds'
are forbidden`. Two more changes land on the same stored state and would make a
forced replacement wrong anyway: the member identity moves from `--name=etcd0`
to `ETCD_NAME=frankgateway-etcd-0` on the same data directory, and every
instance now reads its own prefix (`/frankgateway-<class>`) instead of
`/apisix`, so routes, SSL objects and consumers already in etcd would be
orphaned — invisible to the new instances, still occupying the store.

**etcd contents are not migrated, by design.** The values file is the
complete truth for routes (see [values deltas](4.9.0-to-4.9.1-values-deltas.md#breaking--frankgateway-only-when-frankgatewayenabled-true))
and the seed hook rebuilds them; the server certificate is re-pushed by the
ssl-sync step of the same hook. Before the upgrade, on an environment running
4.9.0's gateway:

1. If anything was created through the dashboard or the Admin API and is worth
   keeping, export it first — `GET /apisix/admin/routes` (and `/ssls`,
   `/consumers`) with the admin key — and carry it into
   `frankgateway.instances.<class>.routes`.
2. Delete the old StatefulSet and its volume:
   `kubectl -n podiumd delete statefulset frankgateway-etcd` then
   `kubectl -n podiumd delete pvc data-frankgateway-etcd-0` (4.9.0's volume
   claim template carries no labels, so name it; confirm with
   `kubectl -n podiumd get pvc | grep frankgateway-etcd`).
   The gateway pods keep serving from their in-memory copy until they roll.
3. Run the upgrade. The new three-member etcd bootstraps in parallel, the
   gateways roll onto it, and the `frankgateway-<class>-seed` hooks re-create
   every route from values.

Expect the seed log to show `-> 201` for every route on this first run, and
`-> 200` on every run after that.

#### Minimum node count

The 4.9.1 defaults — two gateway replicas per class and three etcd members,
each set spread with `whenUnsatisfiable: DoNotSchedule` — need **at least 3
schedulable nodes**. On a smaller rig the third etcd member stays Pending, and
under `helm upgrade --wait` the only symptom is a timeout. Decide before the
upgrade: `frankgateway.etcd.replicas: 1` for a rig that does not need quorum,
or `topologySpreadConstraints` with `whenUnsatisfiable: ScheduleAnyway` for the
gateway and for etcd.

#### Defaults that change silently

None of these errors; each is a behaviour change an environment relying on the
default gets without asking. The table is in the
[values deltas](4.9.0-to-4.9.1-values-deltas.md#breaking--frankgateway-only-when-frankgatewayenabled-true).

### Zaakbrug 1.26.15 → 1.26.18 (chart 2.3.28 → 2.3.32)

Only relevant to gemeentes running the opt-in Zaakbrug component
(`zaakbrug.enabled: true` — default is `false`). **No `podiumd.yml` changes
are required**: the image tag and sub-chart version are podiumd chart
defaults.

Upstream changes across the three patch releases
([changelog](https://github.com/wearefrank/zaakbrug/blob/master/CHANGELOG.md)):

- **1.26.16** — two bug fixes: a missing exception catch in several
  document-related SOAP actions that produced a StUF error response with no
  `Fo03` content, and JWT-token caching that ignored the cache key
  parameters. Frank!Framework runtime bumped to the 10.2 line.
- **1.26.17** — Frank!Framework runtime to `10.2.1-20260804.125921`.
- **1.26.18** — CI/release-tooling only, no application change.

Net runtime move: Frank!Framework `10.1.0-20260323.042326` →
`10.2.1-20260804.125921`.

The sub-chart bump 2.3.28 → 2.3.32 is `appVersion` tracking plus a fix to
stray trailing commas in the sub-chart's default `configurations[].route`
strings. **No new or changed values keys, and no `extraVolumes`/
`extraVolumeMounts` support yet** — so the post-deploy `kubectl patch` that
mounts ConfigMap `zaakbrug-oauth-role-mapping` at `/opt/frank/resources/` is
still required, and the deploy must still avoid `helm --wait`/`--atomic`.
See [`docs/apps/zaakbrug/zaakbrug-deploy.md`](../apps/zaakbrug/zaakbrug-deploy.md).

#### Action required (Zaakbrug)

None beyond the normal rollout, plus mirroring
`docker.io/wearefrank/zaakbrug:1.26.18` to `acrprodmgmt` for environments that
run Zaakbrug (see [`images-4.9.1.yaml`](../images/images-4.9.1.yaml)). The
Frank console and its Keycloak client, roles and secrets are unchanged.
