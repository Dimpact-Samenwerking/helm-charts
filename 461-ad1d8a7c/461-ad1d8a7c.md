## Prose review

This PR is a Helm release‑cycle change. The only real *logic* is the new `oidcUrl` validation block in `templates/keycloak-podiumd-realm-config.yaml`; the rest is values/data. I could not find a defect that is provable from the diff alone except a minor error‑message wording issue. Everything else hinges on parts of the chart that are **not** in the diff (the `values.yaml` defaults for `configuration.oidcUrl` / `.enabled`, the actual Keycloak‑client rendering below the hunk, and whether every `*redisImage` alias was removed), so those are tagged ASSUMED.

**Validation block (`keycloak-podiumd-realm-config.yaml`)**
- The comment asserts "a component with no enabled flag is always deployed and is therefore always checked," implemented as `if not (eq .enabled false)`. That is only correct if the real client templates also treat *unset* `enabled` as deployed. If a client template gates on `if .Values.X.enabled` (false when unset) and `values.yaml` leaves `enabled` unset, the validation fails the render for a component whose client is never rendered — a false positive that blocks a valid deploy. (ASSUMED)
- The comment claims the 11‑entry `$oidcClients` list is "every component whose Keycloak client is rendered below." The client‑rendering section is below the hunk and not shown, so I can't confirm completeness; any client present but absent from the list (e.g. kiss/zac/ita) would skip validation and ship placeholder redirect URIs. (ASSUMED)
- The `contains "example.nl"` guard depends on the unverified claim that `values.yaml` ships `example.nl` defaults. If a component's default `oidcUrl` is some *other* non‑empty placeholder, neither `empty` nor the `example.nl` check fires, so the render passes while redirect URIs still point at a placeholder. (ASSUMED)
- SELF‑CONTAINED (minor): the `fail` text says `configuration.oidcUrl is not set`, but the triggering `or` also fires when `oidcUrl` *is* set (to an `example.nl` placeholder), so the message mislabels a set‑but‑placeholder value as "not set."

**`values.yaml`**
- The `&redisImage` anchor is deleted. The diff removes 10 `*redisImage` aliases plus the anchor; if *any* alias remains elsewhere in the (unshown) file it becomes a dangling YAML alias and the chart fails to parse for every `helm` command. (ASSUMED)
- `openformulieren` is bumped to `3.5.8` while `release-table.csv` still lists the target as `3.5.6`. The CSV is a generated/data file reviewed separately and the PR marks the images‑manifest a TODO, so this is a known‑gap consistency note rather than a confirmed bug. (ASSUMED)

**`etc/release-baseline.yaml`**
- `upgrade_docs` is advanced to `"4.9.1"` for a 4.9.2 release. The prior state (`4.9.0` when the release was 4.9.1) suggests it intentionally tracks the *previous* release, so this is likely correct; flagging only because the test plan says "4.9.2 upgrade docs … completed," which would be inconsistent if a consumer resolves docs by this baseline. (ASSUMED)

The image digest re‑pinnings (nginx, solr, clamav), the `postgres` anchor reuse, and the `openbao` schema‑job switch to `*postgresImage` (same digest, tag label `16-alpine`→`16.15-alpine`) are internally consistent and match their comments; I'm not flagging them.

## Review

This is a draft release-cycle PR touching three files: a deleted naming-reference doc, a reorganized `images-4.9.1.yaml`, and a new `images-4.9.2.yaml`. The manifests encode the ACR mirror naming convention via `name:`/`url:`, and the deleted doc is the authoritative statement of that convention (`name = strip_registry(url)`). A few concrete issues:

**1. `images-4.9.1.yaml` — the `python` entry regresses from a correct name to a wrong one.** The diff moves the keycloak-jobs python sidecar and changes `name: library/python` → `name: python` while `url: docker.io/library/python` is unchanged. `strip_registry(url)` is `library/python`, so the new `name` is the basename form the deleted doc explicitly calls out as a "common mistake" ("the rule strips only the registry host, not the namespace"). It also contradicts every sibling entry in the same file (`nginxinc/nginx-unprivileged`, `keycloak/keycloak`, `hashicorp/vault-k8s`, …) which all keep the namespace. If the (migrated) values files reference `library/python` but the import now mirrors into repo `python`, keycloak jobs' python sidecar will `ImagePullBackOff`.

**2. `images-4.9.2.yaml` — `openformulieren` uses a legacy name for an existing image.** `name: openformulieren` for `url: docker.io/openformulieren/open-forms` should be `openformulieren/open-forms` under the convention. `openformulieren` is the frozen legacy-table name (Dutch rename + drop hyphen). This is only correct if the 4.9.1 baseline still carries the pre-migration name for open-forms; if the baseline has been migrated to `openformulieren/open-forms`, the delta mirrors into the wrong repo. I'm assuming the baseline's name is unknown (not shown) — unverified.

**3. `images-4.9.1.yaml` — `redis` carries the same legacy-name inconsistency (pre-existing).** `name: redis` for `url: docker.io/library/redis` should be `library/redis`. The name itself isn't changed by this PR (the entry is only moved/re-commented), so this is a pre-existing inconsistency rather than a regression — but the PR is already editing this entry and the adjacent `python` entry, so it's a natural place to normalize it.

**4. `acr-mirror-naming.md` — unexplained deletion of the naming reference.** The PR removes the doc that defines the convention, the frozen legacy table, the migration workflow, and the common-mistakes guidance that the manifests depend on, but the PR description doesn't mention it and says the replacement upgrade docs are still TODO-stubs. With the reference gone and the stubs unfilled, the rule that the `name:` values must obey is left undocumented, which is exactly the condition that lets finding #1/#2 slip through.

No security issues (digests/URLs only, no secrets or injection surface). The registry-host additions to `otel`/`vault-k8s`/`openbao-*` URLs in 4.9.1 are consistent with the convention and fine.

#### Chunk 3/3: `charts/podiumd/docs/images/images-baseline.yaml`

## Review

This diff wholesale-regenerates `charts/podiumd/docs/images/images-baseline.yaml`. The new header redefines the file as a "full, CURRENT snapshot" produced by `lib.image_docs.regenerate_images_baseline_manifest`, and explicitly states the naming contract:

> `name = strip_registry(url): upstream url with the registry host removed, full <namespace>/<repo> path kept.`

Two entries in the regenerated output violate that contract, and both are inconsistent with sibling entries in the same file that correctly keep the namespace.

### Findings

**1. `name: python` drops the `library` namespace (line 49)** — SELF-CONTAINED, High, correctness
The entry is `name: python` / `url: docker.io/library/python`. Per the header's own convention, the name must be `library/python` (registry host removed, namespace kept). This directly contradicts the header, and is inconsistent with the sibling entries `library/busybox`, `library/postgres`, and `library/solr` in the same file, all of which correctly retain the `library/` prefix. The old file had `name: library/python` for the same URL, so this is a regression introduced by the regeneration. Failure scenario: any consumer that derives the mirror path from `name` (e.g. `<registry>/<name>`) will mirror to `…/python` instead of `…/library/python`, so a lookup or pull keyed on the conventional `library/python` path will miss the entry.

**2. `name: zaakbrug` drops the `wearefrank` namespace (line 284)** — SELF-CONTAINED, High, correctness
The entry is `name: zaakbrug` / `url: docker.io/wearefrank/zaakbrug`. Per the header's convention the name must be `wearefrank/zaakbrug`. The old file had `name: wearefrank/zaakbrug` for the same URL, so this is also a regression. Same failure scenario as above: the mirror path / lookup key is wrong.

Both defects are provable from the diff alone (the header's stated convention vs. the emitted entries), and both are the same class of bug: the generator is not applying `strip_registry` uniformly — it keeps the namespace for `library/busybox`, `library/postgres`, `library/solr` but drops it for `library/python` and `wearefrank/zaakbrug`. That non-uniformity is the tell that this is a generator defect rather than an intentional convention change (if the convention had genuinely changed, all `library/*` entries would be affected, not just one).

No other issues worth flagging: the dual-version collapse (e.g. the four `nginx-unprivileged` entries → one, the three `library/python` → one) is consistent with the "no stale dual-version entries" claim; all 60 entries carry a digest; the `elastic/eck-operator` → `eck/eck-operator` URL change is a path correction with an identical digest (same image), not a defect; and the removed "NOT INCLUDED" notes are explicitly sanctioned by the new header.
