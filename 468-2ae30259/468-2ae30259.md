## Review

This is a docs‑only chunk (2/2) describing the namespace‑portability change. The Redis bare‑name and Django‑wildcard explanations are internally consistent and technically sound (Django's `validate_host` uses an `endswith` check, so `.svc.cluster.local` genuinely matches any `*.svc.cluster.local` FQDN). The concerns below are about two claims that are *likely* false or unverified, plus one completeness gap.

### 1. The `.svc.cluster.local` "accepted by nginx `server_name`" claim is suspect
`charts/podiumd/docs/misc/deploying-to-a-custom-namespace.md`, line 15 (also `openbeheer.md` ~line 223, which explicitly ties the value to the nginx sidecar).

**ASSUMED** — I'm assuming the chart passes the raw `allowedHosts` value into an nginx `server_name` without transforming it; that templating is not in this diff, so this is unverified. nginx only treats `*` and `?` as wildcards in `server_name`; a *leading dot* is **not** a wildcard, so `.svc.cluster.local` is parsed as a literal hostname and will never match a real request. Django accepts the leading dot (subdomain rule), which is why the doc's "accepted by **both**" phrasing is the problem: the same literal works for Django but not for nginx.

Failure scenario: openbeheer's nginx sidecar has `server_name .svc.cluster.local;` (literal). A request to `openbeheer-nginx.<ns>.svc.cluster.local` doesn't match that block; if the block isn't also the `default_server`, nginx falls through and returns 404/default, breaking the sidecar. If the chart actually rewrites `.svc.cluster.local` → `*.svc.cluster.local` for nginx (or relies on a single catch‑all `default_server`), this is a non‑issue — but the doc should then say so rather than claim the raw value is "accepted by" nginx.

### 2. The "ECK cert SAN includes the short name" claim needs verification
`charts/podiumd/docs/misc/deploying-to-a-custom-namespace.md`, line 17 (also `elastic-BASICS.md` ~line 90).

**ASSUMED** — I'm assuming ECK's self‑signed Kibana certificate may contain only the FQDN SAN (`kiss-kb-http.<ns>.svc.cluster.local`) and not the bare short name; ECK's actual SAN generation is not in this diff, so this is unverified. If the SAN lacks the short name, any client that dials `kiss-kb-http:5601` over HTTPS will fail TLS hostname validation.

Failure scenario: an app (or a browser) connects to `kiss-kb-http:5601`; the presented cert's SAN is `kiss-kb-http.<ns>.svc.cluster.local` only, the requested name `kiss-kb-http` doesn't match, and the handshake is rejected — Kibana becomes unreachable. Please confirm against a real ECK‑generated Kibana cert before shipping this as a guarantee.

### 3. Release upgrade guide is incomplete and the images file dangles off it
`charts/podiumd/docs/_UPGRADE_PATHS/4.9.1-to-4.9.2-upgrade.md` (empty "Component versions" table at lines 10–11, TODOs at lines 6 and 36) and `charts/podiumd/docs/images/images-4.9.2.yaml`, line 7.

**SELF‑CONTAINED** — both files are in this diff. `images-4.9.2.yaml` tells readers to "See `4.9.1-to-4.9.2-upgrade.md` for the operator upgrade notes," but that doc's component table is empty and its only "Changes" entry is the namespace‑portability note — there are no operator upgrade notes to point at, and the guide still carries `TODO: describe this hop's changes.`

Failure scenario: an operator upgrading 4.9.1→4.9.2 follows the images file to the upgrade guide for the promised operator notes and finds an empty table and TODO placeholders, so the hop is effectively undocumented.
